# Структуры, методы и интерфейсы

**[Весь код для этой главы вы можете найти здесь](https://github.com/quii/learn-go-with-tests/tree/main/structs)**

Предположим, нам нужен геометрический код для вычисления периметра прямоугольника по заданной высоте и ширине. Мы можем написать функцию `Perimeter(width float64, height float64)`, где `float64` предназначен для чисел с плавающей точкой, таких как `123.45`.

К этому моменту цикл TDD должен быть вам хорошо знаком.

## Сначала напишите тест

```go
func TestPerimeter(t *testing.T) {
	got := Perimeter(10.0, 10.0)
	want := 40.0

	if got != want {
		t.Errorf("got %.2f want %.2f", got, want)
	}
}
```

Заметили новую строку форматирования? `f` — для нашего `float64`, а `.2` означает вывод 2 знаков после запятой.

## Попробуйте запустить тест

`./shapes_test.go:6:9: undefined: Perimeter`

## Напишите минимальный объем кода, чтобы тест запустился, и проверьте вывод неудачного теста

```go
func Perimeter(width float64, height float64) float64 {
	return 0
}
```

Результат: `shapes_test.go:10: got 0.00 want 40.00`.

## Напишите достаточно кода, чтобы тест прошел

```go
func Perimeter(width float64, height float64) float64 {
	return 2 * (width + height)
}
```

Пока все легко. Теперь давайте создадим функцию `Area(width, height float64)`, которая возвращает площадь прямоугольника.

Попробуйте сделать это самостоятельно, следуя циклу TDD.

В итоге у вас должны получиться тесты, похожие на эти

```go
func TestPerimeter(t *testing.T) {
	got := Perimeter(10.0, 10.0)
	want := 40.0

	if got != want {
		t.Errorf("got %.2f want %.2f", got, want)
	}
}

func TestArea(t *testing.T) {
	got := Area(12.0, 6.0)
	want := 72.0

	if got != want {
		t.Errorf("got %.2f want %.2f", got, want)
	}
}
```

Возможно, вы слышали, что сравнение чисел с плавающей точкой с помощью `!=`/`==` — плохая идея из-за способа их представления в памяти:

```go
func Example_floatComparison() {
	fmt.Println(0.1 + 0.2 == 0.3)

	var a, b, c float64 = 0.1, 0.2, 0.3
	fmt.Println(a+b == c)

	// Output:
	// true
	// false
}
```

Второе сравнение дает `false`, потому что `0.1` и `0.2` не могут быть точно представлены как `float64`, поэтому их сумма также не будет точно равна `0.3`. Первое сравнение дает `true` только потому, что оно записано как литеральное выражение — Go вычисляет такие выражения с произвольной точностью, а не как `float64`, до тех пор, пока они не будут присвоены какой-либо переменной.

Однако эта неточность не относится к нашему тесту `Area` выше: каждое используемое нами значение (`12.0`, `6.0`, `72.0` и так далее) является целым числом, которое `float64` _может_ представить точно, а умножение двух точно представленных чисел, пока результат остается в диапазоне, дает еще один точно представимый результат. Точное сравнение становится небезопасным только при введении значений или вычислений, которые не могут быть точно представлены, например, `0.1`, или результатов деления. Если вы пишете подобные тесты, используйте вместо этого сравнение с допустимой погрешностью, например [`cmp.Diff` с `cmpopts.EquateApprox`](https://pkg.go.dev/github.com/google/go-cmp/cmp/cmpopts#EquateApprox) из пакета `go-cmp`.

И код, похожий на этот

```go
func Perimeter(width float64, height float64) float64 {
	return 2 * (width + height)
}

func Area(width float64, height float64) float64 {
	return width * height
}
```

## Рефакторинг

Наш код работает, но он не содержит ничего явного о прямоугольниках. Невнимательный разработчик может попытаться передать этим функциям ширину и высоту треугольника, не понимая, что они вернут неверный ответ.

Мы могли бы просто дать функциям более специфичные имена, такие как `RectangleArea`. Более изящное решение — определить наш собственный _тип_ под названием `Rectangle`, который инкапсулирует эту концепцию.

Мы можем создать простой тип, используя **структуру**. [Структура](https://golang.org/ref/spec#Struct_types) — это просто именованная коллекция полей, где вы можете хранить данные.

Объявите структуру в вашем файле `shapes.go` следующим образом:

```go
type Rectangle struct {
	Width  float64
	Height float64
}
```

Теперь давайте проведем рефакторинг тестов, чтобы использовать `Rectangle` вместо простых `float64`.

```go
func TestPerimeter(t *testing.T) {
	rectangle := Rectangle{10.0, 10.0}
	got := Perimeter(rectangle)
	want := 40.0

	if got != want {
		t.Errorf("got %.2f want %.2f", got, want)
	}
}

func TestArea(t *testing.T) {
	rectangle := Rectangle{12.0, 6.0}
	got := Area(rectangle)
	want := 72.0

	if got != want {
		t.Errorf("got %.2f want %.2f", got, want)
	}
}
```

Не забудьте запустить тесты перед попыткой исправления. Тесты должны показать полезную ошибку, например:

```text
./shapes_test.go:7:18: not enough arguments in call to Perimeter
    have (Rectangle)
    want (float64, float64)
```

Вы можете получить доступ к полям структуры с помощью синтаксиса `myStruct.field`.

Измените две функции, чтобы исправить тест.

```go
func Perimeter(rectangle Rectangle) float64 {
	return 2 * (rectangle.Width + rectangle.Height)
}

func Area(rectangle Rectangle) float64 {
	return rectangle.Width * rectangle.Height
}
```

Надеюсь, вы согласитесь, что передача `Rectangle` в функцию более четко выражает наше намерение, но есть и другие преимущества использования структур, которые мы рассмотрим позже.

Наше следующее требование — написать функцию `Area` для кругов.

## Сначала напишите тест

```go
func TestArea(t *testing.T) {

	t.Run("rectangles", func(t *testing.T) {
		rectangle := Rectangle{12, 6}
		got := Area(rectangle)
		want := 72.0

		if got != want {
			t.Errorf("got %g want %g", got, want)
		}
	})

	t.Run("circles", func(t *testing.T) {
		circle := Circle{10}
		got := Area(circle)
		want := 314.1592653589793

		if got != want {
			t.Errorf("got %g want %g", got, want)
		}
	})

}
```

Как вы можете видеть, `f` был заменен на `g`, и на это есть веская причина.
Использование `g` выведет более точное десятичное число в сообщении об ошибке \([опции fmt](https://golang.org/pkg/fmt/)\).
Например, при использовании радиуса 1.5 в расчете площади круга, `f` показал бы `7.068583`, тогда как `g` показал бы `7.0685834705770345`.

## Попробуйте запустить тест

`./shapes_test.go:28:13: undefined: Circle`

## Напишите минимальный объем кода, чтобы тест запустился, и проверьте вывод неудачного теста

Нам нужно определить наш тип `Circle`.

```go
type Circle struct {
	Radius float64
}
```

Теперь попробуйте запустить тесты снова

`./shapes_test.go:29:14: cannot use circle (type Circle) as type Rectangle in argument to Area`

Некоторые языки программирования позволяют делать нечто подобное:

```go
func Area(circle Circle) float64       {}
func Area(rectangle Rectangle) float64 {}
```

Но вы не можете в Go

`./shapes.go:20:32: Area redeclared in this block`

У нас есть два варианта:

*   Вы можете иметь функции с одинаковыми именами, объявленные в разных _пакетах_. Таким образом, мы могли бы создать нашу `Area(Circle)` в новом пакете, но здесь это кажется избыточным.
*   Вместо этого мы можем определить [_методы_](https://golang.org/ref/spec#Method_declarations) для наших недавно определенных типов.

### Что такое методы?

До сих пор мы писали только _функции_, но использовали некоторые методы. Когда мы вызываем `t.Errorf`, мы вызываем метод `Errorf` на экземпляре нашего `t` \(`testing.T`\).

Метод — это функция с получателем.
Объявление метода связывает идентификатор, имя метода, с методом и ассоциирует метод с базовым типом получателя.

Методы очень похожи на функции, но они вызываются путем вызова на экземпляре конкретного типа. В то время как вы можете вызывать функции где угодно, например `Area(rectangle)`, методы вы можете вызывать только на "объектах".

Пример поможет, поэтому давайте сначала изменим наши тесты для вызова методов, а затем исправим код.

```go
func TestArea(t *testing.T) {

	t.Run("rectangles", func(t *testing.T) {
		rectangle := Rectangle{12, 6}
		got := rectangle.Area()
		want := 72.0

		if got != want {
			t.Errorf("got %g want %g", got, want)
		}
	})

	t.Run("circles", func(t *testing.T) {
		circle := Circle{10}
		got := circle.Area()
		want := 314.1592653589793

		if got != want {
			t.Errorf("got %g want %g", got, want)
		}
	})

}
```

Если мы попробуем запустить тесты, мы получим

```text
./shapes_test.go:19:19: rectangle.Area undefined (type Rectangle has no field or method Area)
./shapes_test.go:29:16: circle.Area undefined (type Circle has no field or method Area)
```

> type Circle has no field or method Area

Я хотел бы еще раз подчеркнуть, насколько хорош здесь компилятор. Очень важно не торопясь читать сообщения об ошибках, это поможет вам в долгосрочной перспективе.

## Напишите минимальный объем кода, чтобы тест запустился, и проверьте вывод неудачного теста

Давайте добавим несколько методов к нашим типам

```go
type Rectangle struct {
	Width  float64
	Height float64
}

func (r Rectangle) Area() float64 {
	return 0
}

type Circle struct {
	Radius float64
}

func (c Circle) Area() float64 {
	return 0
}
```

Синтаксис объявления методов почти такой же, как и функций, и это потому, что они так похожи. Единственное отличие — это синтаксис получателя метода `func (receiverName ReceiverType) MethodName(args)`.

Когда ваш метод вызывается на переменной этого типа, вы получаете ссылку на ее данные через переменную `receiverName`. Во многих других языках программирования это делается неявно, и вы обращаетесь к получателю через `this`.

В Go принято, чтобы переменная-получатель была первой буквой типа.

```
r Rectangle
```

Если вы попробуете снова запустить тесты, они теперь должны скомпилироваться и выдать сообщение о неудачном прохождении.

## Напишите достаточно кода, чтобы тест прошел

Теперь давайте заставим наши тесты для прямоугольников пройти, исправив наш новый метод

```go
func (r Rectangle) Area() float64 {
	return r.Width * r.Height
}
```

Если вы снова запустите тесты, тесты для прямоугольника должны пройти, но тесты для круга по-прежнему будут завершаться неудачей.

Чтобы заставить функцию `Area` круга пройти, мы возьмем константу `Pi` из пакета `math` \(не забудьте импортировать его\).

```go
func (c Circle) Area() float64 {
	return math.Pi * c.Radius * c.Radius
}
```

## Рефакторинг

В наших тестах есть некоторое дублирование.

Все, что мы хотим сделать, это взять коллекцию _фигур_, вызвать на них метод `Area()` и затем проверить результат.

Мы хотим иметь возможность написать некую функцию `checkArea`, которой мы могли бы передавать как `Rectangle`, так и `Circle`, но при этом она не должна компилироваться, если мы попытаемся передать что-то, что не является фигурой.

В Go мы можем кодифицировать это намерение с помощью **интерфейсов**.

[Интерфейсы](https://golang.org/ref/spec#Interface_types) — очень мощная концепция в статически типизированных языках, таких как Go, поскольку они позволяют создавать функции, которые можно использовать с различными типами, и создавать сильно декомпозированный код, сохраняя при этом типовую безопасность.

Давайте введем это, проведя рефакторинг наших тестов.

```go
func TestArea(t *testing.T) {

	checkArea := func(t testing.TB, shape Shape, want float64) {
		t.Helper()
		got := shape.Area()
		if got != want {
			t.Errorf("got %g want %g", got, want)
		}
	}

	t.Run("rectangles", func(t *testing.T) {
		rectangle := Rectangle{12, 6}
		checkArea(t, rectangle, 72.0)
	})

	t.Run("circles", func(t *testing.T) {
		circle := Circle{10}
		checkArea(t, circle, 314.1592653589793)
	})

}
```

Мы создаем вспомогательную функцию, как и в других упражнениях, но на этот раз мы просим передать `Shape`. Если мы попытаемся вызвать ее с чем-то, что не является фигурой, то она не скомпилируется.

Как что-то становится фигурой? Мы просто сообщаем Go, что такое `Shape`, используя объявление интерфейса

```go
type Shape interface {
	Area() float64
}
```

Мы создаем новый `type` так же, как мы делали это с `Rectangle` и `Circle`, но на этот раз это `interface`, а не `структура`.

Как только вы добавите это в код, тесты пройдут.

### Подождите, что?

Это довольно сильно отличается от интерфейсов в большинстве других языков программирования. Обычно вам приходится писать код, чтобы сказать `Мой тип Foo реализует интерфейс Bar`.

Но в нашем случае

*   У `Rectangle` есть метод `Area`, который возвращает `float64`, поэтому он удовлетворяет интерфейсу `Shape`.
*   У `Circle` есть метод `Area`, который возвращает `float64`, поэтому он удовлетворяет интерфейсу `Shape`.
*   У `string` нет такого метода, поэтому он не удовлетворяет интерфейсу.
*   и т. д.

В Go **разрешение интерфейсов неявное**. Если передаваемый вами тип соответствует тому, что требует интерфейс, код скомпилируется.

### Снижение связности

Обратите внимание, что нашей вспомогательной функции не нужно беспокоиться о том, является ли фигура `Rectangle`, `Circle` или `Triangle`. Объявляя интерфейс, вспомогательная функция _снижает связность_ с конкретными типами и имеет только тот метод, который ей нужен для выполнения своей работы.

Такой подход использования интерфейсов для объявления **только того, что вам нужно**, очень важен в проектировании программного обеспечения и будет более подробно рассмотрен в следующих разделах.

## Дальнейший рефакторинг

Теперь, когда у вас есть некоторое представление о структурах, мы можем ввести "табличные тесты".

[Табличные тесты](https://go.dev/wiki/TableDrivenTests) полезны, когда вы хотите создать список тестовых случаев, которые могут быть протестированы одним и тем же способом.

```go
func TestArea(t *testing.T) {

	areaTests := []struct {
		shape Shape
		want  float64
	}{
		{Rectangle{12, 6}, 72.0},
		{Circle{10}, 314.1592653589793},
	}

	for _, tt := range areaTests {
		got := tt.shape.Area()
		if got != tt.want {
			t.Errorf("got %g want %g", got, tt.want)
		}
	}

}
```

Единственный новый синтаксис здесь — это создание "анонимной структуры", `areaTests`. Мы объявляем срез структур, используя `[]struct` с двумя полями: `shape` и `want`. Затем мы заполняем срез тестовыми случаями.

Затем мы итерируем по ним так же, как и по любому другому срезу, используя поля структуры для запуска наших тестов.

Вы видите, как легко разработчику будет ввести новую фигуру, реализовать `Area`, а затем добавить ее в тестовые случаи. Кроме того, если обнаружена ошибка в `Area`, очень легко добавить новый тестовый случай для ее проверки перед исправлением.

Табличные тесты могут быть отличным инструментом в вашем арсенале, но убедитесь, что у вас есть необходимость в дополнительном "шуме" в тестах.
Они отлично подходят, когда вы хотите протестировать различные реализации интерфейса или когда данные, передаваемые в функцию, имеют множество различных требований, которые необходимо протестировать.

Давайте продемонстрируем все это, добавив еще одну фигуру и протестировав ее; треугольник.

## Сначала напишите тест

Добавить новый тест для нашей новой фигуры очень просто. Просто добавьте `{Triangle{12, 6}, 36.0},` в наш список.

```go
func TestArea(t *testing.T) {

	areaTests := []struct {
		shape Shape
		want  float64
	}{
		{Rectangle{12, 6}, 72.0},
		{Circle{10}, 314.1592653589793},
		{Triangle{12, 6}, 36.0},
	}

	for _, tt := range areaTests {
		got := tt.shape.Area()
		if got != tt.want {
			t.Errorf("got %g want %g", got, tt.want)
		}
	}

}
```

## Попробуйте запустить тест

Помните, продолжайте запускать тест и позвольте компилятору направить вас к решению.

## Рефакторинг

Опять же, реализация в порядке, но наши тесты можно было бы улучшить.

Когда вы сканируете это

```
{Rectangle{12, 6}, 72.0},
{Circle{10}, 314.1592653589793},
{Triangle{12, 6}, 36.0},
```

Не сразу понятно, что означают все эти числа, и вы должны стремиться к тому, чтобы ваши тесты были легко понятны.

До сих пор вам показывался только синтаксис создания экземпляров структур `MyStruct{val1, val2}`, но вы можете опционально называть поля.

Давайте посмотрим, как это выглядит

```
        {shape: Rectangle{Width: 12, Height: 6}, want: 72.0},
        {shape: Circle{Radius: 10}, want: 314.1592653589793},
        {shape: Triangle{Base: 12, Height: 6}, want: 36.0},
```

В книге [Разработка через тестирование: примеры](https://g.co/kgs/yCzDLF) Кент Бек рефакторит некоторые тесты до определенного момента и утверждает:

> Тест говорит с нами более ясно, как будто это утверждение истины, **а не последовательность операций**

(выделение в цитате моё)

Теперь наши тесты — точнее, список тестовых случаев — делают утверждения об истинности фигур и их площадей.

## Убедитесь, что вывод вашего теста полезен

Помните, когда мы ранее реализовывали `Triangle` и у нас был неудачный тест? Он вывел `shapes_test.go:31: got 0.00 want 36.00`.

Мы знали, что это связано с `Triangle`, потому что мы только что работали с ним.
Но что, если ошибка прокралась в систему в одном из 20 случаев в таблице?
Как разработчик узнает, какой случай не прошел?
Это не очень хороший опыт для разработчика, ему придется вручную просматривать случаи, чтобы выяснить, какой из них фактически не прошел.

Мы можем изменить наше сообщение об ошибке на `%#v got %g want %g`. Строка форматирования `%#v` выведет нашу структуру со значениями ее полей, чтобы разработчик мог с первого взгляда увидеть проверяемые свойства.

Чтобы еще больше повысить читаемость наших тестовых случаев, мы можем переименовать поле `want` во что-то более описательное, например `hasArea`.

Последний совет по табличным тестам — используйте `t.Run` и называйте тестовые случаи.

Оборачивая каждый случай в `t.Run`, вы получите более четкий вывод теста при ошибках, так как будет напечатано имя тестового случая.

```text
--- FAIL: TestArea (0.00s)
    --- FAIL: TestArea/Rectangle (0.00s)
        shapes_test.go:33: main.Rectangle{Width:12, Height:6} got 72.00 want 72.10
```

И вы можете запускать конкретные тесты в вашей таблице с помощью `go test -run TestArea/Rectangle`.

Вот наш окончательный тестовый код, который это отражает

```go
func TestArea(t *testing.T) {

	areaTests := []struct {
		name    string
		shape   Shape
		hasArea float64
	}{
		{name: "Rectangle", shape: Rectangle{Width: 12, Height: 6}, hasArea: 72.0},
		{name: "Circle", shape: Circle{Radius: 10}, hasArea: 314.1592653589793},
		{name: "Triangle", shape: Triangle{Base: 12, Height: 6}, hasArea: 36.0},
	}

	for _, tt := range areaTests {
		// using tt.name from the case to use it as the `t.Run` test name
		t.Run(tt.name, func(t *testing.T) {
			got := tt.shape.Area()
			if got != tt.hasArea {
				t.Errorf("%#v got %g want %g", tt.shape, got, tt.hasArea)
			}
		})

	}

}
```

## Подведение итогов

Это была еще одна практика TDD, итеративное улучшение наших решений для базовых математических задач и изучение новых возможностей языка, мотивированное нашими тестами.

*   Объявление структур для создания ваших собственных типов данных, что позволяет связывать связанные данные вместе и делать намерение вашего кода более ясным.
*   Объявление интерфейсов, чтобы вы могли определять функции, которые могут использоваться с различными типами \([ad hoc полиморфизм](https://en.wikipedia.org/wiki/Ad_hoc_polymorphism)\).
*   Добавление методов, чтобы вы могли добавлять функциональность к вашим типам данных и таким образом реализовывать интерфейсы.
*   Табличные тесты, чтобы сделать ваши утверждения более ясными, а наборы тестов — более простыми для расширения и поддержки.

Это была важная глава, потому что теперь мы начинаем определять свои собственные типы. В статически типизированных языках, таких как Go, умение проектировать свои собственные типы имеет решающее значение для создания программного обеспечения, которое легко понять, собрать воедино и протестировать.

Интерфейсы — отличный инструмент для сокрытия сложности от других частей системы. В нашем случае нашему вспомогательному _коду_ теста не нужно было знать точную форму, для которой он делал утверждение, только как "спросить" ее площадь.

По мере того, как вы будете лучше знакомиться с Go, вы начнете видеть истинную силу интерфейсов и стандартной библиотеки. Вы узнаете об интерфейсах, определенных в стандартной библиотеке, которые используются _повсюду_, и, реализуя их для своих собственных типов, вы сможете очень быстро повторно использовать множество замечательных функций.
