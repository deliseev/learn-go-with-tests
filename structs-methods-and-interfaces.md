# Структуры, методы и интерфейсы

**[Весь код для этой главы вы можете найти здесь](https://github.com/quii/learn-go-with-tests/tree/main/structs)**

Предположим, что нам нужен некоторый геометрический код для вычисления периметра прямоугольника по заданной высоте и ширине. Мы можем написать функцию `Perimeter(width float64, height float64)`, где `float64` используется для чисел с плавающей запятой, таких как `123.45`.

Цикл TDD должен быть вам уже достаточно хорошо знаком.

## Напишите тест первым

```go
func TestPerimeter(t *testing.T) {
	got := Perimeter(10.0, 10.0)
	want := 40.0

	if got != want {
		t.Errorf("got %.2f want %.2f", got, want)
	}
}
```

Обратили внимание на новую строку формата? Символ `f` предназначен для нашего `float64`, а `.2` означает вывод 2 знаков после запятой.

## Попробуйте запустить тест

`./shapes_test.go:6:9: undefined: Perimeter`

## Напишите минимальный код, чтобы тест запустился, и проверьте вывод неудачного теста

```go
func Perimeter(width float64, height float64) float64 {
	return 0
}
```

В результате получаем `shapes_test.go:10: got 0.00 want 40.00`.

## Напишите достаточно кода, чтобы тест прошел

```go
func Perimeter(width float64, height float64) float64 {
	return 2 * (width + height)
}
```

Пока все легко. Теперь давайте создадим функцию под названием `Area(width, height float64)`, которая возвращает площадь прямоугольника.

Попробуйте сделать это самостоятельно, следуя циклу TDD.

В итоге вы должны получить тесты, похожие на эти:

```go
func TestPerimeter(t *testing.T) {
	got := Perimeter(10.0, 10.0)
	want := 40.0

	if got != want {
		t.Errorf("got %.2f want %.2f", got, want)
	}
}

func TestArea(t *testing.T) {
	got := Area(12.0, 6.0)
	want := 72.0

	if got != want {
		t.Errorf("got %.2f want %.2f", got, want)
	}
}
```

Возможно, вы слышали, что сравнение чисел с плавающей запятой с помощью `!=`/`==` является плохой идеей из-за того, как они представлены в памяти:

```go
func Example_floatComparison() {
	fmt.Println(0.1 + 0.2 == 0.3)

	var a, b, c float64 = 0.1, 0.2, 0.3
	fmt.Println(a+b == c)

	// Output:
	// true
	// false
}
```

Второе сравнение дает `false`, потому что `0.1` и `0.2` не могут быть представлены точно как `float64`, поэтому их сложение также не дает ровно `0.3`. Первое сравнение дает `true` только потому, что оно записано как литеральное выражение — Go вычисляет их с произвольной точностью, а не как `float64`, до тех пор, пока они не будут присвоены чему-либо.

Однако эта неточность не относится к нашему тесту `Area` выше: каждое используемое нами значение (`12.0`, `6.0`, `72.0` и так далее) является целым числом, которое `float64` *может* точно представить, и умножение двух точно представленных чисел, пока результат остается в диапазоне, дает еще один точно представимый результат. Точное сравнение становится небезопасным только тогда, когда вы вводите значения или вычисления, которые не могут быть точно представлены, например `0.1`, или результаты деления. Если вы обнаружите, что пишете подобные тесты, вместо этого используйте сравнение с допустимым допуском, например [`cmp.Diff` с `cmpopts.EquateApprox`](https://pkg.go.dev/github.com/google/go-cmp/cmp/cmpopts#EquateApprox) из `go-cmp`.

И код, похожий на этот:

```go
func Perimeter(width float64, height float64) float64 {
	return 2 * (width + height)
}

func Area(width float64, height float64) float64 {
	return width * height
}
```

## Рефакторинг

Наш код справляется со своей задачей, но в нем нет ничего явного о прямоугольниках. Неосторожный разработчик может попытаться передать ширину и высоту треугольника этим функциям, не осознавая, что они вернут неверный ответ.

Мы могли бы просто дать функциям более конкретные имена, такие как `RectangleArea`. Более изящное решение — определить наш собственный *тип* под названием `Rectangle`, который инкапсулирует эту концепцию для нас.

Мы можем создать простой тип, используя **структуру**. [Структура](https://golang.org/ref/spec#Struct_types) — это просто именованная коллекция полей, где вы можете хранить данные.

Объявите структуру в вашем файле `shapes.go` следующим образом:

```go
type Rectangle struct {
	Width  float64
	Height float64
}
```

Теперь давайте проведем рефакторинг тестов, чтобы использовать `Rectangle` вместо обычных `float64`.

```go
func TestPerimeter(t *testing.T) {
	rectangle := Rectangle{10.0, 10.0}
	got := Perimeter(rectangle)
	want := 40.0

	if got != want {
		t.Errorf("got %.2f want %.2f", got, want)
	}
}

func TestArea(t *testing.T) {
	rectangle := Rectangle{12.0, 6.0}
	got := Area(rectangle)
	want := 72.0

	if got != want {
		t.Errorf("got %.2f want %.2f", got, want)
	}
}
```

Не забудьте запустить тесты перед тем, как пытаться исправить. Тесты должны показать полезную ошибку, например:

```text
./shapes_test.go:7:18: not enough arguments in call to Perimeter
    have (Rectangle)
    want (float64, float64)
```

Вы можете получить доступ к полям структуры с помощью синтаксиса `myStruct.field`.

Измените две функции, чтобы исправить тест.

```go
func Perimeter(rectangle Rectangle) float64 {
	return 2 * (rectangle.Width + rectangle.Height)
}

func Area(rectangle Rectangle) float64 {
	return rectangle.Width * rectangle.Height
}
```

Надеюсь, вы согласитесь, что передача `Rectangle` в функцию более четко выражает наше намерение, но есть и другие преимущества использования структур, которые мы рассмотрим позже.

Наше следующее требование — написать функцию `Area` для кругов.

## Напишите тест первым

```go
func TestArea(t *testing.T) {

	t.Run("rectangles", func(t *testing.T) {
		rectangle := Rectangle{12, 6}
		got := Area(rectangle)
		want := 72.0

		if got != want {
			t.Errorf("got %g want %g", got, want)
		}
	})

	t.Run("circles", func(t *testing.T) {
		circle := Circle{10}
		got := Area(circle)
		want := 314.1592653589793

		if got != want {
			t.Errorf("got %g want %g", got, want)
		}
	})

}
```

Как видите, `f` был заменен на `g`, и на то есть веская причина. Использование `g` выведет более точное десятичное число в сообщении об ошибке ([опции fmt](https://golang.org/pkg/fmt/)). Например, при расчете площади круга с радиусом 1.5, `f` показал бы `7.068583`, тогда как `g` показал бы `7.0685834705770345`.

## Попробуйте запустить тест

`./shapes_test.go:28:13: undefined: Circle`

## Напишите минимальный код, чтобы тест запустился, и проверьте вывод неудачного теста

Нам нужно определить наш тип `Circle`.

```go
type Circle struct {
	Radius float64
}
```

Теперь попробуйте снова запустить тесты:

`./shapes_test.go:29:14: cannot use circle (type Circle) as type Rectangle in argument to Area`

Некоторые языки программирования позволяют делать нечто подобное:

```go
func Area(circle Circle) float64       {}
func Area(rectangle Rectangle) float64 {}
```

Но в Go это невозможно:

`./shapes.go:20:32: Area redeclared in this block`

У нас есть два варианта:

*   Вы можете иметь функции с одинаковым именем, объявленные в разных *пакетах*. Таким образом, мы могли бы создать нашу `Area(Circle)` в новом пакете, но здесь это кажется избыточным.
*   Вместо этого мы можем определить [_методы_](https://golang.org/ref/spec#Method_declarations) для наших вновь определенных типов.

### Что такое методы?

До сих пор мы писали только *функции*, но уже использовали некоторые методы. Когда мы вызываем `t.Errorf`, мы вызываем метод `Errorf` для экземпляра нашего `t` (`testing.T`).

Метод — это функция с получателем. Объявление метода связывает идентификатор, имя метода, с методом и ассоциирует метод с базовым типом получателя.

Методы очень похожи на функции, но они вызываются путем их вызова на экземпляре определенного типа. В то время как функции можно вызывать где угодно, например `Area(rectangle)`, методы можно вызывать только на "вещах".

Пример поможет, поэтому давайте сначала изменим наши тесты для вызова методов, а затем исправим код.

```go
func TestArea(t *testing.T) {

	t.Run("rectangles", func(t *testing.T) {
		rectangle := Rectangle{12, 6}
		got := rectangle.Area()
		want := 72.0

		if got != want {
			t.Errorf("got %g want %g", got, want)
		}
	})

	t.Run("circles", func(t *testing.T) {
		circle := Circle{10}
		got := circle.Area()
		want := 314.1592653589793

		if got != want {
			t.Errorf("got %g want %g", got, want)
		}
	})

}
```

Если мы попробуем запустить тесты, мы получим:

```text
./shapes_test.go:19:19: rectangle.Area undefined (type Rectangle has no field or method Area)
./shapes_test.go:29:16: circle.Area undefined (type Circle has no field or method Area)
```

> type Circle has no field or method Area

Хочу еще раз подчеркнуть, насколько прекрасен компилятор. Очень важно не торопиться и внимательно читать сообщения об ошибках, это поможет вам в долгосрочной перспективе.

## Напишите минимальный код, чтобы тест запустился, и проверьте вывод неудачного теста

Давайте добавим несколько методов к нашим типам:

```go
type Rectangle struct {
	Width  float64
	Height float64
}

func (r Rectangle) Area() float64 {
	return 0
}

type Circle struct {
	Radius float64
}

func (c Circle) Area() float64 {
	return 0
}
```

Синтаксис объявления методов почти такой же, как и функций, потому что они очень похожи. Единственное отличие — это синтаксис получателя метода `func (receiverName ReceiverType) MethodName(args)`.

Когда ваш метод вызывается для переменной этого типа, вы получаете ссылку на ее данные через переменную `receiverName`. Во многих других языках программирования это делается неявно, и вы обращаетесь к получателю через `this`.

В Go принято, чтобы переменная-получатель была первой буквой типа.

```
r Rectangle
```

Если вы попробуете снова запустить тесты, они должны скомпилироваться и выдать сообщение о неудачных тестах.

## Напишите достаточно кода, чтобы тест прошел

Теперь давайте сделаем так, чтобы наши тесты для прямоугольника прошли, исправив наш новый метод:

```go
func (r Rectangle) Area() float64 {
	return r.Width * r.Height
}
```

Если вы снова запустите тесты, тесты для прямоугольника должны пройти, но тесты для круга по-прежнему будут неудачными.

Чтобы функция `Area` для круга прошла, мы позаимствуем константу `Pi` из пакета `math` (не забудьте импортировать его).

```go
func (c Circle) Area() float64 {
	return math.Pi * c.Radius * c.Radius
}
```

## Рефакторинг

В наших тестах есть некоторое дублирование.

Все, что нам нужно сделать, это взять коллекцию *фигур*, вызвать на них метод `Area()` и затем проверить результат.

Мы хотим иметь возможность написать некую функцию `checkArea`, которой мы можем передавать как `Rectangle`, так и `Circle`, но которая не скомпилируется, если мы попытаемся передать что-то, что не является фигурой.

В Go мы можем кодифицировать это намерение с помощью **интерфейсов**.

[Интерфейсы](https://golang.org/ref/spec#Interface_types) — очень мощная концепция в статически типизированных языках, таких как Go, потому что они позволяют создавать функции, которые можно использовать с различными типами, и разрабатывать сильно декомпозированный код, сохраняя при этом типовую безопасность.

Давайте представим это, проведя рефакторинг наших тестов.

```go
func TestArea(t *testing.T) {

	checkArea := func(t testing.TB, shape Shape, want float64) {
		t.Helper()
		got := shape.Area()
		if got != want {
			t.Errorf("got %g want %g", got, want)
		}
	}

	t.Run("rectangles", func(t *testing.T) {
		rectangle := Rectangle{12, 6}
		checkArea(t, rectangle, 72.0)
	})

	t.Run("circles", func(t *testing.T) {
		circle := Circle{10}
		checkArea(t, circle, 314.1592653589793)
	})

}
```

Мы создаем вспомогательную функцию, как и в других упражнениях, но на этот раз мы просим передать `Shape`. Если мы попытаемся вызвать ее с чем-то, что не является фигурой, то она не скомпилируется.

Как что-то становится фигурой? Мы просто сообщаем Go, что такое `Shape`, используя объявление интерфейса:

```go
type Shape interface {
	Area() float64
}
```

Мы создаем новый тип, точно так же, как мы делали с `Rectangle` и `Circle`, но на этот раз это интерфейс, а не структура.

Как только вы добавите это в код, тесты пройдут.

### Подождите, что?

Это довольно сильно отличается от интерфейсов в большинстве других языков программирования. Обычно вам приходится писать код, чтобы сказать: "Мой тип `Foo` реализует интерфейс `Bar`".

Но в нашем случае:

*   `Rectangle` имеет метод `Area`, который возвращает `float64`, поэтому он удовлетворяет интерфейсу `Shape`
*   `Circle` имеет метод `Area`, который возвращает `float64`, поэтому он удовлетворяет интерфейсу `Shape`
*   `string` не имеет такого метода, поэтому он не удовлетворяет интерфейсу
*   и т.д.

В Go **разрешение интерфейсов неявно**. Если переданный вами тип соответствует тому, что запрашивает интерфейс, он скомпилируется.

### Развязка

Обратите внимание, что нашей вспомогательной функции не нужно беспокоиться о том, является ли фигура `Rectangle` или `Circle` или `Triangle`. Объявляя интерфейс, вспомогательная функция *развязана* от конкретных типов и имеет только тот метод, который ей нужен для выполнения своей работы.

Такой подход использования интерфейсов для объявления **только того, что вам нужно**, очень важен в проектировании программного обеспечения и будет рассмотрен более подробно в следующих разделах.

## Дальнейший рефакторинг

Теперь, когда у вас есть некоторое понимание структур, мы можем ввести "табличные тесты".

[Табличные тесты](https://go.dev/wiki/TableDrivenTests) полезны, когда вы хотите создать список тестовых случаев, которые могут быть протестированы одним и тем же способом.

```go
func TestArea(t *testing.T) {

	areaTests := []struct {
		shape Shape
		want  float64
	}{
		{Rectangle{12, 6}, 72.0},
		{Circle{10}, 314.1592653589793},
	}

	for _, tt := range areaTests {
		got := tt.shape.Area()
		if got != tt.want {
			t.Errorf("got %g want %g", got, tt.want)
		}
	}

}
```

Единственный новый синтаксис здесь — это создание "анонимной структуры", `areaTests`. Мы объявляем срез структур, используя `[]struct` с двумя полями: `shape` и `want`. Затем мы заполняем срез тестовыми случаями.

Затем мы итерируемся по ним так же, как и по любому другому срезу, используя поля структуры для выполнения наших тестов.

Вы видите, как легко разработчику будет ввести новую фигуру, реализовать `Area`, а затем добавить ее в тестовые случаи. Кроме того, если обнаружена ошибка в `Area`, очень легко добавить новый тестовый случай для ее проверки перед исправлением.

Табличные тесты могут быть отличным инструментом в вашем арсенале, но убедитесь, что вам действительно нужен дополнительный "шум" в тестах. Они отлично подходят, когда вы хотите протестировать различные реализации интерфейса, или если данные, передаваемые в функцию, имеют множество различных требований, которые необходимо проверить.

Давайте продемонстрируем все это, добавив еще одну фигуру и протестировав ее: треугольник.

## Напишите тест первым

Добавить новый тест для нашей новой фигуры очень просто. Просто добавьте `{Triangle{12, 6}, 36.0},` в наш список.

```go
func TestArea(t *testing.T) {

	areaTests := []struct {
		shape Shape
		want  float64
	}{
		{Rectangle{12, 6}, 72.0},
		{Circle{10}, 314.1592653589793},
		{Triangle{12, 6}, 36.0},
	}

	for _, tt := range areaTests {
		got := tt.shape.Area()
		if got != tt.want {
			t.Errorf("got %g want %g", got, tt.want)
		}
	}

}
```

## Попробуйте запустить тест

Помните: продолжайте запускать тест, и пусть компилятор направляет вас к решению.

## Напишите минимальный код, чтобы тест запустился, и проверьте вывод неудачного теста

`./shapes_test.go:25:4: undefined: Triangle`

Мы еще не определили `Triangle`.

```go
type Triangle struct {
	Base   float64
	Height float64
}
```

Попробуйте снова:

```text
./shapes_test.go:25:8: cannot use Triangle literal (type Triangle) as type Shape in field value:
    Triangle does not implement Shape (missing Area method)
```

Он говорит нам, что мы не можем использовать `Triangle` как фигуру, потому что у него нет метода `Area()`, поэтому добавьте пустую реализацию, чтобы тест заработал.

```go
func (t Triangle) Area() float64 {
	return 0
}
```

Наконец, код компилируется, и мы получаем нашу ошибку:

`shapes_test.go:31: got 0.00 want 36.00`

## Напишите достаточно кода, чтобы тест прошел

```go
func (t Triangle) Area() float64 {
	return (t.Base * t.Height) * 0.5
}
```

И наши тесты проходят!

## Рефакторинг

Опять же, реализация в порядке, но наши тесты можно улучшить.

Когда вы просматриваете это:

```
{Rectangle{12, 6}, 72.0},
{Circle{10}, 314.1592653589793},
{Triangle{12, 6}, 36.0},
```

Не сразу понятно, что означают все эти числа, и вы должны стремиться к тому, чтобы ваши тесты были легко понятны.

До сих пор вам был показан только синтаксис для создания экземпляров структур `MyStruct{val1, val2}`, но вы можете по желанию называть поля.

Давайте посмотрим, как это выглядит:

```
        {shape: Rectangle{Width: 12, Height: 6}, want: 72.0},
        {shape: Circle{Radius: 10}, want: 314.1592653589793},
        {shape: Triangle{Base: 12, Height: 6}, want: 36.0},
```

В книге [Test-Driven Development by Example](https://g.co/kgs/yCzDLF) Кент Бек рефакторизирует некоторые тесты до определенного момента и утверждает:

> Тест говорит с нами более ясно, как будто это утверждение истины, **а не последовательность операций**

(выделение в цитате моё)

Теперь наши тесты — точнее, список тестовых случаев — делают утверждения об истинности фигур и их площадей.

## Убедитесь, что вывод вашего теста полезен

Помните, когда мы ранее реализовывали `Triangle` и у нас был неудачный тест? Он вывел `shapes_test.go:31: got 0.00 want 36.00`.

Мы знали, что это было связано с `Triangle`, потому что мы только что работали с ним. Но что, если ошибка прокралась в систему в одном из 20 случаев в таблице? Как разработчик узнает, какой случай не сработал? Это не очень хороший опыт для разработчика, ему придется вручную просматривать случаи, чтобы выяснить, какой из них на самом деле провалился.

Мы можем изменить наше сообщение об ошибке на `%#v got %g want %g`. Форматная строка `%#v` выведет нашу структуру со значениями в ее полях, так что разработчик сможет с первого взгляда увидеть проверяемые свойства.

Чтобы еще больше улучшить читаемость наших тестовых случаев, мы можем переименовать поле `want` во что-то более описательное, например `hasArea`.

Последний совет по табличным тестам — использовать `t.Run` и называть тестовые случаи.

Оборачивая каждый случай в `t.Run`, вы получите более четкий вывод теста при ошибках, так как он будет выводить имя случая:

```text
--- FAIL: TestArea (0.00s)
    --- FAIL: TestArea/Rectangle (0.00s)
        shapes_test.go:33: main.Rectangle{Width:12, Height:6} got 72.00 want 72.10
```

И вы можете запускать конкретные тесты в вашей таблице с помощью `go test -run TestArea/Rectangle`.

Вот наш окончательный код теста, который это реализует:

```go
func TestArea(t *testing.T) {

	areaTests := []struct {
		name    string
		shape   Shape
		hasArea float64
	}{
		{name: "Rectangle", shape: Rectangle{Width: 12, Height: 6}, hasArea: 72.0},
		{name: "Circle", shape: Circle{Radius: 10}, hasArea: 314.1592653589793},
		{name: "Triangle", shape: Triangle{Base: 12, Height: 6}, hasArea: 36.0},
	}

	for _, tt := range areaTests {
		// using tt.name from the case to use it as the `t.Run` test name
		t.Run(tt.name, func(t *testing.T) {
			got := tt.shape.Area()
			if got != tt.hasArea {
				t.Errorf("%#v got %g want %g", tt.shape, got, tt.hasArea)
			}
		})

	}

}
```

## Подводим итоги

Это была еще одна практика TDD, итеративное решение базовых математических задач и изучение новых языковых особенностей, мотивированное нашими тестами.

*   Объявление структур для создания собственных типов данных, что позволяет объединять связанные данные и делать намерение вашего кода более ясным
*   Объявление интерфейсов, чтобы вы могли определять функции, которые могут использоваться различными типами ([специальный полиморфизм](https://en.wikipedia.org/wiki/Ad_hoc_polymorphism))
*   Добавление методов, чтобы вы могли добавлять функциональность к своим типам данных и таким образом реализовывать интерфейсы
*   Табличные тесты, чтобы сделать ваши утверждения более ясными, а наборы тестов — более легкими для расширения и поддержки

Это была важная глава, потому что мы теперь начинаем определять свои собственные типы. В статически типизированных языках, таких как Go, возможность проектировать собственные типы имеет решающее значение для создания программного обеспечения, которое легко понять, собрать воедино и протестировать.

Интерфейсы — отличный инструмент для сокрытия сложности от других частей системы. В нашем случае наш вспомогательный *код* теста не должен был знать точную форму, которую он проверял, а только то, как "запросить" ее площадь.

По мере того, как вы будете лучше знакомиться с Go, вы начнете видеть истинную мощь интерфейсов и стандартной библиотеки. Вы узнаете об интерфейсах, определенных в стандартной библиотеке, которые используются *повсюду*, и, реализуя их для своих собственных типов, вы сможете очень быстро повторно использовать множество отличной функциональности.
