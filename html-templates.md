# HTML Шаблоны

**[Весь код вы найдете здесь](https://github.com/quii/learn-go-with-tests/tree/main/blogrenderer)**

Мы живем в мире, где каждый хочет создавать веб-приложения с помощью новейшего модного фронтенд-фреймворка, построенного на гигабайтах транспилированного JavaScript, работающего со сложной системой сборки; [но, возможно, это не всегда необходимо](https://quii.dev/The_Web_I_Want).

Я бы сказал, что большинство Go-разработчиков ценят простой, стабильный и быстрый инструментарий, но мир фронтенда часто не соответствует этим требованиям.

Многие веб-сайты не нуждаются в [SPA](https://en.wikipedia.org/wiki/Single-page_application). **HTML и CSS — это фантастические способы доставки контента**, и вы можете использовать Go для создания веб-сайта, который будет доставлять HTML.

Если вы все еще хотите иметь некоторые динамические элементы, вы можете добавить немного клиентского JavaScript, или даже попробовать экспериментировать с [Hotwire](https://hotwired.dev), который позволяет обеспечить динамический пользовательский опыт с серверным подходом.

Вы можете генерировать HTML в Go, активно используя [`fmt.Fprintf`](https://pkg.go.dev/fmt#Fprintf), но в этой главе вы узнаете, что стандартная библиотека Go предоставляет инструменты для генерации HTML более простым и поддерживаемым способом. Вы также узнаете более эффективные способы тестирования такого кода, с которыми, возможно, не сталкивались раньше.

## Что мы собираемся создать

В главе [Чтение файлов](/reading-files.md) мы написали код, который принимает [`fs.FS`](https://pkg.go.dev/io/fs) (файловую систему) и возвращает срез `Post` для каждого найденного markdown-файла.

```go
posts, err := blogposts.NewPostsFromFS(os.DirFS("posts"))
```

Вот как мы определили `Post`:

```go
type Post struct {
	Title, Description, Body string
	Tags                     []string
}
```

Вот пример одного из markdown-файлов, который может быть разобран.

```markdown
Title: Welcome to my blog
Description: Introduction to my blog
Tags: cooking, family, live-laugh-love
---
# First recipe!
Welcome to my **amazing recipe blog**. I am going to write about my family recipes, and make sure I write a long, irrelevant and boring story about my family before you get to the actual instructions.
```

Если мы продолжим наше путешествие по созданию блог-программы, мы возьмем эти данные и сгенерируем из них HTML, чтобы наш веб-сервер мог возвращать его в ответ на HTTP-запросы.

Для нашего блога мы хотим генерировать два типа страниц:

1.  **Просмотр поста**. Отображает конкретный пост. Поле `Body` в `Post` — это строка, содержащая markdown, поэтому её следует преобразовать в HTML.
2.  **Индекс**. Перечисляет все посты с гиперссылками для просмотра конкретного поста.

Мы также захотим обеспечить единообразный внешний вид нашего сайта, поэтому для каждой страницы у нас будет стандартная HTML-разметка, такая как `<html>` и `<head>`, содержащая ссылки на CSS-таблицы стилей и всё остальное, что нам может понадобиться.

При создании блог-программы у вас есть несколько вариантов подхода к построению и отправке HTML в браузер пользователя.

Мы спроектируем наш код так, чтобы он принимал `io.Writer`. Это означает, что вызывающий наш код имеет гибкость:

- Записывать их в [os.File](https://pkg.go.dev/os#File), чтобы их можно было статически обслуживать.
- Записывать HTML непосредственно в [`http.ResponseWriter`](https://pkg.go.dev/net/http#ResponseWriter).
- Или просто записывать их куда угодно! Пока оно реализует `io.Writer`, пользователь может генерировать HTML из `Post`.

## Сначала напишите тест

Как всегда, важно обдумать требования, прежде чем слишком быстро погружаться в разработку. Как мы можем взять этот относительно большой набор требований и разбить его на небольшой, достижимый шаг, на котором мы можем сосредоточиться?

На мой взгляд, фактический просмотр контента имеет более высокий приоритет, чем индексная страница. Мы могли бы запустить этот продукт и делиться прямыми ссылками на наш замечательный контент. Индексная страница, которая не может ссылаться на сам контент, бесполезна.

Тем не менее, отрисовка поста, как описано ранее, всё ещё кажется большой задачей. Вся HTML-разметка, преобразование markdown-тела в HTML, вывод тегов и т.д.

На этом этапе я не слишком беспокоюсь о конкретной разметке, и простым первым шагом было бы просто проверить, можем ли мы отобразить заголовок поста как `<h1>`. Это *кажется* самым маленьким первым шагом, который может немного продвинуть нас вперед.

```go
package blogrenderer_test

import (
	"bytes"
	"github.com/quii/learn-go-with-tests/blogrenderer"
	"testing"
)

func TestRender(t *testing.T) {
	var (
		aPost = blogrenderer.Post{
			Title:       "hello world",
			Body:        "This is a post",
			Description: "This is a description",
			Tags:        []string{"go", "tdd"},
		}
	)

	t.Run("it converts a single post into HTML", func(t *testing.T) {
		buf := bytes.Buffer{}
		err := blogrenderer.Render(&buf, aPost)

		if err != nil {
			t.Fatal(err)
		}

		got := buf.String()
		want := `<h1>hello world</h1>`
		if got != want {
			t.Errorf("got '%s' want '%s'", got, want)
		}
	})
}
```

Наше решение принимать `io.Writer` также упрощает тестирование, в данном случае мы записываем в [`bytes.Buffer`](https://pkg.go.dev/bytes#Buffer), содержимое которого мы можем впоследствии проверить.

## Рефакторинг

Пока нечего особо рефакторить, поэтому перейдем к следующей итерации.

## Сначала напишите тест

Теперь, когда у нас есть очень базовая рабочая версия, мы можем итерировать над тестом, чтобы расширить функциональность. В данном случае, это отрисовка дополнительной информации из `Post`.

```go
	t.Run("it converts a single post into HTML", func(t *testing.T) {
		buf := bytes.Buffer{}
		err := blogrenderer.Render(&buf, aPost)

		if err != nil {
			t.Fatal(err)
		}

		got := buf.String()
		want := `<h1>hello world</h1>
<p>This is a description</p>
Tags: <ul><li>go</li><li>tdd</li></ul>`

		if got != want {
			t.Errorf("got '%s' want '%s'", got, want)

```

Обратите внимание, что написание этого *выглядит* неуклюже. Видеть всю эту разметку в тесте неприятно, и мы еще даже не добавили тело или фактический HTML, который нам нужен, со всем содержимым `<head>` и любой необходимой разметкой страницы.

Тем не менее, давайте потерпим эту боль *пока*.

## Напишите достаточно кода, чтобы он прошел

Попробуйте сделать это сами, а не копировать код. Вы должны обнаружить, что прохождение этого теста _немного раздражает_! Когда я попробовал, моя первая попытка выдала такую ошибку:

```
=== RUN   TestRender
=== RUN   TestRender/it_converts_a_single_post_into_HTML
    renderer_test.go:32: got '<h1>hello world</h1><p>This is a description</p><ul><li>go</li><li>tdd</li></ul>' want '<h1>hello world</h1>
        <p>This is a description</p>
        Tags: <ul><li>go</li><li></li></ul>'
```

Новые строки! Кому они нужны? Ну, нашему тесту нужны, потому что он сопоставляет точное строковое значение. Должен ли он? Я пока убрал новые строки, чтобы тест прошел.

```go
func Render(w io.Writer, p Post) error {
	_, err := fmt.Fprintf(w, "<h1>%s</h1>\n<p>%s</p>\n", p.Title, p.Description)
	if err != nil {
		return err
	}

	_, err = fmt.Fprint(w, "Tags: <ul>")
	if err != nil {
		return err
	}

	for _, tag := range p.Tags {
		_, err = fmt.Fprintf(w, "<li>%s</li>", tag)
		if err != nil {
			return err
		}
	}

	_, err = fmt.Fprint(w, "</ul>")
	if err != nil {
		return err
	}

	return nil
}
```

**Ой**. Не самый приятный код, который я написал, и мы все еще находимся на очень ранней стадии реализации нашей разметки. Нам понадобится гораздо больше контента и элементов на нашей странице, и мы быстро видим, что такой подход неприемлем.

Однако, что крайне важно, у нас есть проходящий тест; у нас есть работающее программное обеспечение.

## Рефакторинг

Имея страховку в виде проходящего теста для работающего кода, мы теперь можем подумать об изменении нашего подхода к реализации на этапе рефакторинга.

### Введение шаблонов

В Go есть два пакета для шаблонизации: [text/template](https://pkg.go.dev/text/template) и [html/template], и они используют один и тот же интерфейс. Оба они позволяют объединять шаблон и некоторые данные для получения строки.

В чем разница с HTML-версией?

> Пакет template (html/template) реализует управляемые данными шаблоны для генерации HTML-вывода, безопасного от внедрения кода. Он предоставляет тот же интерфейс, что и пакет text/template, и должен использоваться вместо text/template всякий раз, когда вывод является HTML.

Язык шаблонов очень похож на [Mustache](https://mustache.github.io) и позволяет динамически генерировать контент очень чистым способом с хорошим разделением ответственности. По сравнению с другими языками шаблонов, которые вы, возможно, использовали, он очень ограничен или "без логики", как любит говорить Mustache. Это важное **и преднамеренное** проектное решение.

Хотя здесь мы сосредоточены на генерации HTML, если ваш проект выполняет сложные конкатенации строк и инкантации, вы можете обратиться к `text/template`, чтобы привести свой код в порядок.

### Вернемся к коду

Вот шаблон для нашего блога:

`<h1>{{.Title}}</h1><p>{{.Description}}</p>Tags: <ul>{{range .Tags}}<li>{{.}}</li>{{end}}</ul>`

Где мы определяем эту строку? У нас есть несколько вариантов, но чтобы шаги были небольшими, давайте просто начнем с обычной строки:

```go
package blogrenderer

import (
	"html/template"
	"io"
)

const (
	postTemplate = `<h1>{{.Title}}</h1><p>{{.Description}}</p>Tags: <ul>{{range .Tags}}<li>{{.}}</li>{{end}}</ul>`
)

func Render(w io.Writer, p Post) error {
	templ, err := template.New("blog").Parse(postTemplate)
	if err != nil {
		return err
	}

	if err := templ.Execute(w, p); err != nil {
		return err
	}

	return nil
}
```

Мы создаем новый шаблон с именем, а затем разбираем нашу строку шаблона. Затем мы можем использовать метод `Execute`, передавая в него наши данные, в данном случае `Post`.

Шаблон заменит такие вещи, как `{{.Description}}`, на содержимое `p.Description`. Шаблоны также предоставляют некоторые примитивы программирования, такие как `range` для перебора значений и `if`. Более подробную информацию вы можете найти в [документации text/template](https://pkg.go.dev/text/template).

*Это должен быть чистый рефакторинг.* Нам не нужно будет менять наши тесты, и они должны продолжать проходить. Важно отметить, что наш код стал легче читать и содержит гораздо меньше неприятной обработки ошибок.

Часто люди жалуются на многословность обработки ошибок в Go, но вы можете обнаружить, что можно найти лучшие способы написания кода, чтобы он был менее подвержен ошибкам изначально, как здесь.

### Больше рефакторинга

Использование `html/template` определенно стало улучшением, но наличие его в виде строковой константы в нашем коде не очень хорошо:

- Его все еще довольно сложно читать.
- Он не удобен для IDE/редактора. Нет подсветки синтаксиса, возможности форматирования, рефакторинга и т. д.
- Он выглядит как HTML, но вы не можете работать с ним так, как с "обычным" HTML-файлом.

Что бы нам хотелось сделать, так это хранить наши шаблоны в отдельных файлах, чтобы мы могли лучше их организовать и работать с ними как с HTML-файлами.

Создайте папку "templates" и внутри нее файл `blog.gohtml`, вставьте наш шаблон в этот файл.

Теперь измените наш код для встраивания файловых систем, используя [функциональность встраивания, включенную в Go 1.16](https://pkg.go.dev/embed).

```go
package blogrenderer

import (
	"embed"
	"html/template"
	"io"
)

var (
	//go:embed "templates/*"
	postTemplates embed.FS
)

func Render(w io.Writer, p Post) error {
	templ, err := template.ParseFS(postTemplates, "templates/*.gohtml")
	if err != nil {
		return err
	}

	if err := templ.Execute(w, p); err != nil {
		return err
	}

	return nil
}
```

Встраивая "файловую систему" в наш код, мы можем загружать несколько шаблонов и свободно их комбинировать. Это будет полезно, когда мы захотим совместно использовать логику рендеринга между различными шаблонами, например, заголовок для верхней части HTML-страницы и нижний колонтитул.

### Embed?

Встраивание (Embed) было немного затронуто в главе [Чтение файлов](/reading-files.md). [Документация стандартной библиотеки объясняет](https://pkg.go.dev/embed):

> Пакет embed предоставляет доступ к файлам, встроенным в запущенную Go-программу.
>
> Исходные Go-файлы, которые импортируют "embed", могут использовать директиву `//go:embed` для инициализации переменной типа `string`, `[]byte` или `FS` содержимым файлов, прочитанных из каталога пакета или подкаталогов во время компиляции.

Почему мы хотим это использовать? Ну, альтернатива состоит в том, что мы *могли бы* загружать наши шаблоны из "обычной" файловой системы. Однако это означало бы, что нам пришлось бы убедиться, что шаблоны находятся по правильному пути в файловой системе везде, где мы хотим использовать это программное обеспечение. На вашей работе у вас могут быть различные среды, такие как разработка, стейджинг и продакшен. Для этого вам нужно будет убедиться, что ваши шаблоны скопированы в правильное место.

При использовании `embed` файлы включаются в вашу Go-программу при ее сборке. Это означает, что после того, как вы собрали свою программу (что вы должны делать только один раз), файлы всегда будут доступны.

Удобно то, что вы можете встраивать не только отдельные файлы, но и файловые системы; и эта файловая система реализует [io/fs](https://pkg.go.dev/io/fs), что означает, что вашему коду не нужно заботиться о том, с какой файловой системой он работает.

Однако, если вы хотите использовать разные шаблоны в зависимости от конфигурации, вы можете придерживаться загрузки шаблонов с диска более традиционным способом.

## Далее: Сделаем шаблон "красивым"

Мы на самом деле не хотим, чтобы наш шаблон был определен как однострочная строка. Мы хотим иметь возможность разбивать его на строки, чтобы сделать его легче читаемым и удобным для работы, примерно так:

```handlebars
<h1>{{.Title}}</h1>

<p>{{.Description}}</p>

Tags: <ul>{{range .Tags}}<li>{{.}}</li>{{end}}</ul>
```

Но если мы это сделаем, наш тест завершится ошибкой. Это потому, что наш тест ожидает возврата очень специфической строки.

Но на самом деле нам не важны пробелы. Поддержание этого теста превратится в кошмар, если нам придется кропотливо обновлять строку утверждения каждый раз, когда мы вносим незначительные изменения в разметку. По мере роста шаблона такие правки становятся всё труднее управляемыми, и затраты на работу будут выходить из-под контроля.

## Введение Approval Tests

[Go Approval Tests](https://github.com/approvals/go-approval-tests)

> ApprovalTests позволяет легко тестировать большие объекты, строки и всё остальное, что может быть сохранено в файл (изображения, звуки, CSV и т. д.).

Идея схожа с "золотыми" файлами или snapshot-тестированием. Вместо неудобного поддержания строк внутри тестового файла, инструмент утверждения может сравнить вывод с "утвержденным" файлом, который вы создали. Затем вы просто копируете новую версию, если одобряете её. Повторно запустите тест, и вы снова вернетесь к "зеленому" состоянию.

Добавьте зависимость `"github.com/approvals/go-approval-tests"` (с помощью команды `go get github.com/approvals/go-approval-tests`) в ваш проект и измените тест следующим образом:

```go
func TestRender(t *testing.T) {
	var (
		aPost = blogrenderer.Post{
			Title:       "hello world",
			Body:        "This is a post",
			Description: "This is a description",
			Tags:        []string{"go", "tdd"},

	)

	t.Run("it converts a single post into HTML", func(t *testing.T) {
		buf := bytes.Buffer{}

```

При первом запуске он завершится ошибкой, потому что мы еще ничего не утвердили:

```
=== RUN   TestRender
=== RUN   TestRender/it_converts_a_single_post_into_HTML
    renderer_test.go:29: Failed Approval: received does not match approved.
```

Будут созданы два файла, которые выглядят следующим образом:

- `renderer_test.TestRender.it_converts_a_single_post_into_HTML.received.txt`
- `renderer_test.TestRender.it_converts_a_single_post_into_HTML.approved.txt`

Файл `received` содержит новую, неутвержденную версию вывода. Скопируйте его в пустой файл `approved` и запустите тест снова.

Скопировав новую версию, вы "утвердили" изменение, и тест теперь проходит.

Чтобы увидеть рабочий процесс в действии, отредактируйте шаблон, как мы обсуждали, чтобы сделать его легче читаемым (но семантически он тот же).

```handlebars
<h1>{{.Title}}</h1>

<p>{{.Description}}</p>

Tags: <ul>{{range .Tags}}<li>{{.}}</li>{{end}}</ul>
```

Запустите тест снова. Будет сгенерирован новый файл "received", потому что вывод нашего кода отличается от утвержденной версии. Просмотрите их, и если вы довольны изменениями, просто скопируйте новую версию и запустите тест снова. Обязательно закоммитьте утвержденные файлы в систему контроля версий.

Этот подход значительно упрощает управление изменениями в больших, неуклюжих вещах, таких как HTML. Вы можете использовать инструмент сравнения, чтобы просматривать и управлять различиями, и это делает ваш тестовый код чище.

![Use diff tool to manage changes](https://i.imgur.com/0MoNdva.png)

Это на самом деле довольно незначительное использование тестов утверждения, которые являются чрезвычайно полезным инструментом в вашем арсенале тестирования. [Эмили Бах](https://twitter.com/emilybache) имеет [интересное видео, где она использует тесты утверждения для добавления невероятно обширного набора тестов к сложному коду, который вообще не имел тестов](https://www.youtube.com/watch?v=zyM2Ep28ED8). "Комбинаторное тестирование" определенно стоит изучить.

Теперь, когда мы внесли это изменение, мы по-прежнему получаем выгоду от хорошо протестированного кода, но тесты не будут сильно мешать, когда мы будем вносить изменения в разметку.

### Мы все еще используем TDD?

Интересным побочным эффектом этого подхода является то, что он уводит нас от TDD. Конечно, вы *могли бы* вручную редактировать утвержденные файлы до желаемого состояния, запускать тесты, а затем исправлять шаблоны, чтобы они выдавали то, что вы определили.

Но это просто глупо! TDD — это метод работы, а именно проектирования; но это не означает, что мы должны догматически использовать его для **всего**.

Важно то, что мы поступили правильно и использовали TDD как **инструмент проектирования** для создания API нашего пакета. Для изменений в шаблонах наш процесс может быть таким:

- Внести небольшое изменение в шаблон
- Запустить тест утверждения
- Визуально проверить вывод на корректность
- Сделать утверждение
- Повторить

Мы по-прежнему не должны отказываться от ценности работы небольшими достижимыми шагами. Старайтесь находить способы сделать изменения небольшими и продолжать перезапускать тесты, чтобы получить реальную обратную связь о том, что вы делаете.

Если мы начнем менять код *вокруг* шаблонов, то, конечно, это может потребовать возврата к нашему методу работы TDD.

## Расширение разметки

Большинство веб-сайтов имеют более богатый HTML, чем у нас сейчас. Для начала, элемент `html`, а также `head`, возможно, и `nav`. Обычно также есть идея футера.

Если наш сайт будет иметь разные страницы, мы бы хотели определить эти вещи в одном месте, чтобы наш сайт выглядел единообразно. Шаблоны Go поддерживают определение секций, которые мы затем можем импортировать в другие шаблоны.

Отредактируйте наш существующий шаблон, чтобы импортировать верхний и нижний шаблоны:

```handlebars
{{template "top" .}}
<h1>{{.Title}}</h1>

<p>{{.Description}}</p>

Tags: <ul>{{range .Tags}}<li>{{.}}</li>{{end}}</ul>
{{template "bottom" .}}
```

Затем создайте `top.gohtml` со следующим содержимым:

```handlebars
{{define "top"}}
<!DOCTYPE html>
<html lang="en">
<head>
    <title>My amazing blog!</title>
    <meta charset="UTF-8"/>
    <meta name="description" content="Wow, like and subscribe, it really helps the channel guys" lang="en"/>
</head>
<body>
<nav role="navigation">
    <div>
        <h1>Budding Gopher's blog</h1>
        <ul>
            <li><a href="/">home</a></li>
            <li><a href="about">about</a></li>
            <li><a href="archive">archive</a></li>
        </ul>
    </div>
</nav>
<main>
{{end}}
```

И `bottom.gohtml`:

```handlebars
{{define "bottom"}}
</main>
<footer>
    <ul>
        <li><a href="https://twitter.com/quii">Twitter</a></li>
        <li><a href="https://github.com/quii">GitHub</a></li>
    </ul>
</footer>
</body>
</html>
{{end}}
```

(Очевидно, не стесняйтесь размещать любую разметку, которая вам нравится!)

Теперь нам нужно указать конкретный шаблон для запуска. В рендерере блога измените команду `Execute` на `ExecuteTemplate`:

```go
if err := templ.ExecuteTemplate(w, "blog.gohtml", p); err != nil {
	return err
}
```

Запустите тест снова. Должен быть создан новый файл "received", и тест завершится ошибкой. Проверьте его, и если вы довольны, утвердите, скопировав его поверх старой версии. Запустите тест снова, и он должен пройти.

## Повод поиграться с бенчмарками

Прежде чем продолжить, давайте рассмотрим, что делает наш код.

```go
func Render(w io.Writer, p Post) error {
	templ, err := template.ParseFS(postTemplates, "templates/*.gohtml")
	if err != nil {
		return err
	}

	if err := templ.ExecuteTemplate(w, "blog.gohtml", p); err != nil {
		return err
	}

	return nil
}
```

- Разбирает шаблоны
- Использует шаблон для рендеринга поста в `io.Writer`

Хотя влияние на производительность от повторного разбора шаблонов для каждого поста в большинстве случаев будет довольно незначительным, усилия, чтобы *не* делать это, также довольно незначительны и должны немного упорядочить код.

Чтобы увидеть влияние отказа от этого повторного разбора, мы можем использовать инструмент бенчмаркинга, чтобы узнать, насколько быстра наша функция.

```go
func BenchmarkRender(b *testing.B) {
	var (
		aPost = blogrenderer.Post{
			Title:       "hello world",
			Body:        "This is a post",
			Description: "This is a description",
			Tags:        []string{"go", "tdd"},
		}
	)

	for b.Loop() {
		blogrenderer.Render(io.Discard, aPost)
	}
}
```

На моем компьютере результаты таковы:

```
BenchmarkRender-8 22124 53812 ns/op
```

Чтобы нам не приходилось разбирать шаблоны снова и снова, мы создадим тип, который будет хранить разобранный шаблон, и у этого типа будет метод для выполнения рендеринга.

```go
type PostRenderer struct {
	templ *template.Template
}

func NewPostRenderer() (*PostRenderer, error) {
	templ, err := template.ParseFS(postTemplates, "templates/*.gohtml")
	if err != nil {
		return nil, err
	}

	return &PostRenderer{templ: templ}, nil
}

func (r *PostRenderer) Render(w io.Writer, p Post) error {

	if err := r.templ.ExecuteTemplate(w, "blog.gohtml", p); err != nil {
		return err
	}

	return nil
}
```

Это меняет интерфейс нашего кода, поэтому нам нужно будет обновить наш тест:

## Вернемся к реальной работе

Что касается рендеринга постов, то важная оставшаяся часть — это фактически рендеринг `Body`. Если вы помните, это должен быть markdown, написанный автором, поэтому его нужно будет преобразовать в HTML.

Мы оставим это в качестве упражнения для вас, читатель. Вы сможете найти Go-библиотеку для этого. Используйте тест утверждения, чтобы проверить, что вы делаете.

### О тестировании сторонних библиотек

**Примечание**. Будьте осторожны и не беспокойтесь слишком сильно о явном тестировании поведения сторонней библиотеки в модульных тестах.

Написание тестов для кода, который вы не контролируете, расточительно и увеличивает накладные расходы на сопровождение. Иногда вы можете захотеть использовать [внедрение зависимостей](./dependency-injection.md) для управления зависимостью и имитации ее поведения для теста.

В данном случае, однако, я рассматриваю преобразование markdown в HTML как деталь реализации рендеринга, и наши тесты утверждения должны дать нам достаточную уверенность.

### Рендеринг индекса

Следующая часть функциональности, которую мы собираемся реализовать, это рендеринг индекса, выводящего посты в виде упорядоченного HTML-списка.

Мы расширяем наш API, поэтому снова наденем шляпу TDD.

## Сначала напишите тест

На первый взгляд, страница индекса кажется простой, но написание теста все же побуждает нас сделать некоторые проектные решения:

```go
t.Run("it renders an index of posts", func(t *testing.T) {
	buf := bytes.Buffer{}
	posts := []blogrenderer.Post{{Title: "Hello World"}, {Title: "Hello World 2"}}

	if err := postRenderer.RenderIndex(&buf, posts); err != nil {
		t.Fatal(err)
	}

	got := buf.String()
	want := `<ol><li><a href="/post/hello-world">Hello World</a></li><li><a href="/post/hello-world-2">Hello World 2</a></li></ol>`

	if got != want {
		t.Errorf("got %q want %q", got, want)
	}
})
```

1.  Мы используем поле `Title` из `Post` как часть пути URL, но на самом деле мы не хотим пробелов в URL, поэтому заменяем их дефисами.
2.  Мы добавили метод `RenderIndex` в наш `PostRenderer`, который снова принимает `io.Writer` и срез `Post`.

Если бы мы придерживались подхода "тестирование после" с тестами утверждения, мы бы не отвечали на эти вопросы в контролируемой среде. **Тесты дают нам пространство для размышлений**.

## Напишите достаточно кода, чтобы он прошел

Хотя это *кажется*, что должно быть легко, это немного неудобно. Я сделал это в несколько шагов:

```go
func (r *PostRenderer) RenderIndex(w io.Writer, posts []Post) error {
	indexTemplate := `<ol>{{range .}}<li><a href="/post/{{.Title}}">{{.Title}}</a></li>{{end}}</ol>`

	templ, err := template.New("index").Parse(indexTemplate)
	if err != nil {
		return err
	}

	if err := templ.Execute(w, posts); err != nil {
		return err
	}

	return nil
}
```

Сначала я не хотел заморачиваться с отдельными файлами шаблонов, я просто хотел, чтобы это работало. Я рассматриваю предварительный разбор шаблона и разделение как рефакторинг, который я могу сделать позже.

Это не проходит, но близко.

```
=== RUN   TestRender
=== RUN   TestRender/it_renders_an_index_of_posts
    renderer_test.go:49: got "<ol><li><a href=\"/post/Hello%20World\">Hello World</a></li><li><a href=\"/post/Hello%20World%202\">Hello World 2</a></li></ol>" want "<ol><li><a href=\"/post/hello-world\">Hello World</a></li><li><a href=\"/post/hello-world-2\">Hello World 2</a></li></ol>"
--- FAIL: TestRender (0.00s)
    --- FAIL: TestRender/it_renders_an_index_of_posts (0.00s)
```

Вы можете видеть, что код шаблонизации экранирует пробелы в атрибутах `href`. Нам нужен способ замены пробелов на дефисы. Мы не можем просто пройтись по `[]Post` и заменить их в памяти, потому что мы все еще хотим, чтобы пробелы отображались пользователю в анкорах.

У нас есть несколько вариантов. Первый, который мы рассмотрим, это передача функции в наш шаблон.

### Передача функций в шаблоны

```go
func (r *PostRenderer) RenderIndex(w io.Writer, posts []Post) error {
	indexTemplate := `<ol>{{range .}}<li><a href="/post/{{sanitiseTitle .Title}}">{{.Title}}</a></li>{{end}}</ol>`

	templ, err := template.New("index").Funcs(template.FuncMap{
		"sanitiseTitle": func(title string) string {
			return strings.ToLower(strings.Replace(title, " ", "-", -1))
		},
	}).Parse(indexTemplate)
	if err != nil {
		return err
	}

	if err := templ.Execute(w, posts); err != nil {
		return err
	}

	return nil
}
```

*Перед разбором шаблона* вы можете добавить `template.FuncMap` в ваш шаблон, что позволяет определять функции, которые могут быть вызваны внутри вашего шаблона. В этом случае мы создали функцию `sanitiseTitle`, которую затем вызываем внутри нашего шаблона с помощью `{{sanitiseTitle .Title}}`.

Это мощная функция, возможность отправлять функции в ваш шаблон позволит вам делать очень крутые вещи, но, стоит ли? Возвращаясь к принципам Mustache и шаблонов без логики, почему они выступали за отсутствие логики? **Что плохого в логике в шаблонах?**

Как мы показали, чтобы протестировать наши шаблоны, *нам пришлось ввести совершенно другой вид тестирования*.

Представьте, что вы вводите функцию в шаблон, которая имеет несколько различных пермутаций поведения и граничных случаев, **как вы будете ее тестировать**? С текущим дизайном ваш единственный способ тестирования этой логики — это *рендеринг HTML и сравнение строк*. Это не простой или разумный способ тестирования логики, и определенно не то, что вы хотели бы для *важной* бизнес-логики.

Хотя метод тестов утверждения снизил затраты на поддержку этих тестов, они все равно дороже в обслуживании, чем большинство модульных тестов, которые вы будете писать. Они по-прежнему чувствительны к любым незначительным изменениям разметки, которые вы можете внести, просто мы упростили управление ими. Мы все равно должны стремиться архитектурно строить наш код так, чтобы нам не приходилось писать много тестов вокруг наших шаблонов, и стараться разделять обязанности, чтобы любая логика, которой не нужно находиться внутри нашего кода рендеринга, была должным образом отделена.

То, что дают вам движки шаблонов, вдохновленные Mustache, — это полезное ограничение, не пытайтесь слишком часто его обходить; **не идите против течения**. Вместо этого примите идею [моделей представления (view models)](https://stackoverflow.com/a/11074506/3193), где вы конструируете специфические типы, содержащие данные, необходимые для рендеринга, таким образом, который удобен для языка шаблонов.

Таким образом, любая важная бизнес-логика, которую вы используете для генерации этого набора данных, может быть протестирована модульно отдельно, вдали от сложного мира HTML и шаблонизации.

### Разделение ответственности

Итак, что мы могли бы сделать вместо этого?

#### Добавить метод к `Post`, а затем вызвать его в шаблоне

Мы можем вызывать методы в нашем коде шаблонизации на типах, которые мы отправляем, поэтому мы могли бы добавить метод `SanitisedTitle` к `Post`. Это упростило бы шаблон, и мы могли бы легко модульно тестировать эту логику отдельно, если захотим. Это, вероятно, самое простое решение, хотя и не обязательно самое прямолинейное.

Недостаток этого подхода заключается в том, что это все еще _логика представления_. Она не интересна остальной части системы, но теперь она становится частью API для основного доменного объекта. Такой подход со временем может привести к созданию [объектов-богов (God Objects)](https://en.wikipedia.org/wiki/God_object).

#### Создать выделенный тип модели представления, такой как `PostViewModel`, с точно необходимыми данными

Вместо того чтобы наш код рендеринга был связан с доменным объектом `Post`, он принимает модель представления.

```go
type PostViewModel struct {
	Title, SanitisedTitle, Description, Body string
	Tags                                     []string
}
```

Вызывающие наш код должны будут сопоставлять `[]Post` с `[]PostView`, генерируя `SanitizedTitle`. Способ сохранить это в чистоте — это иметь `func NewPostView(p Post) PostView`, который будет инкапсулировать сопоставление.

Это сделало бы наш код рендеринга безлогичным и, вероятно, является самым строгим разделением ответственности, которое мы могли бы сделать, но компромисс заключается в немного более сложном процессе рендеринга наших постов.

Оба варианта хороши, в данном случае я склонен выбрать первый. По мере развития системы вы должны остерегаться добавления всё большего количества специальных методов только для того, чтобы облегчить процесс рендеринга; выделенные модели представления становятся более полезными, когда преобразование между доменным объектом и представлением становится более сложным.

Итак, мы можем добавить наш метод к `Post`:

```go
func (p Post) SanitisedTitle() string {
	return strings.ToLower(strings.Replace(p.Title, " ", "-", -1))
}
```

И затем мы можем вернуться к более простому миру в нашем коде рендеринга:

```go
func (r *PostRenderer) RenderIndex(w io.Writer, posts []Post) error {
	indexTemplate := `<ol>{{range .}}<li><a href="/post/{{.SanitisedTitle}}">{{.Title}}</a></li>{{end}}</ol>`

	templ, err := template.New("index").Parse(indexTemplate)
	if err != nil {
		return err
	}

	if err := templ.Execute(w, posts); err != nil {
		return err
	}

	return nil
}
```

## Рефакторинг

Наконец, тест должен пройти. Теперь мы можем переместить наш шаблон в файл (`templates/index.gohtml`) и загружать его один раз, при создании нашего рендерера.

```go
package blogrenderer

import (
	"embed"
	"html/template"
	"io"
)

var (
	//go:embed "templates/*"
	postTemplates embed.FS
)

type PostRenderer struct {
	templ *template.Template
}

func NewPostRenderer() (*PostRenderer, error) {
	templ, err := template.ParseFS(postTemplates, "templates/*.gohtml")
	if err != nil {
		return nil, err
	}

	return &PostRenderer{templ: templ}, nil
}

func (r *PostRenderer) Render(w io.Writer, p Post) error {
	return r.templ.ExecuteTemplate(w, "blog.gohtml", p)
}

func (r *PostRenderer) RenderIndex(w io.Writer, posts []Post) error {
	return r.templ.ExecuteTemplate(w, "index.gohtml", posts)
}
```

Разобрав более одного шаблона в `templ`, мы теперь должны вызывать `ExecuteTemplate` и указывать, *какой* шаблон мы хотим отобразить, как это уместно, но, надеюсь, вы согласитесь, что код, к которому мы пришли, выглядит отлично.

Существует *небольшой* риск, если кто-то переименует один из файлов шаблона, это приведет к ошибке, но наши быстро запускающиеся модульные тесты быстро поймают это.

Теперь, когда мы довольны дизайном API нашего пакета и реализовали некоторое базовое поведение с помощью TDD, давайте изменим наш тест на использование утверждений.

```go
	t.Run("it renders an index of posts", func(t *testing.T) {
		buf := bytes.Buffer{}
		posts := []blogrenderer.Post{{Title: "Hello World"}, {Title: "Hello World 2"}}

		if err := postRenderer.RenderIndex(&buf, posts); err != nil {
			t.Fatal(err)
		}

		approvals.VerifyString(t, buf.String())
	})
```

Не забудьте запустить тест, чтобы увидеть, как он завершается ошибкой, а затем утвердить изменение.

Наконец, мы можем добавить нашу базовую разметку на страницу индекса:

```handlebars
{{template "top" .}}
<ol>{{range .}}<li><a href="/post/{{.SanitisedTitle}}">{{.Title}}</a></li>{{end}}</ol>
{{template "bottom" .}}
```

Перезапустите тест, утвердите изменение, и мы закончили с индексом!

## Рендеринг тела markdown

Я предложил вам попробовать сделать это самостоятельно, вот подход, к которому я в итоге пришел.

```go
package blogrenderer

import (
	"embed"
	"github.com/gomarkdown/markdown"
	"github.com/gomarkdown/markdown/parser"
	"html/template"
	"io"
)

var (
	//go:embed "templates/*"
	postTemplates embed.FS
)

type PostRenderer struct {
	templ *template.Template
}

func NewPostRenderer() (*PostRenderer, error) {
	templ, err := template.ParseFS(postTemplates, "templates/*.gohtml")
	if err != nil {
		return nil, err
	}

	return &PostRenderer{templ: templ}, nil
}

func (r *PostRenderer) Render(w io.Writer, p Post) error {
	return r.templ.ExecuteTemplate(w, "blog.gohtml", newPostVM(p))
}

func (r *PostRenderer) RenderIndex(w io.Writer, posts []Post) error {
	return r.templ.ExecuteTemplate(w, "index.gohtml", posts)
}

type postViewModel struct {
	Post
	HTMLBody template.HTML
}

func newPostVM(p Post) postViewModel {
	vm := postViewModel{Post: p}
	extensions := parser.CommonExtensions | parser.AutoHeadingIDs
	mdParser := parser.NewWithExtensions(extensions)
	vm.HTMLBody = template.HTML(markdown.ToHTML([]byte(p.Body), mdParser, nil))
	return vm
}
```

Я использовал отличную библиотеку [gomarkdown](https://github.com/gomarkdown/markdown), которая работала именно так, как я и ожидал.

Обратите внимание, что мы создаем новый `parser.Parser` при каждом вызове `newPostVM`, вместо того чтобы создавать его один раз и хранить в `PostRenderer`. Обычно, если вы можете создать что-то один раз и использовать повторно, это стоит сделать — это экономит повторные затраты на создание. Но этот общий инстинкт здесь не работает: парсер `gomarkdown` сохраняет внутреннее состояние, пока строит дерево документа, и небезопасен для повторного использования в нескольких вызовах `Parse` — вы получите панику (или, в старых версиях, гораздо менее полезное разыменование нулевого указателя) при втором использовании одного и того же парсера. Поскольку `PostRenderer` предназначен для `Render` многих постов в течение своего жизненного цикла, свежий парсер на каждый вызов является правильным способом его использования — и это дешево в любом случае, так как его создание тривиально по сравнению с самой работой по парсингу.

Если вы пытались сделать это сами, возможно, вы обнаружили, что ваш рендерер тела имел экранированный HTML. Это функция безопасности пакета Go `html/template`, предотвращающая вывод вредоносного стороннего HTML.

Чтобы обойти это, в типе, который вы отправляете для рендеринга, вам нужно обернуть ваш доверенный HTML в [template.HTML](https://pkg.go.dev/html/template#HTML).

> `HTML` инкапсулирует известный безопасный фрагмент HTML-документа. Его не следует использовать для HTML от третьих сторон или для HTML с незакрытыми тегами или комментариями. Результаты хорошего санитайзера HTML и шаблона, экранированного этим пакетом, подходят для использования с `HTML`.
>
> Использование этого типа представляет риск безопасности: инкапсулированное содержимое должно поступать из доверенного источника, поскольку оно будет включено в вывод шаблона дословно.

Поэтому я создал **неэкспортированную** модель представления (`postViewModel`), потому что я все еще рассматривал это как внутреннюю деталь реализации рендеринга. Мне нет необходимости тестировать это отдельно, и я не хочу, чтобы это загрязняло мой API.

Я создаю его при рендеринге, чтобы я мог парсить `Body` в `HTMLBody`, а затем использую это поле в шаблоне для рендеринга HTML.

## Заключение

Если вы объедините свои знания из главы [Чтение файлов](reading-files.md) и этой, вы сможете уверенно создать хорошо протестированный, простой статический генератор сайтов и запустить собственный блог. Найдите несколько руководств по CSS, и вы сможете сделать его красивым.

Этот подход выходит за рамки блогов. Получение данных из любого источника, будь то база данных, API или файловая система, и преобразование их в HTML с последующим возвратом с сервера — это простая техника, используемая на протяжении многих десятилетий. Люди любят сетовать на сложность современной веб-разработки, но уверены ли вы, что не навлекаете эту сложность на себя сами?

Go прекрасно подходит для веб-разработки, особенно если вы четко представляете свои реальные требования к создаваемому веб-сайту. Генерация HTML на сервере часто является лучшим, более простым и производительным подходом, чем создание "веб-приложения" с такими технологиями, как React.

### Что мы узнали

- Как создавать и рендерить HTML-шаблоны.
- Как компоновать шаблоны вместе и применять принцип [DRY](https://en.wikipedia.org/wiki/Don't_repeat_yourself) к связанной разметке, помогая нам поддерживать единообразный внешний вид.
- Как передавать функции в шаблоны и почему стоит дважды подумать об этом.
- Как писать "тесты утверждения" (Approval Tests), которые помогают тестировать большой, неуклюжий вывод таких элементов, как рендереры шаблонов.

### О шаблонах без логики

Как всегда, здесь все дело в **разделении ответственности**. Важно учитывать, каковы обязанности различных частей нашей системы. Слишком часто люди допускают утечку важной бизнес-логики в шаблоны, смешивая обязанности и делая системы трудными для понимания, поддержки и тестирования.

### Не только для HTML

Помните, что в Go есть `text/template` для генерации других видов данных из шаблона. Если вы обнаружите, что вам нужно преобразовать данные в какой-либо структурированный вывод, методы, изложенные в этой главе, могут быть полезны.
