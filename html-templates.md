# HTML-шаблоны

**[Весь код можно найти здесь](https://github.com/quii/learn-go-with-tests/tree/main/blogrenderer)**

Мы живем в мире, где все хотят создавать веб-приложения с использованием новейшего на данный момент фронтенд-фреймворка, построенного на гигабайтах транспилированного JavaScript, работающего со сложной системой сборки; [но, возможно, это не всегда необходимо](https://quii.dev/The_Web_I_Want).

Я бы сказал, что большинство Go-разработчиков ценят простой, стабильный и быстрый набор инструментов, но фронтенд-мир часто не справляется с этой задачей.

Многим веб-сайтам не нужно быть [SPA](https://en.wikipedia.org/wiki/Single-page_application). **HTML и CSS — это фантастические способы доставки контента**, и вы можете использовать Go для создания веб-сайта, который будет доставлять HTML.

Если вы все еще хотите иметь некоторые динамические элементы, вы можете добавить немного клиентского JavaScript, или даже попробовать экспериментировать с [Hotwire](https://hotwired.dev), который позволяет обеспечить динамический опыт с серверным подходом.

Вы можете генерировать HTML в Go с помощью сложного использования [`fmt.Fprintf`](https://pkg.go.dev/fmt#Fprintf), но в этой главе вы узнаете, что стандартная библиотека Go предлагает инструменты для генерации HTML более простым и поддерживаемым способом. Вы также узнаете о более эффективных способах тестирования такого рода кода, с которыми, возможно, раньше не сталкивались.

## Что мы будем строить

В главе [Чтение файлов](/reading-files.md) мы написали код, который принимал [`fs.FS`](https://pkg.go.dev/io/fs) (файловую систему) и возвращал срез `Post` для каждого найденного markdown-файла.

```go
posts, err := blogposts.NewPostsFromFS(os.DirFS("posts"))
```

Вот как мы определили `Post`:

```go
type Post struct {
	Title, Description, Body string
	Tags                     []string
}
```

Вот пример одного из markdown-файлов, который может быть разобран.

```markdown
Title: Welcome to my blog
Description: Introduction to my blog
Tags: cooking, family, live-laugh-love
---
# First recipe!
Welcome to my **amazing recipe blog**. I am going to write about my family recipes, and make sure I write a long, irrelevant and boring story about my family before you get to the actual instructions.
```

Если мы продолжим наш путь создания программного обеспечения для блога, мы возьмем эти данные и сгенерируем из них HTML, который наш веб-сервер будет возвращать в ответ на HTTP-запросы.

Для нашего блога мы хотим генерировать два типа страниц:

1.  **Просмотр поста**. Отображает конкретный пост. Поле `Body` в `Post` представляет собой строку, содержащую markdown, поэтому оно должно быть преобразовано в HTML.
2.  **Индекс**. Перечисляет все посты с гиперссылками для просмотра конкретного поста.

Мы также хотим, чтобы наш сайт имел единый внешний вид, поэтому для каждой страницы у нас будет обычное HTML-оформление, такое как `<html>` и `<head>`, содержащий ссылки на таблицы стилей CSS и все, что нам может понадобиться.

При создании программного обеспечения для блога у вас есть несколько вариантов подхода к построению и отправке HTML в браузер пользователя.

Мы спроектируем наш код так, чтобы он принимал `io.Writer`. Это означает, что вызывающий наш код имеет гибкость:

-   Записывать их в [os.File](https://pkg.go.dev/os#File), чтобы их можно было статически обслуживать.
-   Записывать HTML напрямую в [`http.ResponseWriter`](https://pkg.go.dev/net/http#ResponseWriter).
-   Или просто записывать их куда угодно! Пока оно реализует `io.Writer`, пользователь может генерировать HTML из `Post`.

## Сначала напишем тест

Как всегда, важно обдумать требования, прежде чем слишком быстро погружаться в код. Как мы можем взять этот довольно большой набор требований и разбить его на маленький, достижимый шаг, на котором мы можем сосредоточиться?

На мой взгляд, фактический просмотр контента имеет более высокий приоритет, чем страница индекса. Мы могли бы запустить этот продукт и делиться прямыми ссылками на наш замечательный контент. Страница индекса, которая не может ссылаться на фактический контент, бесполезна.

Тем не менее, рендеринг поста, как описано выше, все еще кажется большим. Все HTML-оформление, преобразование markdown тела в HTML, перечисление тегов и т.д.

На этом этапе меня не слишком беспокоит конкретная разметка, и легким первым шагом было бы просто проверить, можем ли мы отобразить заголовок поста как `<h1>`. Это *кажется* самым маленьким первым шагом, который может продвинуть нас вперед.

```go
package blogrenderer_test

import (
	"bytes"
	"github.com/quii/learn-go-with-tests/blogrenderer"
	"testing"
)

func TestRender(t *testing.T) {
	var (
		aPost = blogrenderer.Post{
			Title:       "hello world",
			Body:        "This is a post",
			Description: "This is a description",
			Tags:        []string{"go", "tdd"},
		}
	)

	t.Run("it converts a single post into HTML", func(t *testing.T) {
		buf := bytes.Buffer{}
		err := blogrenderer.Render(&buf, aPost)

		if err != nil {
			t.Fatal(err)
		}

		got := buf.String()
		want := `<h1>hello world</h1>`
		if got != want {
			t.Errorf("got '%s' want '%s'", got, want)
		}
	})
}
```

Наше решение принимать `io.Writer` также упрощает тестирование, в этом случае мы записываем в [`bytes.Buffer`](https://pkg.go.dev/bytes#Buffer), содержимое которого мы можем затем проверить.

## Напишем достаточно кода, чтобы тест прошел

```go

```

Помните, разработка программного обеспечения — это прежде всего процесс обучения. Чтобы обнаруживать и учиться по ходу работы, нам нужно работать так, чтобы получать частые, высококачественные циклы обратной связи, и самый простой способ сделать это — работать небольшими шагами.

Поэтому мы не беспокоимся об использовании каких-либо шаблонных библиотек прямо сейчас. Вы можете создавать HTML с помощью "обычных" строковых шаблонов, и, пропуская часть с шаблонами, мы можем проверить небольшой полезный фрагмент поведения, а также выполнить небольшую работу по проектированию API нашего пакета.

## Рефакторинг

Пока нечего особо рефакторить, поэтому перейдем к следующей итерации.

## Сначала напишем тест

Теперь, когда у нас есть очень базовая рабочая версия, мы можем итерировать тест, чтобы расширить функциональность. В этом случае — отображая больше информации из `Post`.

```go
	t.Run("it converts a single post into HTML", func(t *testing.T) {
		buf := bytes.Buffer{}
		err := blogrenderer.Render(&buf, aPost)

		if err != nil {
			t.Fatal(err)
		}

		got := buf.String()
		want := `<h1>hello world</h1>
<p>This is a description</p>
Tags: <ul><li>go</li><li>tdd</li></ul>`

		if got != want {
			t.Errorf("got '%s' want '%s'", got, want)
		}
	})
```

Обратите внимание, что писать это *неудобно*. Весь этот HTML-код в тесте выглядит плохо, а мы еще даже не вставили тело или настоящий HTML, который нам нужен, со всем содержимым `<head>` и любым другим оформлением страницы.

Тем не менее, давайте потерпим боль *пока что*.

## Попробуем запустить тест

Он должен завершиться ошибкой, жалуясь, что у него нет ожидаемой нами строки, так как мы не отображаем описание и теги.

## Напишем достаточно кода, чтобы тест прошел

Попробуйте сделать это сами, а не копировать код. Вы должны обнаружить, что прохождение этого теста _немного раздражает_! Когда я попробовал, моя первая попытка получила эту ошибку:

```
=== RUN   TestRender
=== RUN   TestRender/it_converts_a_single_post_into_HTML
    renderer_test.go:32: got '<h1>hello world</h1><p>This is a description</p><ul><li>go</li><li>tdd</li></ul>' want '<h1>hello world</h1>
        <p>This is a description</p>
        Tags: <ul><li>go</li><li></li></ul>'
```

Новые строки! Кому они нужны? Ну, нашему тесту нужны, потому что он сопоставляется с точным строковым значением. Должен ли он? Я пока удалил новые строки, чтобы тест прошел.

```go
func Render(w io.Writer, p Post) error {
	_, err := fmt.Fprintf(w, "<h1>%s</h1>\n<p>%s</p>\n", p.Title, p.Description)
	if err != nil {
		return err
	}

	_, err = fmt.Fprint(w, "Tags: <ul>")
	if err != nil {
		return err
	}

	for _, tag := range p.Tags {
		_, err = fmt.Fprintf(w, "<li>%s</li>", tag)
		if err != nil {
			return err
		}
	}

	_, err = fmt.Fprint(w, "</ul>")
	if err != nil {
		return err
	}

	return nil
}
```

**Ой**. Не самый красивый код, который я когда-либо писал, и мы все еще находимся на очень ранней стадии реализации нашей разметки. Нам понадобится гораздо больше контента и элементов на нашей странице, и мы быстро видим, что этот подход неприемлем.

Однако, что крайне важно, у нас есть проходящий тест; у нас есть рабочее программное обеспечение.

## Рефакторинг

С подстраховкой в виде проходящего теста для работающего кода мы теперь можем подумать об изменении подхода к реализации на этапе рефакторинга.

### Представляем шаблоны

В Go есть два пакета для работы с шаблонами: [text/template](https://pkg.go.dev/text/template) и [html/template), и они используют один и тот же интерфейс. Оба они позволяют комбинировать шаблон и некоторые данные для получения строки.

В чем разница с HTML-версией?

> Пакет template (html/template) реализует управляемые данными шаблоны для генерации HTML-вывода, безопасного от внедрения кода. Он предоставляет тот же интерфейс, что и пакет text/template, и должен использоваться вместо text/template всякий раз, когда вывод является HTML.

Язык шаблонов очень похож на [Mustache](https://mustache.github.io) и позволяет динамически генерировать контент очень чистым способом с хорошим разделением ответственности. По сравнению с другими языками шаблонов, которые вы, возможно, использовали, он очень ограничен или "безлогичен", как любит говорить Mustache. Это важное **и преднамеренное** проектное решение.

Хотя здесь мы сосредоточены на генерации HTML, если ваш проект выполняет сложные конкатенации строк и заклинания, вы можете обратиться к `text/template`, чтобы навести порядок в своем коде.

### Возвращаемся к коду

Вот шаблон для нашего блога:

`<h1>{{.Title}}</h1><p>{{.Description}}</p>Tags: <ul>{{range .Tags}}<li>{{.}}</li>{{end}}</ul>`

Где мы определяем эту строку? У нас есть несколько вариантов, но чтобы шаги были небольшими, давайте начнем с обычной строки:

```go
package blogrenderer

import (
	"html/template"
	"io"
)

const (
	postTemplate = `<h1>{{.Title}}</h1><p>{{.Description}}</p>Tags: <ul>{{range .Tags}}<li>{{.}}</li>{{end}}</ul>`
)

func Render(w io.Writer, p Post) error {
	templ, err := template.New("blog").Parse(postTemplate)
	if err != nil {
		return err
	}

	if err := templ.Execute(w, p); err != nil {
		return err
	}

	return nil
}
```

Мы создаем новый шаблон с именем, а затем разбираем нашу строку шаблона. Затем мы можем использовать метод `Execute` для него, передавая наши данные, в данном случае `Post`.

Шаблон заменит такие вещи, как `{{.Description}}` содержимым `p.Description`. Шаблоны также предоставляют некоторые программные примитивы, такие как `range` для перебора значений и `if`. Более подробную информацию вы можете найти в [документации text/template](https://pkg.go.dev/text/template).

*Это должен быть чистый рефакторинг.* Нам не нужно менять наши тесты, и они должны продолжать проходить. Важно отметить, что наш код стал легче читать и содержит гораздо меньше раздражающей обработки ошибок.

Часто люди жалуются на многословность обработки ошибок в Go, но вы можете обнаружить, что можно найти лучшие способы написания кода, чтобы он изначально был менее подвержен ошибкам, как здесь.

### Больше рефакторинга

Использование `html/template`, безусловно, стало улучшением, но хранить его в виде строковой константы в нашем коде не очень хорошо:

-   Его все еще довольно трудно читать.
-   Он недружелюбен к IDE/редакторам. Нет подсветки синтаксиса, возможности переформатировать, рефакторить и т.д.
-   Он выглядит как HTML, но вы не можете работать с ним, как с "обычным" HTML-файлом.

Нам бы хотелось, чтобы наши шаблоны жили в отдельных файлах, чтобы мы могли лучше их организовывать и работать с ними, как с HTML-файлами.

Создайте папку "templates" и внутри нее создайте файл `blog.gohtml`, вставьте наш шаблон в этот файл.

Теперь измените наш код, чтобы встроить файловые системы, используя [функциональность встраивания, включенную в Go 1.16](https://pkg.go.dev/embed).

```go
package blogrenderer

import (
	"embed"
	"html/template"
	"io"
)

var (
	//go:embed "templates/*"
	postTemplates embed.FS
)

func Render(w io.Writer, p Post) error {
	templ, err := template.ParseFS(postTemplates, "templates/*.gohtml")
	if err != nil {
		return err
	}

	if err := templ.Execute(w, p); err != nil {
		return err
	}

	return nil
}
```

Встраивая "файловую систему" в наш код, мы можем загружать несколько шаблонов и свободно их комбинировать. Это станет полезным, когда мы захотим совместно использовать логику рендеринга в разных шаблонах, например, заголовок для верхней части HTML-страницы и футер.

### Embed?

`Embed` был вкратце затронут в главе [Чтение файлов](reading-files.md). [Документация из стандартной библиотеки объясняет](https://pkg.go.dev/embed):

> Пакет embed предоставляет доступ к файлам, встроенным в запущенную программу Go.
>
> Исходные файлы Go, которые импортируют "embed", могут использовать директиву `//go:embed` для инициализации переменной типа `string`, `[]byte` или `FS` содержимым файлов, прочитанных из каталога пакета или подкаталогов во время компиляции.

Зачем нам это использовать? Альтернатива заключается в том, что мы *можем* загружать наши шаблоны из "обычной" файловой системы. Однако это означает, что нам придется убедиться, что шаблоны находятся в правильном пути к файлу везде, где мы хотим использовать это программное обеспечение. В вашей работе у вас может быть несколько сред, таких как разработка, промежуточная и рабочая. Для того чтобы это работало, вам нужно убедиться, что ваши шаблоны скопированы в правильное место.

С `embed` файлы включаются в вашу программу Go при ее сборке. Это означает, что после сборки вашей программы (что вы должны делать только один раз), файлы всегда будут доступны вам.

Удобно то, что вы можете встраивать не только отдельные файлы, но и файловые системы; и эта файловая система реализует [io/fs](https://pkg.go.dev/io/fs), что означает, что вашему коду не нужно заботиться о том, с какой файловой системой он работает.

Однако, если вы хотите использовать разные шаблоны в зависимости от конфигурации, вы можете придерживаться загрузки шаблонов с диска более традиционным способом.

## Далее: Сделаем шаблон "красивым"

Нам не очень хочется, чтобы наш шаблон был определен как строка в одну строку. Мы хотим иметь возможность расположить его так, чтобы его было легче читать и работать с ним, примерно так:

```handlebars
<h1>{{.Title}}</h1>

<p>{{.Description}}</p>

Tags: <ul>{{range .Tags}}<li>{{.}}</li>{{end}}</ul>
```

Но если мы сделаем это, наш тест не пройдет. Это потому, что наш тест ожидает возвращения очень конкретной строки.

Но на самом деле нам все равно на пробелы. Поддержание этого теста превратится в кошмар, если нам придется постоянно кропотливо обновлять строку утверждения каждый раз, когда мы вносим незначительные изменения в разметку. По мере роста шаблона такие изменения становятся все труднее управлять, и затраты на работу выйдут из-под контроля.

## Представляем Approval Tests

[Go Approval Tests](https://github.com/approvals/go-approval-tests)

> ApprovalTests позволяет легко тестировать более крупные объекты, строки и все остальное, что может быть сохранено в файл (изображения, звуки, CSV и т. д.).

Идея похожа на "золотые" файлы или snapshot-тестирование. Вместо неудобного поддержания строк внутри тестового файла, инструмент утверждений может сравнить вывод с "утвержденным" файлом, который вы создали. Затем вы просто копируете новую версию, если одобряете ее. Перезапускаете тест, и все снова зеленое.

Добавьте зависимость `"github.com/approvals/go-approval-tests"` (с помощью команды `go get github.com/approvals/go-approval-tests`) в ваш проект и измените тест следующим образом:

```go
func TestRender(t *testing.T) {
	var (
		aPost = blogrenderer.Post{
			Title:       "hello world",
			Body:        "This is a post",
			Description: "This is a description",
			Tags:        []string{"go", "tdd"},
		}
	)

	t.Run("it converts a single post into HTML", func(t *testing.T) {
		buf := bytes.Buffer{}

		if err := blogrenderer.Render(&buf, aPost); err != nil {
			t.Fatal(err)
		}

		approvals.VerifyString(t, buf.String())
	})
}
```

При первом запуске он завершится ошибкой, потому что мы еще ничего не утвердили:

```
=== RUN   TestRender
=== RUN   TestRender/it_converts_a_single_post_into_HTML
    renderer_test.go:29: Failed Approval: received does not match approved.
```

Он создаст два файла, которые выглядят следующим образом:

-   `renderer_test.TestRender.it_converts_a_single_post_into_HTML.received.txt`
-   `renderer_test.TestRender.it_converts_a_single_post_into_HTML.approved.txt`

Файл `received` содержит новую, неутвержденную версию вывода. Скопируйте ее в пустой файл `approved` и перезапустите тест.

Скопировав новую версию, вы "утвердили" изменение, и тест теперь проходит.

Чтобы увидеть рабочий процесс в действии, отредактируйте шаблон, как мы обсуждали, чтобы сделать его более читаемым (но семантически он тот же).

```handlebars
<h1>{{.Title}}</h1>

<p>{{.Description}}</p>

Tags: <ul>{{range .Tags}}<li>{{.}}</li>{{end}}</ul>
```

Перезапустите тест. Будет сгенерирован новый файл "received", потому что вывод нашего кода отличается от утвержденной версии. Просмотрите их, и если вы довольны изменениями, просто скопируйте новую версию и перезапустите тест. Обязательно зафиксируйте утвержденные файлы в системе контроля версий.

Этот подход значительно упрощает управление изменениями в больших и некрасивых вещах, таких как HTML. Вы можете использовать инструмент сравнения для просмотра и управления различиями, и это делает ваш тестовый код чище.

![Использование инструмента сравнения для управления изменениями](https://i.imgur.com/0MoNdva.png)

Это на самом деле довольно незначительное использование тестов утверждения, которые являются чрезвычайно полезным инструментом в вашем арсенале тестирования. У [Эмили Баче](https://twitter.com/emilybache) есть [интересное видео, где она использует тесты утверждения для добавления невероятно обширного набора тестов к сложному коду, который вообще не имел тестов](https://www.youtube.com/watch?v=zyM2Ep28ED8). "Комбинаторное тестирование" — это определенно то, на что стоит обратить внимание.

Теперь, когда мы внесли это изменение, мы по-прежнему получаем выгоду от хорошо протестированного кода, но тесты не будут слишком мешать, когда мы будем вносить изменения в разметку.

### Мы все еще используем TDD?

Интересным побочным эффектом такого подхода является то, что он отводит нас от TDD. Конечно, вы *могли бы* вручную редактировать утвержденные файлы до желаемого состояния, запускать тесты, а затем исправлять шаблоны так, чтобы они выводили то, что вы определили.

Но это просто глупо! TDD — это метод работы, а именно проектирования; но это не означает, что мы должны догматически использовать его для **всего**.

Важно то, что мы поступили правильно и использовали TDD в качестве **инструмента проектирования** для разработки API нашего пакета. Для изменений в шаблонах наш процесс может быть следующим:

-   Внести небольшое изменение в шаблон.
-   Запустить тест утверждения.
-   Просмотреть вывод, чтобы убедиться, что он выглядит правильно.
-   Выполнить утверждение.
-   Повторить.

Мы по-прежнему не должны отказываться от ценности работы небольшими достижимыми шагами. Постарайтесь найти способы сделать изменения небольшими и продолжать перезапускать тесты, чтобы получить реальную обратную связь о том, что вы делаете.

Если мы начнем делать что-то вроде изменения кода *вокруг* шаблонов, то, конечно, это может потребовать возвращения к нашему методу работы TDD.

## Расширим разметку

Большинство веб-сайтов имеют более богатый HTML, чем у нас сейчас. Для начала, элемент `html`, а также `head`, возможно, также `nav`. Обычно есть также идея футера.

Если на нашем сайте будут разные страницы, мы бы хотели определить эти вещи в одном месте, чтобы наш сайт выглядел единообразно. Шаблоны Go поддерживают определение разделов, которые затем мы можем импортировать в другие шаблоны.

Измените наш существующий шаблон, чтобы импортировать верхний и нижний шаблоны:

```handlebars
{{template "top" .}}
<h1>{{.Title}}</h1>

<p>{{.Description}}</p>

Tags: <ul>{{range .Tags}}<li>{{.}}</li>{{end}}</ul>
{{template "bottom" .}}
```

Затем создайте `top.gohtml` со следующим содержанием:

```handlebars
{{define "top"}}
<!DOCTYPE html>
<html lang="en">
<head>
    <title>My amazing blog!</title>
    <meta charset="UTF-8"/>
    <meta name="description" content="Wow, like and subscribe, it really helps the channel guys" lang="en"/>
</head>
<body>
<nav role="navigation">
    <div>
        <h1>Budding Gopher's blog</h1>
        <ul>
            <li><a href="/">home</a></li>
            <li><a href="about">about</a></li>
            <li><a href="archive">archive</a></li>
        </ul>
    </div>
</nav>
<main>
{{end}}
```

И `bottom.gohtml`:

```handlebars
{{define "bottom"}}
</main>
<footer>
    <ul>
        <li><a href="https://twitter.com/quii">Twitter</a></li>
        <li><a href="https://github.com/quii">GitHub</a></li>
    </ul>
</footer>
</body>
</html>
{{end}}
```

(Очевидно, не стесняйтесь вставлять любую разметку, которая вам нравится!)

Теперь нам нужно указать конкретный шаблон для запуска. В `blogrenderer` измените команду `Execute` на `ExecuteTemplate`:

```go
if err := templ.ExecuteTemplate(w, "blog.gohtml", p); err != nil {
	return err
}
```

Перезапустите ваш тест. Должен быть создан новый файл "received", и тест завершится ошибкой. Проверьте его, и если вы довольны, утвердите его, скопировав поверх старой версии. Перезапустите тест еще раз, и он должен пройти.

## Повод поиграть с бенчмарками

Прежде чем продолжить, давайте рассмотрим, что делает наш код.

```go
func Render(w io.Writer, p Post) error {
	templ, err := template.ParseFS(postTemplates, "templates/*.gohtml")
	if err != nil {
		return err
	}

	if err := templ.ExecuteTemplate(w, "blog.gohtml", p); err != nil {
		return err
	}

	return nil
}
```

-   Разбирает шаблоны.
-   Использует шаблон для рендеринга поста в `io.Writer`.

Хотя влияние на производительность повторного разбора шаблонов для каждого поста в большинстве случаев будет довольно незначительным, усилия, чтобы *не* делать этого, также довольно незначительны и должны немного упорядочить код.

Чтобы увидеть влияние отказа от повторного разбора шаблонов, мы можем использовать инструмент бенчмаркинга, чтобы узнать, насколько быстра наша функция.

```go
func BenchmarkRender(b *testing.B) {
	var (
		aPost = blogrenderer.Post{
			Title:       "hello world",
			Body:        "This is a post",
			Description: "This is a description",
			Tags:        []string{"go", "tdd"},
		}
	)

	for b.Loop() {
		blogrenderer.Render(io.Discard, aPost)
	}
}
```

На моем компьютере вот результаты:

```
BenchmarkRender-8 22124 53812 ns/op
```

Чтобы нам не приходилось перебирать шаблоны снова и снова, мы создадим тип, который будет хранить разобранный шаблон, и у которого будет метод для выполнения рендеринга.

```go
type PostRenderer struct {
	templ *template.Template
}

func NewPostRenderer() (*PostRenderer, error) {
	templ, err := template.ParseFS(postTemplates, "templates/*.gohtml")
	if err != nil {
		return nil, err
	}

	return &PostRenderer{templ: templ}, nil
}

func (r *PostRenderer) Render(w io.Writer, p Post) error {

	if err := r.templ.ExecuteTemplate(w, "blog.gohtml", p); err != nil {
		return err
	}

	return nil
}
```

Это меняет интерфейс нашего кода, поэтому нам нужно обновить наш тест:

```go

	}

}
```

И наш бенчмарк:

## Возвращаемся к реальной работе

Что касается рендеринга постов, то важная оставшаяся часть — это фактический рендеринг `Body`. Если вы помните, это должен быть markdown, написанный автором, поэтому его нужно будет преобразовать в HTML.

Мы оставим это в качестве упражнения для вас, читателя. Вы сможете найти Go-библиотеку, которая сделает это за вас. Используйте тест утверждения, чтобы проверить то, что вы делаете.

### О тестировании сторонних библиотек

**Примечание**. Будьте осторожны, чтобы не слишком беспокоиться о явном тестировании поведения сторонней библиотеки в модульных тестах.

Написание тестов для кода, который вы не контролируете, расточительно и увеличивает накладные расходы на обслуживание. Иногда вы можете захотеть использовать [внедрение зависимостей](./dependency-injection.md), чтобы контролировать зависимость и имитировать ее поведение для теста.

В этом случае, однако, я рассматриваю преобразование markdown в HTML как деталь реализации рендеринга, и наши тесты утверждения должны дать нам достаточную уверенность.

### Рендеринг индекса

Следующая часть функциональности, которую мы собираемся реализовать, — это рендеринг индекса, отображающего посты в виде упорядоченного HTML-списка.

Мы расширяем наш API, поэтому снова наденем шляпу TDD.

## Сначала напишем тест

На первый взгляд, страница индекса кажется простой, но написание теста все же побуждает нас сделать некоторые проектные выборы:

```go
t.Run("it renders an index of posts", func(t *testing.T) {
	buf := bytes.Buffer{}
	posts := []blogrenderer.Post{{Title: "Hello World"}, {Title: "Hello World 2"}}

	if err := postRenderer.RenderIndex(&buf, posts); err != nil {
		t.Fatal(err)
	}

	got := buf.String()
	want := `<ol><li><a href="/post/hello-world">Hello World</a></li><li><a href="/post/hello-world-2">Hello World 2</a></li></ol>`

	if got != want {
		t.Errorf("got %q want %q", got, want)
	}
})
```

1.  Мы используем поле `title` `Post` как часть пути URL, но на самом деле нам не нужны пробелы в URL, поэтому мы заменяем их дефисами.
2.  Мы добавили метод `RenderIndex` в наш `PostRenderer`, который снова принимает `io.Writer` и срез `Post`.

Если бы мы придерживались подхода "тестирование после, с тестами утверждения", мы бы не отвечали на эти вопросы в контролируемой среде. **Тесты дают нам пространство для размышлений**.

## Напишем достаточно кода, чтобы тест прошел

Хотя это *кажется*, что должно быть легко, это немного неудобно. Я сделал это в несколько шагов:

```go
func (r *PostRenderer) RenderIndex(w io.Writer, posts []Post) error {
	indexTemplate := `<ol>{{range .}}<li><a href="/post/{{.Title}}">{{.Title}}</a></li>{{end}}</ol>`

	templ, err := template.New("index").Parse(indexTemplate)
	if err != nil {
		return err
	}

	if err := templ.Execute(w, posts); err != nil {
		return err
	}

	return nil
}
```

Сначала я не хотел заморачиваться с отдельными файлами шаблонов, я просто хотел, чтобы это заработало. Я рассматриваю предварительный разбор шаблонов и их разделение как рефакторинг, который могу сделать позже.

Это не проходит, но близко:

```
=== RUN   TestRender
=== RUN   TestRender/it_renders_an_index_of_posts
    renderer_test.go:49: got "<ol><li><a href=\"/post/Hello%20World\">Hello World</a></li><li><a href=\"/post/Hello%20World%202\">Hello World 2</a></li></ol>" want "<ol><li><a href=\"/post/hello-world\">Hello World</a></li><li><a href=\"/post/hello-world-2\">Hello World 2</a></li></ol>"
--- FAIL: TestRender (0.00s)
    --- FAIL: TestRender/it_renders_an_index_of_posts (0.00s)
```

Вы можете видеть, что код шаблонизации экранирует пробелы в атрибутах `href`. Нам нужен способ замены пробелов дефисами. Мы не можем просто перебирать `[]Post` и заменять их в памяти, потому что мы все еще хотим, чтобы пробелы отображались пользователю в анкорах.

У нас есть несколько вариантов. Первый, который мы рассмотрим, — передача функции в наш шаблон.

### Передача функций в шаблоны

```go
func (r *PostRenderer) RenderIndex(w io.Writer, posts []Post) error {
	indexTemplate := `<ol>{{range .}}<li><a href="/post/{{sanitiseTitle .Title}}">{{.Title}}</a></li>{{end}}</ol>`

	templ, err := template.New("index").Funcs(template.FuncMap{
		"sanitiseTitle": func(title string) string {
			return strings.ToLower(strings.Replace(title, " ", "-", -1))
		},
	}).Parse(indexTemplate)
	if err != nil {
		return err
	}

	if err := templ.Execute(w, posts); err != nil {
		return err
	}

	return nil
}
```

*Перед разбором шаблона* вы можете добавить `template.FuncMap` в ваш шаблон, что позволит вам определять функции, которые могут быть вызваны внутри вашего шаблона. В этом случае мы создали функцию `sanitiseTitle`, которую затем вызываем внутри нашего шаблона с помощью `{{sanitiseTitle .Title}}`.

Это мощная функция, возможность отправлять функции в шаблон позволит вам делать очень крутые вещи, но стоит ли? Возвращаясь к принципам Mustache и безлогичных шаблонов, почему они выступали за безлогичность? **Что не так с логикой в шаблонах?**

Как мы показали, чтобы протестировать наши шаблоны, *нам пришлось ввести совершенно другой тип тестирования*.

Представьте, что вы вводите функцию в шаблон, которая имеет несколько различных пермутаций поведения и граничных случаев, **как вы будете ее тестировать**? С текущим дизайном ваш единственный способ тестирования этой логики — это _рендеринг HTML и сравнение строк_. Это не простой или разумный способ тестирования логики, и определенно не то, что вам нужно для _важной_ бизнес-логики.

Даже если метод тестов утверждения снизил стоимость поддержки этих тестов, они все равно дороже в обслуживании, чем большинство модульных тестов, которые вы напишете. Они по-прежнему чувствительны к любым незначительным изменениям разметки, которые вы можете внести, просто мы упростили управление. Мы все равно должны стремиться к архитектуре нашего кода таким образом, чтобы нам не приходилось писать много тестов вокруг наших шаблонов, и стараться разделять ответственности, чтобы любая логика, которой не нужно находиться внутри нашего кода рендеринга, была должным образом разделена.

Что предлагают шаблонизаторы, вдохновленные Mustache, так это полезное ограничение: не пытайтесь обходить его слишком часто; **не идите против течения**. Вместо этого примите идею [моделей представления](https://stackoverflow.com/a/11074506/3193), где вы конструируете конкретные типы, содержащие данные, которые вам нужны для рендеринга, способом, удобным для языка шаблонов.

Таким образом, любая важная бизнес-логика, которую вы используете для генерации этого набора данных, может быть отдельно протестирована модульными тестами, вдали от сложного мира HTML и шаблонизации.

### Разделение ответственности

Так что же мы могли бы сделать вместо этого?

#### Добавить метод в `Post` и затем вызвать его в шаблоне

Мы можем вызывать методы в нашем коде шаблонизации для типов, которые мы отправляем, поэтому мы могли бы добавить метод `SanitisedTitle` в `Post`. Это упростило бы шаблон, и мы могли бы легко протестировать эту логику отдельно, если захотим. Это, вероятно, самое простое решение, хотя и не обязательно самое простое.

Недостаток этого подхода заключается в том, что это все еще логика *представления*. Она не интересна остальной системе, но теперь становится частью API для основного доменного объекта. Такой подход со временем может привести к созданию [объектов-богов](https://en.wikipedia.org/wiki/God_object).

#### Создать выделенный тип модели представления, например `PostViewModel`, с точно теми данными, которые нам нужны

Вместо того чтобы наш код рендеринга был связан с доменным объектом `Post`, он вместо этого принимает модель представления.

```go
type PostViewModel struct {
	Title, SanitisedTitle, Description, Body string
	Tags                     []string
}
```

Вызывающие наш код должны были бы сопоставить `[]Post` с `[]PostView`, генерируя `SanitizedTitle`. Способ поддерживать это в чистоте состоял бы в том, чтобы иметь `func NewPostView(p Post) PostView`, который бы инкапсулировал сопоставление.

Это сделало бы наш код рендеринга безлогичным и, вероятно, является самым строгим разделением ответственности, которое мы могли бы сделать, но компромисс заключается в немного более сложным процессе получения наших постов.

Оба варианта хороши, в данном случае я склонен выбрать первый. По мере развития системы следует остерегаться добавления все больше и больше специальных методов просто для смазки колес рендеринга; выделенные модели представления становятся более полезными, когда преобразование между доменным объектом и представлением становится более сложным.

Итак, мы можем добавить наш метод в `Post`:

```go
func (p Post) SanitisedTitle() string {
	return strings.ToLower(strings.Replace(p.Title, " ", "-", -1))
}
```

И затем мы можем вернуться к более простому миру в нашем коде рендеринга:

```go
func (r *PostRenderer) RenderIndex(w io.Writer, posts []Post) error {
	indexTemplate := `<ol>{{range .}}<li><a href="/post/{{.SanitisedTitle}}">{{.Title}}</a></li>{{end}}</ol>`

	templ, err := template.New("index").Parse(indexTemplate)
	if err != nil {
		return err
	}

	if err := templ.Execute(w, posts); err != nil {
		return err
	}

	return nil
}
```

## Рефакторинг

Наконец, тест должен проходить. Теперь мы можем переместить наш шаблон в файл (`templates/index.gohtml`) и загрузить его один раз, при конструировании нашего рендерера.

```go
package blogrenderer

import (
	"embed"
	"html/template"
	"io"
)

var (
	//go:embed "templates/*"
	postTemplates embed.FS
)

type PostRenderer struct {
	templ *template.Template
}

func NewPostRenderer() (*PostRenderer, error) {
	templ, err := template.ParseFS(postTemplates, "templates/*.gohtml")
	if err != nil {
		return nil, err
	}

	return &PostRenderer{templ: templ}, nil
}

func (r *PostRenderer) Render(w io.Writer, p Post) error {
	return r.templ.ExecuteTemplate(w, "blog.gohtml", p)
}

func (r *PostRenderer) RenderIndex(w io.Writer, posts []Post) error {
	return r.templ.ExecuteTemplate(w, "index.gohtml", posts)
}
```

Разобрав более одного шаблона в `templ`, мы теперь должны вызывать `ExecuteTemplate` и указывать, *какой* шаблон мы хотим отобразить, но, надеюсь, вы согласитесь, что полученный код выглядит отлично.

Существует *небольшой* риск, если кто-то переименует один из файлов шаблонов, это приведет к ошибке, но наши быстро выполняющиеся модульные тесты быстро поймают это.

Теперь, когда мы довольны дизайном API нашего пакета и реализовали базовое поведение с помощью TDD, давайте изменим наш тест, чтобы использовать утверждения.

```go
	t.Run("it renders an index of posts", func(t *testing.T) {
		buf := bytes.Buffer{}
		posts := []blogrenderer.Post{{Title: "Hello World"}, {Title: "Hello World 2"}}

		if err := postRenderer.RenderIndex(&buf, posts); err != nil {
			t.Fatal(err)
		}

		approvals.VerifyString(t, buf.String())
	})
```

Не забудьте запустить тест, чтобы увидеть, что он не проходит, а затем утвердите изменение.

Наконец, мы можем добавить оформление страницы к нашей индексной странице:

```handlebars
{{template "top" .}}
<ol>{{range .}}<li><a href="/post/{{.SanitisedTitle}}">{{.Title}}</a></li>{{end}}</ol>
{{template "bottom" .}}
```

Перезапустите тест, утвердите изменение, и мы закончили с индексом!

## Рендеринг markdown-тела

Я предложил вам попробовать это самостоятельно, вот подход, который я в итоге использовал.

```go
package blogrenderer

import (
	"embed"
	"github.com/gomarkdown/markdown"
	"github.com/gomarkdown/markdown/parser"
	"html/template"
	"io"
)

var (
	//go:embed "templates/*"
	postTemplates embed.FS
)

type PostRenderer struct {
	templ *template.Template
}

func NewPostRenderer() (*PostRenderer, error) {
	templ, err := template.ParseFS(postTemplates, "templates/*.gohtml")
	if err != nil {
		return nil, err
	}

	return &PostRenderer{templ: templ}, nil
}

func (r *PostRenderer) Render(w io.Writer, p Post) error {
	return r.templ.ExecuteTemplate(w, "blog.gohtml", newPostVM(p))
}

func (r *PostRenderer) RenderIndex(w io.Writer, posts []Post) error {
	return r.templ.ExecuteTemplate(w, "index.gohtml", posts)
}

type postViewModel struct {
	Post
	HTMLBody template.HTML
}

func newPostVM(p Post) postViewModel {
	vm := postViewModel{Post: p}
	extensions := parser.CommonExtensions | parser.AutoHeadingIDs
	mdParser := parser.NewWithExtensions(extensions)
	vm.HTMLBody = template.HTML(markdown.ToHTML([]byte(p.Body), mdParser, nil))
	return vm
}
```

Я использовал отличную библиотеку [gomarkdown](https://github.com/gomarkdown/markdown), которая работала именно так, как я и ожидал.

Обратите внимание, что мы создаем новый `parser.Parser` при каждом вызове `newPostVM`, а не конструируем его один раз и сохраняем в `PostRenderer`. Обычно, если вы можете что-то сконструировать один раз и повторно использовать, это стоит того — это экономит повторные затраты на конструирование. Но этот общий инстинкт здесь не срабатывает: парсер gomarkdown сохраняет внутреннее состояние, пока строит дерево документа, и не безопасно повторно использовать его в нескольких вызовах `Parse` — вы получите panic (или, в старых версиях, гораздо менее полезный nil pointer dereference) при втором использовании одного и того же парсера. Поскольку `PostRenderer` предназначен для `Render` многих постов в течение своего жизненного цикла, свежий парсер на каждый вызов является правильным способом его использования — и это дешево в любом случае, так как его создание тривиально по сравнению с самой работой по парсингу.

Если вы пытались сделать это сами, вы могли обнаружить, что при рендеринге тела HTML был экранирован. Это функция безопасности пакета html/template Go для предотвращения вывода вредоносного стороннего HTML.

Чтобы обойти это, в типе, который вы отправляете для рендеринга, вам нужно обернуть ваш доверенный HTML в [template.HTML](https://pkg.go.dev/html/template#HTML):

> `HTML` инкапсулирует известный безопасный фрагмент HTML-документа. Его не следует использовать для HTML от третьих сторон или HTML с незакрытыми тегами или комментариями. Выходные данные исправного HTML-санитайзера и шаблона, экранированного этим пакетом, подходят для использования с `HTML`.
>
> Использование этого типа представляет риск безопасности: инкапсулированный контент должен поступать из доверенного источника, так как он будет включен в вывод шаблона без изменений.

Поэтому я создал **неэкспортированную** модель представления (`postViewModel`), потому что я все еще рассматривал это как внутреннюю деталь реализации для рендеринга. У меня нет необходимости тестировать это отдельно, и я не хочу, чтобы это загрязняло мой API.

Я конструирую его при рендеринге, чтобы я мог разобрать `Body` в `HTMLBody`, а затем использую это поле в шаблоне для рендеринга HTML.

## Завершение

Если вы объедините свои знания из главы [Чтение файлов](reading-files.md) и этой главы, вы сможете легко создать хорошо протестированный, простой, статический генератор сайтов и запустить свой собственный блог. Найдите несколько уроков по CSS, и вы сможете сделать его красивым.

Этот подход выходит за рамки блогов. Получение данных из любого источника, будь то база данных, API или файловая система, и преобразование их в HTML с последующим возвратом с сервера — это простая техника, существующая на протяжении многих десятилетий. Люди любят сетовать на сложность современной веб-разработки, но уверены ли вы, что не сами навлекаете на себя эту сложность?

Go отлично подходит для веб-разработки, особенно когда вы четко понимаете свои реальные требования к создаваемому вами веб-сайту. Генерация HTML на сервере часто является лучшим, более простым и производительным подходом, чем создание "веб-приложения" с помощью таких технологий, как React.

### Что мы узнали

-   Как создавать и рендерить HTML-шаблоны.
-   Как объединять шаблоны и [DRY](https://en.wikipedia.org/wiki/Don't_repeat_yourself) связанные разметки, помогая нам поддерживать единообразный внешний вид.
-   Как передавать функции в шаблоны и почему стоит дважды подумать об этом.
-   Как писать "Approval Tests", которые помогают нам тестировать большие, некрасивые выходные данные таких вещей, как рендереры шаблонов.

### О шаблонах без логики

Как всегда, все это связано с **разделением ответственности**. Важно учитывать, каковы обязанности различных частей нашей системы. Слишком часто люди допускают утечку важной бизнес-логики в шаблоны, смешивая обязанности и делая системы трудными для понимания, поддержки и тестирования.

### Не только для HTML

Помните, что в Go есть `text/template` для генерации других видов данных из шаблона. Если вы обнаружите, что вам нужно преобразовать данные в какой-либо структурированный вывод, методы, изложенные в этой главе, могут быть полезны.
