# HTML-шаблоны

**[Весь код вы можете найти здесь](https://github.com/quii/learn-go-with-tests/tree/main/blogrenderer)**

Мы живем в мире, где каждый хочет создавать веб-приложения с помощью новейшего фронтенд-фреймворка месяца, построенного на гигабайтах транспилированного JavaScript и работающего с византийской системой сборки; [но, возможно, это не всегда необходимо](https://quii.dev/The_Web_I_Want).

Я бы сказал, что большинство Go-разработчиков ценят простую, стабильную и быструю цепочку инструментов, но фронтенд-мир часто не справляется с этой задачей.

Многим веб-сайтам не нужно быть [SPA](https://en.wikipedia.org/wiki/Single-page_application). **HTML и CSS — фантастические способы доставки контента**, и вы можете использовать Go для создания веб-сайта, который будет доставлять HTML.

Если вы все еще хотите иметь динамические элементы, вы можете добавить немного клиентского JavaScript, или даже попробовать поэкспериментировать с [Hotwire](https://hotwired.dev), который позволяет обеспечить динамический пользовательский опыт с помощью серверного подхода.

Вы можете генерировать HTML в Go, используя [`fmt.Fprintf`](https://pkg.go.dev/fmt#Fprintf), но в этой главе вы узнаете, что стандартная библиотека Go предлагает инструменты для генерации HTML более простым и поддерживаемым способом. Вы также узнаете более эффективные способы тестирования такого кода, с которыми вы, возможно, не сталкивались ранее.

## Что мы будем строить

В главе [Чтение файлов](/reading-files.md) мы написали код, который принимал [`fs.FS`](https://pkg.go.dev/io/fs) (файловую систему) и возвращал срез `Post` для каждого найденного markdown-файла.

```go
posts, err := blogposts.NewPostsFromFS(os.DirFS("posts"))
```

Вот как мы определили `Post`

```go
type Post struct {
	Title, Description, Body string
	Tags                     []string
}
```

Вот пример одного из markdown-файлов, который может быть разобран.

```markdown
Title: Welcome to my blog
Description: Introduction to my blog
Tags: cooking, family, live-laugh-love
---
# First recipe!
Welcome to my **amazing recipe blog**. I am going to write about my family recipes, and make sure I write a long, irrelevant and boring story about my family before you get to the actual instructions.
```

Если мы продолжим наш путь по написанию программного обеспечения для блога, мы возьмем эти данные и сгенерируем из них HTML, который наш веб-сервер будет возвращать в ответ на HTTP-запросы.

Для нашего блога мы хотим генерировать два типа страниц:

1.  **Просмотр поста**. Рендерит конкретный пост. Поле `Body` в `Post` представляет собой строку, содержащую markdown, поэтому оно должно быть преобразовано в HTML.
2.  **Индекс**. Перечисляет все посты с гиперссылками для просмотра конкретного поста.

Мы также хотим добиться единообразного внешнего вида на всем сайте, поэтому для каждой страницы у нас будет стандартная HTML-разметка, такая как `<html>` и `<head>`, содержащая ссылки на CSS-таблицы стилей и все остальное, что нам может понадобиться.

При создании программного обеспечения для блога у вас есть несколько вариантов подхода к тому, как вы создаете и отправляете HTML в браузер пользователя.

Мы спроектируем наш код так, чтобы он принимал `io.Writer`. Это означает, что вызывающий наш код имеет гибкость:

-   Записывать их в [os.File](https://pkg.go.dev/os#File), чтобы они могли быть статически поданы.
-   Записывать HTML непосредственно в [`http.ResponseWriter`](https://pkg.go.dev/net/http#ResponseWriter).
-   Или просто записывать их куда угодно! Пока что-либо реализует `io.Writer`, пользователь может генерировать HTML из `Post`.

## Сначала напишите тест

Как всегда, важно подумать о требованиях, прежде чем слишком быстро погружаться в работу. Как мы можем взять этот довольно большой набор требований и разбить его на небольшой, достижимый шаг, на котором мы можем сосредоточиться?

На мой взгляд, фактический просмотр контента имеет более высокий приоритет, чем индексная страница. Мы могли бы запустить этот продукт и делиться прямыми ссылками на наш замечательный контент. Индексная страница, которая не может ссылаться на сам контент, бесполезна.

Тем не менее, рендеринг поста, как описано ранее, все еще кажется большим. Вся HTML-разметка, преобразование markdown-тела в HTML, перечисление тегов и т.д.

На этом этапе меня не слишком беспокоит конкретная разметка, и простой первый шаг — это просто проверить, можем ли мы отрисовать заголовок поста как `<h1>`. Это *чувствуется* как самый маленький первый шаг, который может немного продвинуть нас вперед.

```go
package blogrenderer_test

import (
	"bytes"
	"github.com/quii/learn-go-with-tests/blogrenderer"
	"testing"
)

func TestRender(t *testing.T) {
	var (
		aPost = blogrenderer.Post{
			Title:       "hello world",
			Body:        "This is a post",
			Description: "This is a description",
			Tags:        []string{"go", "tdd"},
		}
	)

	t.Run("it converts a single post into HTML", func(t *testing.T) {
		buf := bytes.Buffer{}
		err := blogrenderer.Render(&buf, aPost)

		if err != nil {
			t.Fatal(err)
		}

		got := buf.String()
		want := `<h1>hello world</h1>`
		if got != want {
			t.Errorf("got '%s' want '%s'", got, want)
		}
	})
}
```

Наше решение принимать `io.Writer` также упрощает тестирование; в данном случае мы пишем в [`bytes.Buffer`](https://pkg.go.dev/bytes#Buffer), содержимое которого мы можем позже проверить.

## Рефакторинг

Пока не так много для рефакторинга, поэтому перейдем к следующей итерации.

## Сначала напишите тест

Теперь, когда у нас есть очень простая рабочая версия, мы можем развивать тест, чтобы расширить функциональность. В данном случае, это отрисовка дополнительной информации из `Post`.

```go
	t.Run("it converts a single post into HTML", func(t *testing.T) {
		buf := bytes.Buffer{}
		err := blogrenderer.Render(&buf, aPost)

		if err != nil {
			t.Fatal(err)
		}

		got := buf.String()
		want := `<h1>hello world</h1>
<p>This is a description</p>
Tags: <ul><li>go</li><li>tdd</li></ul>`

		if got != want {
			t.Errorf("got '%s' want '%s'", got, want)
		}
	})
```

Заметьте, что писать это *неудобно*. Видеть всю эту разметку в тесте неприятно, и мы еще даже не добавили тело, или фактический HTML, который мы хотели бы получить со всем содержимым `<head>` и любой другой разметкой страницы, которая нам нужна.

Тем не менее, давайте *пока* потерпим эту боль.

Он должен завершиться сбоем, жалуясь, что у него нет ожидаемой нами строки, поскольку мы не отрисовываем описание и теги.

## Напишите достаточно кода, чтобы он прошел

Попробуйте сделать это сами, а не копировать код. Вы обнаружите, что заставить этот тест пройти _немного раздражает_! Когда я попробовал, моя первая попытка выдала такую ошибку

```
=== RUN   TestRender
=== RUN   TestRender/it_converts_a_single_post_into_HTML
    renderer_test.go:32: got '<h1>hello world</h1><p>This is a description</p><ul><li>go</li><li>tdd</li></ul>' want '<h1>hello world</h1>
        <p>This is a description</p>
        Tags: <ul><li>go</li><li></li></ul>'
```

Новые строки! Кого это волнует? Ну, наш тест волнует, потому что он ищет точное строковое значение. Должен ли? Я пока удалил новые строки, просто чтобы тест прошел.

```go
func Render(w io.Writer, p Post) error {
	_, err := fmt.Fprintf(w, "<h1>%s</h1>\n<p>%s</p>\n", p.Title, p.Description)
	if err != nil {
		return err
	}

	_, err = fmt.Fprint(w, "Tags: <ul>")
	if err != nil {
		return err
	}

	for _, tag := range p.Tags {
		_, err = fmt.Fprintf(w, "<li>%s</li>", tag)
		if err != nil {
			return err
		}
	}

	_, err = fmt.Fprint(w, "</ul>")
	if err != nil {
		return err
	}

	return nil
}
```

**Упс**. Не самый приятный код, который я написал, и мы все еще находимся на очень ранней стадии реализации нашей разметки. Нам понадобится намного больше контента и элементов на нашей странице, и мы быстро видим, что такой подход не подходит.

Что особенно важно, у нас есть проходящий тест; у нас есть работающее программное обеспечение.

## Рефакторинг

Имея страховочную сетку из проходящего теста для работающего кода, мы можем теперь подумать об изменении нашего подхода к реализации на стадии рефакторинга.

### Введение шаблонов

Go имеет два пакета для шаблонов: [text/template](https://pkg.go.dev/text/template) и [html/template](https://pkg.go.dev/html/template), которые используют один и тот же интерфейс. Оба они позволяют объединять шаблон и некоторые данные для получения строки.

В чем разница с HTML-версией?

> Пакет `template` (`html/template`) реализует шаблоны, управляемые данными, для генерации HTML-вывода, безопасного от внедрения кода. Он предоставляет тот же интерфейс, что и пакет `text/template`, и должен использоваться вместо `text/template` всякий раз, когда вывод является HTML.

Язык шаблонов очень похож на [Mustache](https://mustache.github.io) и позволяет динамически генерировать контент очень чисто, с хорошим разделением ответственности. По сравнению с другими языками шаблонов, которые вы, возможно, использовали, он очень ограничен или "безопасен для логики" (logic-less), как любит говорить Mustache. Это важное **и преднамеренное** дизайнерское решение.

Хотя здесь мы сосредоточены на генерации HTML, если ваш проект выполняет сложные конкатенации строк и заклинания, вы можете обратиться к `text/template` для очистки вашего кода.

### Возвращаемся к коду

Вот шаблон для нашего блога:

`<h1>{{.Title}}</h1><p>{{.Description}}</p>Tags: <ul>{{range .Tags}}<li>{{.}}</li>{{end}}</ul>`

Где мы определяем эту строку? У нас есть несколько вариантов, но чтобы шаги были небольшими, давайте просто начнем с обычной строки.

```go
package blogrenderer

import (
	"html/template"
	"io"
)

const (
	postTemplate = `<h1>{{.Title}}</h1><p>{{.Description}}</p>Tags: <ul>{{range .Tags}}<li>{{.}}</li>{{end}}</ul>`
)

func Render(w io.Writer, p Post) error {
	templ, err := template.New("blog").Parse(postTemplate)
	if err != nil {
		return err
	}

	if err := templ.Execute(w, p); err != nil {
		return err
	}

	return nil
}
```

Мы создаем новый шаблон с именем, а затем разбираем нашу строку шаблона. Затем мы можем использовать метод `Execute` для него, передавая наши данные, в данном случае `Post`.

Шаблон заменит такие вещи, как `{{.Description}}`, содержимым `p.Description`. Шаблоны также предоставляют вам некоторые примитивы программирования, такие как `range` для итерации по значениям и `if`. Более подробную информацию вы можете найти в [документации text/template](https://pkg.go.dev/text/template).

*Это должен быть чистый рефакторинг.* Нам не нужно будет менять наши тесты, и они должны продолжать проходить. Важно то, что наш код легче читать и в нем гораздо меньше надоедливой обработки ошибок, с которой приходится бороться.

Часто люди жалуются на многословность обработки ошибок в Go, но вы можете обнаружить, что есть лучшие способы написания кода, чтобы он изначально был менее подвержен ошибкам, как в этом случае.

### Больше рефакторинга

Использование `html/template` определенно стало улучшением, но наличие его в виде строковой константы в нашем коде не очень хорошо:

-   Его все еще довольно трудно читать.
-   Он не удобен для IDE/редактора. Нет подсветки синтаксиса, возможности форматирования, рефакторинга и т.д.
-   Он выглядит как HTML, но вы не можете работать с ним так, как с "обычным" HTML-файлом.

Что мы хотели бы сделать, так это хранить наши шаблоны в отдельных файлах, чтобы мы могли лучше их организовать и работать с ними как с HTML-файлами.

Создайте папку с именем "templates" и внутри нее создайте файл с именем `blog.gohtml`, вставьте наш шаблон в этот файл.

Теперь измените наш код, чтобы встроить файловые системы, используя [функциональность встраивания, включенную в Go 1.16](https://pkg.go.dev/embed).

```go
package blogrenderer

import (
	"embed"
	"html/template"
	"io"
)

var (
	//go:embed "templates/*"
	postTemplates embed.FS
)

func Render(w io.Writer, p Post) error {
	templ, err := template.ParseFS(postTemplates, "templates/*.gohtml")
	if err != nil {
		return err
	}

	if err := templ.Execute(w, p); err != nil {
		return err
	}

	return nil
}
```

Встраивая "файловую систему" в наш код, мы можем загружать несколько шаблонов и свободно их комбинировать. Это станет полезным, когда мы захотим совместно использовать логику рендеринга между различными шаблонами, например, заголовок для верхней части HTML-страницы и нижний колонтитул.

### Встраивание (`embed`)?

Встраивание (Embed) было кратко затронуто в [главе о чтении файлов](reading-files.md). [Документация стандартной библиотеки объясняет](https://pkg.go.dev/embed):

> Пакет `embed` предоставляет доступ к файлам, встроенным в запущенную Go-программу.
>
> Исходные файлы Go, импортирующие "embed", могут использовать директиву `//go:embed` для инициализации переменной типа `string`, `[]byte` или `FS` содержимым файлов, прочитанных из каталога пакета или подкаталогов во время компиляции.

Зачем нам это использовать? Альтернатива заключается в том, что мы *можем* загружать наши шаблоны из "обычной" файловой системы. Однако это означает, что нам придется убедиться, что шаблоны находятся в правильном пути к файлу везде, где мы хотим использовать это программное обеспечение. В вашей работе у вас могут быть различные среды, такие как разработка, стейджинг и продакшн. Чтобы это работало, вам нужно будет убедиться, что ваши шаблоны скопированы в правильное место.

При использовании `embed` файлы включаются в вашу Go-программу при ее сборке. Это означает, что после того, как вы собрали свою программу (что вы должны делать только один раз), файлы всегда доступны вам.

Удобно то, что вы можете встраивать не только отдельные файлы, но и файловые системы; и эта файловая система реализует [io/fs](https://pkg.go.dev/io/fs), что означает, что ваш код не должен заботиться о том, с какой файловой системой он работает.

Однако, если вы хотите использовать разные шаблоны в зависимости от конфигурации, вы можете придерживаться загрузки шаблонов с диска более традиционным способом.

## Далее: Сделаем шаблон "красивым"

Мы не хотим, чтобы наш шаблон был определен как одна строка. Мы хотим иметь возможность распределить его, чтобы облегчить чтение и работу с ним, примерно так:

```handlebars
<h1>{{.Title}}</h1>

<p>{{.Description}}</p>

Tags: <ul>{{range .Tags}}<li>{{.}}</li>{{end}}</ul>
```

Но если мы это сделаем, наш тест завершится сбоем. Это потому, что наш тест ожидает возврата очень специфичной строки.

Но на самом деле нам все равно на пробельные символы. Поддержание этого теста превратится в кошмар, если нам придется кропотливо обновлять строку утверждения каждый раз, когда мы вносим незначительные изменения в разметку. По мере роста шаблона такие изменения становится все труднее управлять, а затраты на работу выйдут из-под контроля.

## Введение в Approval Tests (тесты подтверждения)

[Go Approval Tests](https://github.com/approvals/go-approval-tests)

> ApprovalTests позволяет легко тестировать большие объекты, строки и все остальное, что может быть сохранено в файл (изображения, звуки, CSV и т.д.)

Идея похожа на "золотые" файлы или моментальные снимки тестирования. Вместо неудобного поддержания строк внутри тестового файла, инструмент подтверждения может сравнить вывод с "утвержденным" файлом, который вы создали. Затем вы просто копируете новую версию, если вы ее одобряете. Перезапустите тест, и вы снова "в зеленой зоне".

Добавьте зависимость `"github.com/approvals/go-approval-tests"` (с помощью команды `go get github.com/approvals/go-approval-tests`) в ваш проект и измените тест следующим образом

```go
func TestRender(t *testing.T) {
	var (
		aPost = blogrenderer.Post{
			Title:       "hello world",
			Body:        "This is a post",
			Description: "This is a description",
			Tags:        []string{"go", "tdd"},
		}
	)

	t.Run("it converts a single post into HTML", func(t *testing.T) {
		buf := bytes.Buffer{}

		if err := blogrenderer.Render(&buf, aPost); err != nil {
			t.Fatal(err)
		}

		approvals.VerifyString(t, buf.String())
	})
}
```

При первом запуске он завершится сбоем, потому что мы еще ничего не утвердили.

```
=== RUN   TestRender
=== RUN   TestRender/it_converts_a_single_post_into_HTML
    renderer_test.go:29: Failed Approval: received does not match approved.
```

Он создаст два файла, которые выглядят следующим образом:

-   `renderer_test.TestRender.it_converts_a_single_post_into_HTML.received.txt`
-   `renderer_test.TestRender.it_converts_a_single_post_into_HTML.approved.txt`

Файл `received` содержит новую, неутвержденную версию вывода. Скопируйте его в пустой файл `approved` и перезапустите тест.

Скопировав новую версию, вы "одобрили" изменение, и тест теперь проходит.

Чтобы увидеть рабочий процесс в действии, отредактируйте шаблон, как мы обсуждали, чтобы сделать его более читабельным (но семантически он останется тем же).

```handlebars
<h1>{{.Title}}</h1>

<p>{{.Description}}</p>

Tags: <ul>{{range .Tags}}<li>{{.}}</li>{{end}}</ul>
```

Перезапустите тест. Будет создан новый файл "received", потому что вывод нашего кода отличается от утвержденной версии. Просмотрите их, и если вы довольны изменениями, просто скопируйте новую версию и перезапустите тест. Обязательно зафиксируйте утвержденные файлы в системе контроля версий.

Этот подход значительно упрощает управление изменениями в больших и неуклюжих вещах, таких как HTML. Вы можете использовать инструмент сравнения, чтобы просматривать и управлять различиями, и это делает ваш тестовый код чище.

![Используйте инструмент сравнения для управления изменениями](https://i.imgur.com/0MoNdva.png)

Это на самом деле довольно незначительное использование тестов подтверждения, которые являются чрезвычайно полезным инструментом в вашем арсенале тестирования. У [Эмили Баше](https://twitter.com/emilybache) есть [интересное видео, где она использует тесты подтверждения, чтобы добавить невероятно обширный набор тестов в сложную кодовую базу, у которой нет тестов](https://www.youtube.com/watch?v=zyM2Ep28ED8). "Комбинаторное тестирование" — это определенно то, что стоит изучить.

Теперь, когда мы внесли это изменение, мы все еще получаем выгоду от хорошо протестированного кода, но тесты не будут сильно мешать, когда мы экспериментируем с разметкой.

### Мы все еще используем TDD?

Интересным побочным эффектом этого подхода является то, что он отводит нас от TDD. Конечно, вы *могли бы* вручную отредактировать утвержденные файлы до желаемого состояния, запустить тесты, а затем исправить шаблоны так, чтобы они выдавали то, что вы определили.

Но это просто глупо! TDD — это метод работы, а именно проектирования; но это не означает, что мы должны догматически использовать его для **всего**.

Важно то, что мы поступили правильно и использовали TDD как **инструмент проектирования** для разработки API нашего пакета. Для изменений шаблонов наш процесс может быть таким:

-   Внести небольшое изменение в шаблон
-   Запустить тест подтверждения
-   Визуально проверить вывод, чтобы убедиться, что он выглядит правильно
-   Выполнить утверждение
-   Повторить

Мы все равно не должны отказываться от ценности работы небольшими, достижимыми шагами. Старайтесь находить способы делать изменения небольшими и продолжайте перезапускать тесты, чтобы получать реальную обратную связь о том, что вы делаете.

Если мы начнем вносить изменения в код *вокруг* шаблонов, то, конечно, это может потребовать возвращения к нашему методу работы TDD.

## Расширим разметку

Большинство веб-сайтов имеют более богатый HTML, чем у нас сейчас. Для начала, элемент `html` вместе с `head`, возможно, также `nav`. Обычно также есть идея футера.

Если на нашем сайте будут разные страницы, мы захотим определить эти элементы в одном месте, чтобы сохранить единообразный вид сайта. Шаблоны Go поддерживают определение разделов, которые мы можем затем импортировать в другие шаблоны.

Отредактируйте наш существующий шаблон, чтобы импортировать верхний и нижний шаблоны.

```handlebars
{{template "top" .}}
<h1>{{.Title}}</h1>

<p>{{.Description}}</p>

Tags: <ul>{{range .Tags}}<li>{{.}}</li>{{end}}</ul>
{{template "bottom" .}}
```

Затем создайте `top.gohtml` со следующим содержимым

```handlebars
{{define "top"}}
<!DOCTYPE html>
<html lang="en">
<head>
    <title>My amazing blog!</title>
    <meta charset="UTF-8"/>
    <meta name="description" content="Wow, like and subscribe, it really helps the channel guys" lang="en"/>
</head>
<body>
<nav role="navigation">
    <div>
        <h1>Budding Gopher's blog</h1>
        <ul>
            <li><a href="/">home</a></li>
            <li><a href="about">about</a></li>
            <li><a href="archive">archive</a></li>
        </ul>
    </div>
</nav>
<main>
{{end}}
```

И `bottom.gohtml`

```handlebars
{{define "bottom"}}
</main>
<footer>
    <ul>
        <li><a href="https://twitter.com/quii">Twitter</a></li>
        <li><a href="https://github.com/quii">GitHub</a></li>
    </ul>
</footer>
</body>
</html>
{{end}}
```

(Очевидно, не стесняйтесь использовать любую разметку, которая вам нравится!)

Теперь нам нужно указать конкретный шаблон для запуска. В рендерере блога измените команду `Execute` на `ExecuteTemplate`.

```go
if err := templ.ExecuteTemplate(w, "blog.gohtml", p); err != nil {
	return err
}
```

Перезапустите тест. Должен быть создан новый файл "received", и тест завершится сбоем. Проверьте его, и если вы довольны, утвердите его, скопировав поверх старой версии. Перезапустите тест еще раз, и он должен пройти.

## Повод поиграть с бенчмарками

Прежде чем продолжить, давайте рассмотрим, что делает наш код.

```go
func Render(w io.Writer, p Post) error {
	templ, err := template.ParseFS(postTemplates, "templates/*.gohtml")
	if err != nil {
		return err
	}

	if err := templ.ExecuteTemplate(w, "blog.gohtml", p); err != nil {
		return err
	}

	return nil
}
```

-   Разбирает шаблоны
-   Использует шаблон для отрисовки поста в `io.Writer`

Хотя влияние на производительность повторного разбора шаблонов для каждого поста в большинстве случаев будет довольно незначительным, усилия, чтобы *не* делать этого, также довольно незначительны и должны немного привести код в порядок.

Чтобы увидеть влияние отказа от многократного разбора, мы можем использовать инструмент бенчмаркинга, чтобы узнать, насколько быстра наша функция.

```go
func BenchmarkRender(b *testing.B) {
	var (
		aPost = blogrenderer.Post{
			Title:       "hello world",
			Body:        "This is a post",
			Description: "This is a description",
			Tags:        []string{"go", "tdd"},
		}
	)

	for b.Loop() {
		blogrenderer.Render(io.Discard, aPost)
	}
}
```

На моем компьютере вот результаты:

```
BenchmarkRender-8 22124 53812 ns/op
```

Чтобы избежать повторного разбора шаблонов снова и снова, мы создадим тип, который будет хранить разобранный шаблон, и у него будет метод для выполнения рендеринга.

```go
type PostRenderer struct {
	templ *template.Template
}

func NewPostRenderer() (*PostRenderer, error) {
	templ, err := template.ParseFS(postTemplates, "templates/*.gohtml")
	if err != nil {
		return nil, err
	}

	return &PostRenderer{templ: templ}, nil
}

func (r *PostRenderer) Render(w io.Writer, p Post) error {

	if err := r.templ.ExecuteTemplate(w, "blog.gohtml", p); err != nil {
		return err
	}

	return nil
}
```

Это меняет интерфейс нашего кода, поэтому нам нужно будет обновить наш тест.

```go

	}

```

## Возвращаемся к реальной работе

В отношении рендеринга постов, важная оставшаяся часть — это фактически рендеринг `Body`. Если вы помните, это должен быть markdown, написанный автором, поэтому его нужно будет преобразовать в HTML.

Мы оставим это как упражнение для вас, читатель. Вы должны быть в состоянии найти библиотеку Go, которая сделает это за вас. Используйте тест подтверждения, чтобы проверить то, что вы делаете.

### О тестировании сторонних библиотек

**Примечание**. Будьте осторожны и не слишком беспокойтесь об явном тестировании того, как сторонняя библиотека ведет себя в юнит-тестах.

Написание тестов для кода, который вы не контролируете, расточительно и увеличивает затраты на поддержку. Иногда вы можете захотеть использовать [внедрение зависимостей](./dependency-injection.md) для управления зависимостью и имитации ее поведения для теста.

В данном случае, однако, я рассматриваю преобразование markdown в HTML как деталь реализации рендеринга, и наши тесты подтверждения должны дать нам достаточную уверенность.

### Отрисовка индекса

Следующая часть функциональности, которую мы собираемся реализовать, это отрисовка индекса, выводящего посты в виде упорядоченного списка HTML.

Мы расширяем наш API, поэтому снова наденем шляпу TDD.

## Сначала напишите тест

На первый взгляд индексная страница кажется простой, но написание теста все еще побуждает нас сделать некоторые дизайнерские выборы.

```go
t.Run("it renders an index of posts", func(t *testing.T) {
	buf := bytes.Buffer{}
	posts := []blogrenderer.Post{{Title: "Hello World"}, {Title: "Hello World 2"}}

	if err := postRenderer.RenderIndex(&buf, posts); err != nil {
		t.Fatal(err)
	}

	got := buf.String()
	want := `<ol><li><a href="/post/hello-world">Hello World</a></li><li><a href="/post/hello-world-2">Hello World 2</a></li></ol>`

	if got != want {
		t.Errorf("got %q want %q", got, want)
	}
})
```

1.  Мы используем поле `Title` структуры `Post` как часть пути URL, но мы не хотим пробелов в URL, поэтому заменяем их дефисами.
2.  Мы добавили метод `RenderIndex` в наш `PostRenderer`, который снова принимает `io.Writer` и срез `Post`.

Если бы мы придерживались подхода "тесты после, тесты подтверждения", мы бы не отвечали на эти вопросы в контролируемой среде. **Тесты дают нам пространство для размышлений**.

## Напишите достаточно кода, чтобы он прошел

Хотя это *кажется* легким, это немного неудобно. Я сделал это в несколько шагов:

```go
func (r *PostRenderer) RenderIndex(w io.Writer, posts []Post) error {
	indexTemplate := `<ol>{{range .}}<li><a href="/post/{{.Title}}">{{.Title}}</a></li>{{end}}</ol>`

	templ, err := template.New("index").Parse(indexTemplate)
	if err != nil {
		return err
	}

	if err := templ.Execute(w, posts); err != nil {
		return err
	}

	return nil
}
```

Сначала я не хотел заморачиваться с отдельными файлами шаблонов, я просто хотел, чтобы это заработало. Предварительный разбор и разделение шаблонов я рассматриваю как рефакторинг, который можно сделать позже.

Это не проходит, но близко.

```
=== RUN   TestRender
=== RUN   TestRender/it_renders_an_index_of_posts
    renderer_test.go:49: got "<ol><li><a href=\"/post/Hello%20World\">Hello World</a></li><li><a href=\"/post/Hello%20World%202\">Hello World 2</a></li></ol>" want "<ol><li><a href=\"/post/hello-world\">Hello World</a></li><li><a href=\"/post/hello-world-2\">Hello World 2</a></li></ol>"
--- FAIL: TestRender (0.00s)
    --- FAIL: TestRender/it_renders_an_index_of_posts (0.00s)
```

Вы можете видеть, что код шаблонизатора экранирует пробелы в атрибутах `href`. Нам нужен способ замены пробелов на дефисы в строке. Мы не можем просто перебрать `[]Post` и заменить их в памяти, потому что мы все еще хотим, чтобы пробелы отображались пользователю в ссылках.

У нас есть несколько вариантов. Первый, который мы рассмотрим, это передача функции в наш шаблон.

### Передача функций в шаблоны

```go
func (r *PostRenderer) RenderIndex(w io.Writer, posts []Post) error {
	indexTemplate := `<ol>{{range .}}<li><a href="/post/{{sanitiseTitle .Title}}">{{.Title}}</a></li>{{end}}</ol>`

	templ, err := template.New("index").Funcs(template.FuncMap{
		"sanitiseTitle": func(title string) string {
			return strings.ToLower(strings.Replace(title, " ", "-", -1))
		},
	}).Parse(indexTemplate)
	if err != nil {
		return err
	}

	if err := templ.Execute(w, posts); err != nil {
		return err
	}

	return nil
}
```

_Прежде чем разбирать шаблон_, вы можете добавить `template.FuncMap` в свой шаблон, что позволяет определять функции, которые могут быть вызваны внутри вашего шаблона. В данном случае мы создали функцию `sanitiseTitle`, которую затем вызываем внутри нашего шаблона с помощью `{{sanitiseTitle .Title}}`.

Это мощная функция: возможность отправлять функции в ваш шаблон позволит вам делать очень крутые вещи, но стоит ли? Возвращаясь к принципам Mustache и безлогичных шаблонов, почему они отстаивали отсутствие логики? **Что плохого в логике в шаблонах?**

Как мы показали, для тестирования наших шаблонов *нам пришлось ввести совершенно другой вид тестирования*.

Представьте, что вы вводите функцию в шаблон, которая имеет несколько различных перестановок поведения и крайних случаев, **как вы будете ее тестировать**? С текущим дизайном, вашим единственным средством тестирования этой логики является _рендеринг HTML и сравнение строк_. Это нелегкий или разумный способ тестирования логики, и определенно не то, что вы хотели бы для _важной_ бизнес-логики.

Несмотря на то, что метод тестов подтверждения снизил стоимость поддержания этих тестов, они все еще дороже в поддержании, чем большинство юнит-тестов, которые вы будете писать. Они все еще чувствительны к любым незначительным изменениям разметки, которые вы можете внести, просто мы упростили управление ими. Мы все равно должны стремиться к архитектуре нашего кода таким образом, чтобы нам не приходилось писать много тестов вокруг наших шаблонов, и стараться разделять обязанности, чтобы любая логика, которой не нужно находиться внутри нашего кода рендеринга, была должным образом отделена.

Шаблонизаторы, на которые повлиял Mustache, дают вам полезное ограничение: не пытайтесь обходить его слишком часто; **не идите против течения**. Вместо этого примите идею [моделей представления](https://stackoverflow.com/a/11074506/3193), где вы конструируете специфические типы, содержащие данные, которые вам нужны для рендеринга, таким образом, который удобен для языка шаблонов.

Таким образом, любая важная бизнес-логика, которую вы используете для генерации этого набора данных, может быть протестирована отдельно, вдали от запутанного мира HTML и шаблонов.

### Разделение ответственности

Итак, что мы могли бы сделать вместо этого?

#### Добавить метод к `Post`, а затем вызвать его в шаблоне

Мы можем вызывать методы в нашем коде шаблонов для типов, которые мы отправляем, поэтому мы могли бы добавить метод `SanitisedTitle` к `Post`. Это упростило бы шаблон, и мы могли бы легко тестировать эту логику отдельно, если бы захотели. Это, вероятно, самое легкое решение, хотя не обязательно самое простое.

Недостаток этого подхода в том, что это все еще логика _представления_. Она не интересна остальной части системы, но теперь становится частью API для основного объекта предметной области. Со временем такой подход может привести к созданию [объектов-богов](https://en.wikipedia.org/wiki/God_object).

#### Создать выделенный тип модели представления, например `PostViewModel`, с именно теми данными, которые нам нужны

Вместо того, чтобы наш код рендеринга был связан с объектом предметной области `Post`, он принимает модель представления.

```go
type PostViewModel struct {
	Title, SanitisedTitle, Description, Body string
	Tags                     []string
}
```

Вызывающие наш код должны были бы сопоставлять `[]Post` с `[]PostView`, генерируя `SanitizedTitle`. Способом сохранить это чистым было бы наличие `func NewPostView(p Post) PostView`, который инкапсулировал бы сопоставление.

Это сделало бы наш код рендеринга безлогичным и, вероятно, является самым строгим разделением ответственности, которое мы могли бы сделать, но компромиссом является немного более сложный процесс для рендеринга наших постов.

Оба варианта хороши, в данном случае я склоняюсь к первому. По мере развития системы вам следует опасаться добавлять все больше и больше специальных методов только для того, чтобы облегчить процесс рендеринга; выделенные модели представления становятся более полезными, когда преобразование между объектом предметной области и представлением становится более сложным.

Итак, мы можем добавить наш метод к `Post`.

```go
func (p Post) SanitisedTitle() string {
	return strings.ToLower(strings.Replace(p.Title, " ", "-", -1))
}
```

И затем мы можем вернуться к более простому миру в нашем коде рендеринга.

```go
func (r *PostRenderer) RenderIndex(w io.Writer, posts []Post) error {
	indexTemplate := `<ol>{{range .}}<li><a href="/post/{{.SanitisedTitle}}">{{.Title}}</a></li>{{end}}</ol>`

	templ, err := template.New("index").Parse(indexTemplate)
	if err != nil {
		return err
	}

	if err := templ.Execute(w, posts); err != nil {
		return err
	}

	return nil
}
```

## Рефакторинг

Наконец, тест должен пройти. Теперь мы можем переместить наш шаблон в файл (`templates/index.gohtml`) и загрузить его один раз, когда мы конструируем наш рендерер.

```go
package blogrenderer

import (
	"embed"
	"html/template"
	"io"
)

var (
	//go:embed "templates/*"
	postTemplates embed.FS
)

type PostRenderer struct {
	templ *template.Template
}

func NewPostRenderer() (*PostRenderer, error) {
	templ, err := template.ParseFS(postTemplates, "templates/*.gohtml")
	if err != nil {
		return nil, err
	}

	return &PostRenderer{templ: templ}, nil
}

func (r *PostRenderer) Render(w io.Writer, p Post) error {
	return r.templ.ExecuteTemplate(w, "blog.gohtml", p)
}

func (r *PostRenderer) RenderIndex(w io.Writer, posts []Post) error {
	return r.templ.ExecuteTemplate(w, "index.gohtml", posts)
}
```

Разобрав более одного шаблона в `templ`, мы теперь должны вызывать `ExecuteTemplate` и указывать, *какой* шаблон мы хотим отрисовать, но, надеюсь, вы согласитесь, что полученный код выглядит отлично.

Существует *небольшой* риск, что переименование одного из файлов шаблона приведет к ошибке, но наши быстро выполняющиеся модульные тесты быстро поймают ее.

Теперь, когда мы довольны дизайном API нашего пакета и реализовали базовое поведение с помощью TDD, давайте изменим наш тест для использования подтверждений.

```go
	t.Run("it renders an index of posts", func(t *testing.T) {
		buf := bytes.Buffer{}
		posts := []blogrenderer.Post{{Title: "Hello World"}, {Title: "Hello World 2"}}

		if err := postRenderer.RenderIndex(&buf, posts); err != nil {
			t.Fatal(err)
		}

		approvals.VerifyString(t, buf.String())
	})
```

Не забудьте запустить тест, чтобы увидеть, как он завершится сбоем, а затем утвердите изменение.

Наконец, мы можем добавить нашу стандартную разметку страницы к нашей индексной странице:

```handlebars
{{template "top" .}}
<ol>{{range .}}<li><a href="/post/{{.SanitisedTitle}}">{{.Title}}</a></li>{{end}}</ol>
{{template "bottom" .}}
```

Перезапустите тест, утвердите изменение, и с индексом покончено!

## Рендеринг тела markdown

Я призывал вас попробовать это самостоятельно, вот подход, который я в итоге использовал.

```go
package blogrenderer

import (
	"embed"
	"github.com/gomarkdown/markdown"
	"github.com/gomarkdown/markdown/parser"
	"html/template"
	"io"
)

var (
	//go:embed "templates/*"
	postTemplates embed.FS
)

type PostRenderer struct {
	templ *template.Template
}

func NewPostRenderer() (*PostRenderer, error) {
	templ, err := template.ParseFS(postTemplates, "templates/*.gohtml")
	if err != nil {
		return nil, err
	}

	return &PostRenderer{templ: templ}, nil
}

func (r *PostRenderer) Render(w io.Writer, p Post) error {
	return r.templ.ExecuteTemplate(w, "blog.gohtml", newPostVM(p))
}

func (r *PostRenderer) RenderIndex(w io.Writer, posts []Post) error {
	return r.templ.ExecuteTemplate(w, "index.gohtml", posts)
}

type postViewModel struct {
	Post
	HTMLBody template.HTML
}

func newPostVM(p Post) postViewModel {
	vm := postViewModel{Post: p}
	extensions := parser.CommonExtensions | parser.AutoHeadingIDs
	mdParser := parser.NewWithExtensions(extensions)
	vm.HTMLBody = template.HTML(markdown.ToHTML([]byte(p.Body), mdParser, nil))
	return vm
}
```

Я использовал отличную библиотеку [gomarkdown](https://github.com/gomarkdown/markdown), которая работала именно так, как я и ожидал.

Обратите внимание, что мы создаем новый `parser.Parser` при каждом вызове `newPostVM`, вместо того чтобы создать его один раз и сохранить в `PostRenderer`. Обычно, если вы можете что-то создать один раз и использовать повторно, это стоит сделать — это экономит повторяющиеся затраты на создание. Но этот общий инстинкт здесь не работает: парсер gomarkdown сохраняет внутреннее состояние, пока строит дерево документа, и его небезопасно повторно использовать для нескольких вызовов `Parse` — вы получите панику (или, в старых версиях, гораздо менее полезное разыменование нулевого указателя) при втором использовании того же самого парсера. Поскольку `PostRenderer` предназначен для `Render` множества постов в течение своего срока службы, свежий парсер на каждый вызов — это правильный способ его использования — и это дешево в любом случае, так как его создание тривиально по сравнению с самой работой по парсингу.

Если вы попытались сделать это сами, вы могли обнаружить, что при рендеринге тела HTML-код был экранирован. Это функция безопасности пакета `html/template` Go, предназначенная для предотвращения вывода вредоносного HTML от сторонних источников.

Чтобы обойти это, в типе, который вы отправляете для рендеринга, вам нужно будет обернуть ваш доверенный HTML в [template.HTML](https://pkg.go.dev/html/template#HTML).

> `HTML` инкапсулирует известный безопасный фрагмент HTML-документа. Его не следует использовать для HTML от третьих сторон или для HTML с незакрытыми тегами или комментариями. Выходные данные надежного HTML-санитайзера и шаблона, экранированного этим пакетом, подходят для использования с `HTML`.
>
> Использование этого типа представляет риск безопасности: инкапсулированный контент должен поступать из доверенного источника, так как он будет включен в вывод шаблона без изменений.

Поэтому я создал **неэкспортируемую** модель представления (`postViewModel`), потому что я все еще рассматривал это как внутреннюю деталь реализации рендеринга. Мне не нужно тестировать это отдельно, и я не хочу, чтобы это засоряло мой API.

Я конструирую его при рендеринге, чтобы я мог разобрать `Body` в `HTMLBody`, а затем использую это поле в шаблоне для рендеринга HTML.

## Завершение

Если вы объедините свои знания из главы [Чтение файлов](reading-files.md) и этой главы, вы сможете легко создать хорошо протестированный, простой генератор статических сайтов и запустить свой собственный блог. Найдите несколько уроков по CSS, и вы сможете сделать его красивым.

Этот подход выходит за рамки блогов. Получение данных из любого источника, будь то база данных, API или файловая система, преобразование их в HTML и возвращение с сервера — это простая техника, используемая на протяжении многих десятилетий. Людям нравится сетовать на сложность современной веб-разработки, но вы уверены, что не сами навлекаете на себя эту сложность?

Go прекрасно подходит для веб-разработки, особенно если вы четко понимаете свои реальные требования к создаваемому вами веб-сайту. Генерация HTML на сервере часто является лучшим, более простым и производительным подходом, чем создание "веб-приложения" с такими технологиями, как React.

### Что мы узнали

-   Как создавать и рендерить HTML-шаблоны.
-   Как объединять шаблоны и [устранять дублирование](https://en.wikipedia.org/wiki/Don't_repeat_yourself) связанной разметки, а также поддерживать единообразный внешний вид.
-   Как передавать функции в шаблоны и почему стоит дважды подумать, прежде чем это делать.
-   Как писать "тесты подтверждения" (Approval Tests), которые помогают тестировать большой и некрасивый вывод таких вещей, как рендереры шаблонов.

### О безлогичных шаблонах

Как всегда, речь идет о **разделении ответственности**. Важно учитывать, каковы обязанности различных частей нашей системы. Слишком часто люди допускают просачивание важной бизнес-логики в шаблоны, смешивая обязанности и делая системы трудными для понимания, поддержки и тестирования.

### Не только для HTML

Помните, что Go имеет `text/template` для генерации других видов данных из шаблона. Если вам нужно преобразовать данные в какой-либо структурированный вывод, методы, изложенные в этой главе, могут быть полезны.
