# Привет, мир

**[Весь код для этой главы вы найдете здесь](https://github.com/quii/learn-go-with-tests/tree/main/hello-world)**

Традиционно вашей первой программой на новом языке становится [Hello, World](https://en.m.wikipedia.org/wiki/%22Hello,_World!%22_program).

- Создайте папку в любом удобном для вас месте
- Создайте в ней новый файл с именем `hello.go` и поместите в него следующий код

```go
package main

import "fmt"

func main() {
	fmt.Println("Hello, world")
}
```

Чтобы запустить его, введите `go run hello.go`.

## Как это работает

Когда вы пишете программу на Go, у вас будет определен пакет `main` с функцией `main` внутри него. Пакеты — это способ группировать связанный Go-код вместе.

Ключевое слово `func` определяет функцию с именем и телом.

С помощью `import "fmt"` мы импортируем пакет, который содержит функцию `Println`, используемую для вывода.

## Как тестировать

Как это тестировать? Хорошо отделять код вашей «доменной» области от внешнего мира (побочных эффектов). `fmt.Println` — это побочный эффект (вывод в стандартный вывод), а строка, которую мы передаем, является нашей доменной областью.

Итак, давайте разделим эти concerns, чтобы было проще тестировать

```go
package main

import "fmt"

func Hello() string {
	return "Hello, world"
}

func main() {
	fmt.Println(Hello())
}
```

Мы создали новую функцию с `func`, но на этот раз мы добавили еще одно ключевое слово, `string,` к определению. Это означает, что эта функция возвращает `string`.

Теперь создайте новый файл с именем `hello_test.go`, где мы будем писать тест для нашей функции `Hello`

```go
package main

import "testing"

func TestHello(t *testing.T) {
	got := Hello()
	want := "Hello, world"

	if got != want {
		t.Errorf("got %q want %q", got, want)
	}
}
```

## Go-модули?

Следующий шаг — запустить тесты. Введите `go test` в терминале. Если тесты проходят, то вы, вероятно, используете более раннюю версию Go. Однако, если вы используете Go 1.16 или более позднюю версию, тесты, скорее всего, не запустятся. Вместо этого вы увидите в терминале сообщение об ошибке, подобное этому:

```shell
$ go test
go: cannot find main module; see 'go help modules'
```

В чем проблема? Одним словом, [модули](https://blog.golang.org/go116-module-changes). К счастью, проблема легко решается. Введите `go mod init example.com/hello` в терминале. Это создаст новый файл со следующим содержимым:

```
module example.com/hello

go 1.16
```

Этот файл сообщает инструментам `go` важную информацию о вашем коде. Если бы вы планировали распространять свое приложение, вы бы указали, где код доступен для загрузки, а также информацию о зависимостях. Название модуля, example\.com\/hello, обычно относится к URL-адресу, по которому модуль можно найти и загрузить. Для совместимости с инструментами, которые мы скоро начнем использовать, убедитесь, что имя вашего модуля содержит точку, как в .com в example\.com/hello. Пока ваш файл модуля минимален, и вы можете оставить его таким. Чтобы узнать больше о модулях, [вы можете ознакомиться со справочной информацией в документации Golang](https://golang.org/doc/modules/gomod-ref). Теперь мы можем вернуться к тестированию и изучению Go, так как тесты должны запускаться, даже на Go 1.16.

В будущих главах вам нужно будет запускать `go mod init SOMENAME` в каждой новой папке перед выполнением таких команд, как `go test` или `go build`.

Стоит уточнить, что `SOMENAME`, имя модуля, не связано с `package main` (который каждый `.go` файл в этой книге до сих пор объявляет вверху). Имя модуля — это просто идентификатор вашего проекта в целом — его не обязательно называть `main`, и `go run`, `go test`, а также `go build` будут работать правильно с любым выбранным вами именем, если они запускаются из той же папки.

## Возвращаемся к тестированию

Запустите `go test` в терминале. Тесты должны были пройти! Просто для проверки попробуйте намеренно сломать тест, изменив строку `want`.

Обратите внимание, что вам не пришлось выбирать между несколькими фреймворками тестирования, а затем выяснять, как их установить. Все, что вам нужно, встроено в язык, и синтаксис такой же, как и остальной код, который вы будете писать.

### Написание тестов

Написание теста похоже на написание функции, с несколькими правилами:

*   Он должен находиться в файле с именем вроде `xxx_test.go`
*   Тестовая функция должна начинаться со слова `Test`
*   Тестовая функция принимает только один аргумент `t *testing.T`
*   Чтобы использовать тип `*testing.T`, вам нужно `import "testing"`, как мы это делали с `fmt` в другом файле

На данный момент достаточно знать, что ваш `t` типа `*testing.T` является вашим «крючком» к фреймворку тестирования, так что вы можете делать такие вещи, как `t.Fail()`, когда хотите, чтобы тест провалился.

Мы рассмотрели несколько новых тем:

#### `if`
Операторы `if` в Go очень похожи на операторы в других языках программирования.

#### Объявление переменных

Мы объявляем некоторые переменные с синтаксисом `varName := value`, что позволяет нам повторно использовать некоторые значения в нашем тесте для удобочитаемости.

#### `t.Errorf`

Мы вызываем _метод_ `Errorf` на нашем `t`, который выведет сообщение и провалит тест. Буква `f` означает формат (format), что позволяет нам создавать строку с значениями, вставленными в заполнители `%q`. Когда вы намеренно провалите тест, должно быть понятно, как это работает.

Вы можете прочитать больше о строках-заполнителях в [документации fmt](https://pkg.go.dev/fmt#hdr-Printing). Для тестов `%q` очень полезен, так как он заключает ваши значения в двойные кавычки.

Позже мы рассмотрим разницу между методами и функциями.

### Документация Go

Еще одна удобная функция Go — это документация. Мы только что видели документацию для пакета `fmt` на официальном веб-сайте просмотра пакетов, и Go также предоставляет способы быстрого получения документации в автономном режиме.

В Go есть встроенный инструмент `doc`, который позволяет вам просматривать любой пакет, установленный в вашей системе, или модуль, над которым вы в данный момент работаете. Чтобы просмотреть ту же документацию по глаголам печати:

```
$ go doc fmt
package fmt // import "fmt"

Package fmt implements formatted I/O with functions analogous to C's printf and
scanf. The format 'verbs' are derived from C's but are simpler.

# Printing

The verbs:

General:

    %v	the value in a default format
    	when printing structs, the plus flag (%+v) adds field names
    %#v	a Go-syntax representation of the value
    %T	a Go-syntax representation of the type of the value
    %%	a literal percent sign; consumes no value
...
```

Второй инструмент Go для просмотра документации — это команда `pkgsite`, которая лежит в основе официального веб-сайта Go для просмотра пакетов. Вы можете установить `pkgsite` с помощью `go install golang.org/x/pkgsite/cmd/pkgsite@latest`, а затем запустить его с помощью `pkgsite -open .`. Команда установки Go загрузит исходные файлы из этого репозитория и соберет их в исполняемый бинарный файл. Для стандартной установки Go этот исполняемый файл будет находиться в `$HOME/go/bin` для Linux и macOS, и `%USERPROFILE%\go\bin` для Windows. Если вы еще не добавили эти пути в свою переменную `$PATH`, вы можете сделать это, чтобы упростить запуск установленных Go-команд.

Подавляющее большинство стандартной библиотеки имеет отличную документацию с примерами. Стоит посетить [http://localhost:8080/testing](http://localhost:8080/testing), чтобы увидеть, что вам доступно.

### Привет, ТЫ

Теперь, когда у нас есть тест, мы можем безопасно итерировать наше программное обеспечение.

В предыдущем примере мы написали тест _после_ написания кода, чтобы вы могли получить пример того, как писать тест и объявлять функцию. С этого момента мы будем _сначала писать тесты_.

Наше следующее требование — позволить нам указывать получателя приветствия.

Давайте начнем с фиксации этих требований в тесте. Это базовый test-driven development (разработка через тестирование) и позволяет нам убедиться, что наш тест _действительно_ проверяет то, что мы хотим. При ретроспективном написании тестов существует риск того, что ваш тест может продолжать проходить, даже если код не работает должным образом.

```go
package main

import "testing"

func TestHello(t *testing.T) {
	got := Hello("Chris")
	want := "Hello, Chris"

	if got != want {
		t.Errorf("got %q want %q", got, want)
	}
}
```

Теперь запустите `go test`, у вас должна быть ошибка компиляции

```text
./hello_test.go:6:18: too many arguments in call to Hello
    have (string)
    want ()
```

При использовании статически типизированного языка, такого как Go, важно _слушать компилятор_. Компилятор понимает, как ваш код должен соединяться и работать, так что вам не придется этого делать.

В этом случае компилятор говорит вам, что нужно сделать, чтобы продолжить. Мы должны изменить нашу функцию `Hello`, чтобы она принимала аргумент.

Отредактируйте функцию `Hello`, чтобы она принимала аргумент типа `string`

```go
func Hello(name string) string {
	return "Hello, world"
}
```

Если вы снова попытаетесь запустить свои тесты, ваш `hello.go` не скомпилируется, потому что вы не передаете аргумент. Передайте "world", чтобы он скомпилировался.

```go
func main() {
	fmt.Println(Hello("world"))
}
```

Теперь, когда вы запустите свои тесты, вы должны увидеть что-то вроде

```text
hello_test.go:10: got 'Hello, world' want 'Hello, Chris''
```

У нас наконец-то есть компилируемая программа, но она не соответствует нашим требованиям согласно тесту.

Давайте сделаем так, чтобы тест прошел, используя аргумент `name` и объединив его с `Hello,`

```go
func Hello(name string) string {
	return "Hello, " + name
}
```

Когда вы запустите тесты, они теперь должны пройти. Обычно, в рамках цикла TDD, мы должны теперь _рефакторить_.

### Замечание о системе контроля версий

На этом этапе, если вы используете систему контроля версий (что вы должны делать!), я бы сделал `commit` кода в его текущем состоянии. У нас есть работающее программное обеспечение, поддерживаемое тестом.

Я бы _не_ стал пушить в `main`, потому что я планирую рефакторинг следующим шагом. Приятно сделать коммит на этом этапе на случай, если вы каким-то образом запутаетесь с рефакторингом — вы всегда сможете вернуться к рабочей версии.

Здесь не так много для рефакторинга, но мы можем ввести еще одну языковую особенность — _константы_.

### Константы

Константы определяются так:

```go
const englishHelloPrefix = "Hello, "
```

Теперь мы можем рефакторить наш код

```go
const englishHelloPrefix = "Hello, "

func Hello(name string) string {
	return englishHelloPrefix + name
}
```

После рефакторинга снова запустите тесты, чтобы убедиться, что вы ничего не сломали.

Стоит подумать о создании констант для фиксации значения и иногда для повышения производительности.

## Привет, мир... снова

Следующее требование заключается в том, что когда наша функция вызывается с пустой строкой, она по умолчанию выводит "Hello, World", а не "Hello, ".

Начнем с написания нового, проваливающегося теста:

```go
func TestHello(t *testing.T) {
	t.Run("saying hello to people", func(t *testing.T) {
		got := Hello("Chris")
		want := "Hello, Chris"

		if got != want {
			t.Errorf("got %q want %q", got, want)
		}
	})
	t.Run("say 'Hello, World' when an empty string is supplied", func(t *testing.T) {
		got := Hello("")
		want := "Hello, World"

		if got != want {
			t.Errorf("got %q want %q", got, want)
		}
	})
}
```

Здесь мы вводим еще один инструмент в нашем арсенале тестирования: подтесты. Иногда полезно группировать тесты вокруг «сущности», а затем иметь подтесты, описывающие различные сценарии.

Преимущество этого подхода заключается в том, что вы можете настроить общий код, который можно использовать в других тестах.

Пока у нас есть проваливающийся тест, давайте исправим код, используя `if`.

```go
const englishHelloPrefix = "Hello, "

func Hello(name string) string {
	if name == "" {
		name = "World"
	}
	return englishHelloPrefix + name
}
```

Если мы запустим наши тесты, мы увидим, что они удовлетворяют новому требованию, и мы не сломали случайно другую функциональность.

Важно, чтобы ваши тесты _были четкими спецификациями_ того, что должен делать код. Но есть повторяющийся код, когда мы проверяем, соответствует ли сообщение нашим ожиданиям.

Рефакторинг предназначен не _только_ для производственного кода!

Теперь, когда тесты проходят, мы можем и должны рефакторить наши тесты.

```go
func TestHello(t *testing.T) {
	t.Run("saying hello to people", func(t *testing.T) {
		got := Hello("Chris")
		want := "Hello, Chris"
		assertCorrectMessage(t, got, want)
	})

	t.Run("empty string defaults to 'world'", func(t *testing.T) {
		got := Hello("")
		want := "Hello, World"
		assertCorrectMessage(t, got, want)
	})

}

func assertCorrectMessage(t testing.TB, got, want string) {
	t.Helper()
	if got != want {
		t.Errorf("got %q want %q", got, want)
	}
}
```

Что мы здесь сделали?

Мы рефакторили наше утверждение в новую функцию. Это уменьшает дублирование и улучшает читаемость наших тестов. Нам нужно передавать `t *testing.T`, чтобы мы могли указать тестовому коду на провал, когда это необходимо.

Для вспомогательных функций хорошей идеей является прием `testing.TB`, который является интерфейсом, удовлетворяемым как `*testing.T`, так и `*testing.B`, так что вы можете вызывать вспомогательные функции из теста или бенчмарка (не беспокойтесь, если слова вроде «интерфейс» вам сейчас ничего не говорят, это будет рассмотрено позже).

`t.Helper()` необходим, чтобы сообщить тестовому набору, что этот метод является вспомогательным. Делая это, при провале, сообщаемый номер строки будет в нашем _вызове функции_, а не внутри нашей вспомогательной функции теста. Это поможет другим разработчикам легче отслеживать проблемы. Если вы все еще не понимаете, закомментируйте его, сделайте так, чтобы тест провалился, и понаблюдайте за выводом теста. Комментарии в Go — отличный способ добавить дополнительную информацию к вашему коду, или, в данном случае, быстрый способ сказать компилятору игнорировать строку. Вы можете закомментировать код `t.Helper()`, добавив два косых черты `//` в начале строки. Вы должны увидеть, как эта строка станет серой или изменит цвет, отличный от остального вашего кода, чтобы показать, что она теперь закомментирована.

Когда у вас несколько аргументов одного типа (в нашем случае две строки), вместо `(got string, want string)` вы можете сократить это до `(got, want string)`.

### Возвращаемся к системе контроля версий

Теперь, когда мы довольны кодом, я бы изменил предыдущий коммит, чтобы мы зафиксировали только прекрасную версию нашего кода с тестом.

### Дисциплина

Давайте снова пройдемся по циклу:

*   Написать тест
*   Добиться, чтобы компилятор успешно прошел
*   Запустить тест, убедиться, что он проваливается, и проверить, что сообщение об ошибке понятно
*   Написать достаточно кода, чтобы тест прошел
*   Выполнить рефакторинг

На первый взгляд это может показаться утомительным, но придерживаться цикла обратной связи важно.

Это не только гарантирует, что у вас есть _релевантные тесты_, это помогает _проектировать хорошее программное обеспечение_, выполняя рефакторинг с безопасностью тестов.

Видеть, как тест проваливается, — важная проверка, потому что это также позволяет вам увидеть, как выглядит сообщение об ошибке. Как разработчику, может быть очень трудно работать с кодовой базой, когда проваливающиеся тесты не дают четкого представления о том, в чем проблема.

Обеспечивая _быстроту_ ваших тестов и настраивая инструменты таким образом, чтобы запуск тестов был простым, вы можете войти в состояние потока при написании кода.

Не написав тесты, вы обязуетесь вручную проверять свой код, запуская свое программное обеспечение, что нарушает ваше состояние потока. Вы не сэкономите себе время, особенно в долгосрочной перспективе.

## Продолжаем! Новые требования

О боже, у нас еще больше требований. Теперь нам нужно поддерживать второй параметр, указывающий язык приветствия. Если передается неизвестный язык, просто использовать английский по умолчанию.

Мы должны быть уверены, что можем легко использовать TDD для реализации этой функциональности!

Напишите тест для пользователя, передающего испанский язык. Добавьте его в существующий набор тестов.

```go
	t.Run("in Spanish", func(t *testing.T) {
		got := Hello("Elodie", "Spanish")
		want := "Hola, Elodie"
		assertCorrectMessage(t, got, want)
	})
```

Помните, не жульничайте! _Сначала тест_. Когда вы попытаетесь запустить тест, компилятор _должен_ пожаловаться, потому что вы вызываете `Hello` с двумя аргументами вместо одного.

```text
./hello_test.go:27:19: too many arguments in call to Hello
    have (string, string)
    want (string)
```

Исправьте проблемы компиляции, добавив еще один строковый аргумент в `Hello`

```go
func Hello(name string, language string) string {
	if name == "" {
		name = "World"
	}
	return englishHelloPrefix + name
}
```

Когда вы снова попытаетесь запустить тест, он пожалуется на то, что вы не передаете достаточно аргументов в `Hello` в других ваших тестах и в `hello.go`

```text
./hello.go:15:19: not enough arguments in call to Hello
    have (string)
    want (string, string)
```

Исправьте это, передав пустые строки. Теперь все ваши тесты должны компилироваться _и_ проходить, кроме нашего нового сценария:

```text
hello_test.go:29: got 'Hello, Elodie' want 'Hola, Elodie'
```

Мы можем использовать `if` здесь, чтобы проверить, равен ли язык "Spanish", и если да, изменить сообщение.

```go
func Hello(name string, language string) string {
	if name == "" {
		name = "World"
	}

	if language == "Spanish" {
		return "Hola, " + name
	}
	return englishHelloPrefix + name
}
```

Теперь тесты должны проходить.

Пришло время _рефакторинга_. Вы должны заметить некоторые проблемы в коде: «магические» строки, некоторые из которых повторяются. Попробуйте рефакторить самостоятельно, при каждом изменении убедитесь, что вы снова запускаете тесты, чтобы убедиться, что ваш рефакторинг ничего не сломал.

```go
	const spanish = "Spanish"
	const englishHelloPrefix = "Hello, "
	const spanishHelloPrefix = "Hola, "

	func Hello(name string, language string) string {
		if name == "" {
			name = "World"
		}

		if language == spanish {
			return spanishHelloPrefix + name
		}
		return englishHelloPrefix + name
	}
```

### Французский

*   Напишите тест, подтверждающий, что если вы передадите `"French"`, вы получите `"Bonjour, "`
*   Убедитесь, что он провалился, проверьте, легко ли читается сообщение об ошибке
*   Сделайте самое минимальное разумное изменение в коде

Возможно, вы написали что-то, что выглядит примерно так:

```go
func Hello(name string, language string) string {
	if name == "" {
		name = "World"
	}

	if language == spanish {
		return spanishHelloPrefix + name
	}
	if language == french {
		return frenchHelloPrefix + name
	}
	return englishHelloPrefix + name
}
```

## `switch`

Когда у вас много операторов `if`, проверяющих определенное значение, обычно вместо них используется оператор `switch`. Мы можем использовать `switch` для рефакторинга кода, чтобы сделать его более читабельным и расширяемым, если мы захотим добавить поддержку других языков позже.

```go
func Hello(name string, language string) string {
	if name == "" {
		name = "World"
	}

	prefix := englishHelloPrefix

	switch language {
	case spanish:
		prefix = spanishHelloPrefix
	case french:
		prefix = frenchHelloPrefix
	}

	return prefix + name
}
```

Обратите внимание, что мы используем `:=` один раз для `prefix` (объявляя новую переменную и присваивая ей начальное значение), но простой `=` везде, где значение изменяется, как для `name` выше, так и для `prefix` внутри `switch`. `:=` — это [короткое объявление переменной](https://go.dev/ref/spec#Short_variable_declarations) в Go — оно создает новую переменную. `=` — это [обычное присваивание](https://go.dev/ref/spec#Assignment_statements) — оно изменяет значение уже существующей переменной (`name` уже существует как параметр, а `prefix` был объявлен парой строк выше с помощью `:=`). Использование `:=` для переменной, которая уже существует в той же области видимости, или `=` для той, которая еще не существует, является ошибкой компиляции.

Напишите тест, чтобы теперь включить приветствие на выбранном вами языке, и вы увидите, как просто расширить нашу _замечательную_ функцию.

### Еще одно... последнее... рефакторинг?

Можно утверждать, что наша функция становится немного большой. Самый простой рефакторинг для этого заключался бы в извлечении некоторой функциональности в другую функцию.

```go

const (
	spanish = "Spanish"
	french  = "French"

	englishHelloPrefix = "Hello, "
	spanishHelloPrefix = "Hola, "
	frenchHelloPrefix  = "Bonjour, "
)

func Hello(name string, language string) string {
	if name == "" {
		name = "World"
	}

	return greetingPrefix(language) + name
}

func greetingPrefix(language string) (prefix string) {
	switch language {
	case french:
		prefix = frenchHelloPrefix
	case spanish:
		prefix = spanishHelloPrefix
	default:
		prefix = englishHelloPrefix
	}
	return
}
```

Несколько новых концепций:

*   В сигнатуре нашей функции мы сделали _именованное возвращаемое значение_ `(prefix string)`.
*   Это создаст переменную с именем `prefix` в вашей функции.
    *   Ей будет присвоено «нулевое» значение. Это зависит от типа, например, для `int` это 0, а для `string` это `""`.
    *   Вы можете вернуть любое установленное значение, просто вызвав `return`, а не `return prefix`.
    *   Это будет отображаться в Go Doc для вашей функции, что может сделать намерение вашего кода более ясным.
*   `default` в операторе `switch` будет использоваться, если ни один из других операторов `case` не совпадает.
*   Имя функции начинается со строчной буквы. В Go публичные функции начинаются с заглавной буквы, а приватные — со строчной. Мы не хотим, чтобы внутренности нашего алгоритма были доступны миру, поэтому мы сделали эту функцию приватной.
*   Также мы можем группировать константы в блок вместо объявления их на отдельных строках. Для читаемости хорошей идеей является использование пустой строки между наборами связанных констант.

## Подведение итогов

Кто знал, что можно получить так много от `Hello, world`?

К этому моменту у вас должно быть некоторое понимание:

### Некоторые аспекты синтаксиса Go, касающиеся

*   Написания тестов
*   Объявления функций с аргументами и типами возвращаемых значений
*   `if`, `const` и `switch`
*   Объявления переменных и констант

### Процесс TDD и _почему_ шаги важны

*   _Написание проваливающегося теста и наблюдение за его провалом_, чтобы мы знали, что написали _релевантный_ тест для наших требований, и увидели, что он дает _легко понятное описание сбоя_.
*   Написание минимального количества кода, чтобы тест прошел, чтобы мы знали, что у нас есть работающее программное обеспечение.
*   _Затем_ рефакторинг, подкрепленный безопасностью наших тестов, чтобы обеспечить наличие хорошо проработанного кода, с которым легко работать.

В нашем случае мы перешли от `Hello()` к `Hello("name")`, а затем к `Hello("name", "French")` небольшими, легко понятными шагами.

Конечно, это тривиально по сравнению с «реальным» программным обеспечением, но принципы остаются в силе. TDD — это навык, который требует практики для развития, но разбивая проблемы на более мелкие компоненты, которые вы можете тестировать, вы значительно упростите себе написание программного обеспечения.
