# Привет, мир

**[Весь код для этой главы вы можете найти здесь](https://github.com/quii/learn-go-with-tests/tree/main/hello-world)**

Традиционно вашей первой программой на новом языке является [Hello, World](https://en.m.wikipedia.org/wiki/%22Hello,_World!%22_program).

- Создайте папку в любом удобном для вас месте
- Поместите в нее новый файл под названием `hello.go` и вставьте в него следующий код:

```go
package main

import "fmt"

func main() {
	fmt.Println("Hello, world")
}
```

Чтобы запустить его, введите `go run hello.go`.

## Как это работает

Когда вы пишете программу на Go, у вас будет определён `main` пакет с функцией `main` внутри него. Пакеты — это способ группировки связанного кода Go.

Ключевое слово `func` определяет функцию с именем и телом.

С помощью `import "fmt"` мы импортируем пакет, который содержит функцию `Println`, используемую нами для вывода.

## Как тестировать

Как это протестировать? Хорошо отделять ваш "доменный" код от внешнего мира (побочных эффектов). `fmt.Println` является побочным эффектом (вывод в `stdout`), а строка, которую мы передаём, — это наш домен.

Так давайте разделим эти concerns, чтобы было легче тестировать:

```go
package main

import "fmt"

func Hello() string {
	return "Hello, world"
}

func main() {
	fmt.Println(Hello())
}
```

Мы создали новую функцию с помощью `func`, но на этот раз добавили к определению ещё одно ключевое слово: `string`. Это означает, что эта функция возвращает `string`.

Теперь создайте новый файл под названием `hello_test.go`, где мы будем писать тест для нашей функции `Hello`:

```go
package main

import "testing"

func TestHello(t *testing.T) {
	got := Hello()
	want := "Hello, world"

	if got != want {
		t.Errorf("got %q want %q", got, want)
	}
}
```

## Go модули?

Следующий шаг — запустить тесты. Введите `go test` в терминале. Если тесты проходят, то вы, вероятно, используете более раннюю версию Go. Однако, если вы используете Go 1.16 или более позднюю версию, тесты, скорее всего, не запустятся. Вместо этого вы увидите сообщение об ошибке в терминале:

```shell
$ go test
go: cannot find main module; see 'go help modules'
```

В чем проблема? Одним словом, [модули](https://blog.golang.org/go116-module-changes). К счастью, проблему легко исправить. Введите `go mod init example.com/hello` в терминале. Это создаст новый файл со следующим содержимым:

```
module example.com/hello

go 1.16
```

Этот файл сообщает инструментам `go` важную информацию о вашем коде. Если вы планировали распространять свое приложение, вы бы указали, где код доступен для скачивания, а также информацию о зависимостях. Имя модуля, `example.com/hello`, обычно ссылается на URL, по которому модуль можно найти и загрузить. Для совместимости с инструментами, которые мы скоро начнём использовать, убедитесь, что имя вашего модуля содержит точку, как точка в `.com` в `example.com/hello`. Пока ваш файл модуля минимален, и вы можете оставить его таким. Чтобы узнать больше о модулях, [вы можете ознакомиться со справочником в документации Golang](https://golang.org/doc/modules/gomod-ref). Теперь мы можем вернуться к тестированию и изучению Go, поскольку тесты должны работать, даже на Go 1.16.

В будущих главах вам нужно будет запускать `go mod init SOMENAME` в каждой новой папке перед выполнением таких команд, как `go test` или `go build`.

Стоит уточнить, что `SOMENAME`, имя модуля, не связано с `package main` (который каждый `.go` файл в этой книге до сих пор объявляет вверху). Имя модуля — это просто идентификатор для вашего проекта в целом — его не обязательно называть `main`, и `go run`, `go test`, и `go build` будут работать корректно с любым выбранным вами именем, запускаемые из той же папки.

## Возвращаемся к тестированию

Запустите `go test` в терминале. Он должен был пройти! Просто для проверки попробуйте намеренно сломать тест, изменив строку `want`.

Обратите внимание, что вам не пришлось выбирать между несколькими фреймворками для тестирования, а затем выяснять, как их установить. Все необходимое встроено в язык, и синтаксис такой же, как и остальной код, который вы будете писать.

### Написание тестов

Написание теста похоже на написание функции, с несколькими правилами:

*   Он должен находиться в файле с именем вроде `xxx_test.go`.
*   Тестовая функция должна начинаться со слова `Test`.
*   Тестовая функция принимает только один аргумент `t *testing.T`.
*   Чтобы использовать тип `*testing.T`, вам нужно `import "testing"`, как мы это делали с `fmt` в другом файле.

На данный момент достаточно знать, что ваш `t` типа `*testing.T` — это ваш "крючок" для тестового фреймворка, так что вы можете делать такие вещи, как `t.Fail()`, когда хотите, чтобы тест провалился.

Мы рассмотрели несколько новых тем:

#### `if`
Операторы `if` в Go очень похожи на другие языки программирования.

#### Объявление переменных

Мы объявляем некоторые переменные с синтаксисом `varName := value`, что позволяет нам повторно использовать некоторые значения в нашем тесте для читабельности.

#### `t.Errorf`

Мы вызываем _метод_ `Errorf` на нашем `t`, который выведет сообщение и провалит тест. Буква `f` означает формат (`format`), что позволяет нам строить строку со значениями, вставленными вместо заполнителей `%q`. Когда вы намеренно провалите тест, должно быть понятно, как это работает.

Вы можете узнать больше о строках-заполнителях в [документации fmt](https://pkg.go.dev/fmt#hdr-Printing). Для тестов `%q` очень полезен, так как он заключает ваши значения в двойные кавычки.

Позже мы рассмотрим разницу между методами и функциями.

### Документация Go

Еще одна удобная особенность Go — это документация. Мы только что видели документацию по пакету `fmt` на официальном сайте просмотра пакетов, и Go также предоставляет способы быстрого доступа к документации в автономном режиме.

Go имеет встроенный инструмент `doc`, который позволяет вам изучать любой пакет, установленный в вашей системе, или модуль, над которым вы в данный момент работаете. Чтобы просмотреть ту же документацию по глаголам Printing:

```
$ go doc fmt

scanf. The format 'verbs' are derived from C's but are simpler.

# Printing

The verbs:

General:

    %v	the value in a default format
    	when printing structs, the plus flag (%+v) adds field names
    %#v	a Go-syntax representation of the value
    %T	a Go-syntax representation of the type of the value
    %%	a literal percent sign; consumes no value
...
```

Второй инструмент Go для просмотра документации — команда `pkgsite`, которая лежит в основе официального сайта просмотра пакетов Go. Вы можете установить `pkgsite` с помощью `go install golang.org/x/pkgsite/cmd/pkgsite@latest`, а затем запустить его с помощью `pkgsite -open .`. Команда `go install` загрузит исходные файлы из этого репозитория и скомпилирует их в исполняемый бинарный файл. Для установки Go по умолчанию этот исполняемый файл будет находиться в `$HOME/go/bin` для Linux и macOS, и `%USERPROFILE%\go\bin` для Windows. Если вы ещё не добавили эти пути в вашу переменную `$PATH`, вы можете захотеть это сделать, чтобы упростить запуск команд, установленных с помощью `go`.

Подавляющее большинство стандартной библиотеки имеет отличную документацию с примерами. Стоит перейти по адресу [http://localhost:8080/testing](http://localhost:8080/testing), чтобы увидеть, что вам доступно.

### Привет, ТЫ

Теперь, когда у нас есть тест, мы можем безопасно итерировать наше программное обеспечение.

В последнем примере мы написали тест _после_ того, как код был написан, чтобы вы могли получить пример того, как писать тест и объявлять функцию. С этого момента мы будем _сначала писать тесты_.

Наше следующее требование — позволить нам указывать получателя приветствия.

Давайте начнём с того, что зафиксируем эти требования в тесте. Это базовый подход разработки через тестирование (TDD), который позволяет нам убедиться, что наш тест _действительно_ проверяет то, что мы хотим. При ретроспективном написании тестов существует риск того, что ваш тест может продолжать проходить, даже если код не работает так, как задумано.

```go
package main

import "testing"

func TestHello(t *testing.T) {
	got := Hello("Chris")
	want := "Hello, Chris"

	if got != want {
		t.Errorf("got %q want %q", got, want)
	}
}
```

Теперь запустите `go test`, у вас должна появиться ошибка компиляции:

```text
./hello_test.go:6:18: too many arguments in call to Hello
    have (string)
    want ()
```

При использовании статически типизированного языка, такого как Go, важно _слушать компилятор_. Компилятор понимает, как ваш код должен соединяться и работать, так что вам не нужно это делать.

В этом случае компилятор сообщает вам, что нужно сделать, чтобы продолжить. Мы должны изменить нашу функцию `Hello`, чтобы она принимала аргумент.

Измените функцию `Hello`, чтобы она принимала аргумент типа `string`:

```go
func Hello(name string) string {
	return "Hello, world"
}
```

Если вы снова попытаетесь запустить свои тесты, ваш `hello.go` не скомпилируется, потому что вы не передаете аргумент. Передайте "world", чтобы он скомпилировался.

```go
func main() {
	fmt.Println(Hello("world"))
}
```

Теперь, когда вы запустите свои тесты, вы должны увидеть что-то вроде:

```text
hello_test.go:10: got 'Hello, world' want 'Hello, Chris''
```

Наконец-то у нас есть компилирующаяся программа, но она не соответствует нашим требованиям, согласно тесту.

Давайте сделаем тест проходящим, используя аргумент `name` и объединив его с `Hello,`:

```go
func Hello(name string) string {
	return "Hello, " + name
}
```

Когда вы запустите тесты, они теперь должны пройти. Обычно, в рамках цикла TDD, мы должны теперь _рефакторить_.

### Заметка о системах контроля версий

На этом этапе, если вы используете систему контроля версий (что вам следовало бы!), я бы
`commit`-ил код в текущем виде. У нас есть рабочее программное обеспечение, поддерживаемое тестом.

Я _не_ стал бы пушить в `main`, потому что планирую рефакторинг. Приятно
сделать `commit` на этом этапе на случай, если вы каким-то образом запутаетесь при рефакторинге — вы всегда можете вернуться к рабочей версии.

Здесь не так много для рефакторинга, но мы можем ввести ещё одну языковую особенность — _константы_.

### Константы

Константы определяются так:

```go
const englishHelloPrefix = "Hello, "
```

Теперь мы можем рефакторить наш код:

```go
const englishHelloPrefix = "Hello, "

func Hello(name string) string {
	return englishHelloPrefix + name
}
```

После рефакторинга заново запустите тесты, чтобы убедиться, что вы ничего не сломали.

Стоит подумать о создании констант для фиксации смысла значений, а иногда и для повышения производительности.

## Привет, мир... снова

Следующее требование заключается в том, что когда наша функция вызывается с пустой строкой, по умолчанию она выводит "Hello, World", а не "Hello, ".

Начните с написания нового неработающего теста:

```go
func TestHello(t *testing.T) {
	t.Run("saying hello to people", func(t *testing.T) {
		got := Hello("Chris")
		want := "Hello, Chris"

		if got != want {
			t.Errorf("got %q want %q", got, want)
		}
	})
	t.Run("say 'Hello, World' when an empty string is supplied", func(t *testing.T) {
		got := Hello("")
		want := "Hello, World"

		if got != want {
			t.Errorf("got %q want %q", got, want)
		}
	})
}
```

Здесь мы представляем ещё один инструмент в нашем арсенале тестирования: подтесты. Иногда полезно группировать тесты вокруг "чего-либо", а затем иметь подтесты, описывающие различные сценарии.

Преимуществом такого подхода является возможность настроить общий код, который может быть использован в других тестах.

Пока у нас есть неработающий тест, давайте исправим код, используя `if`.

```go
const englishHelloPrefix = "Hello, "

func Hello(name string) string {
	if name == "" {
		name = "World"
	}
	return englishHelloPrefix + name
}
```

Если мы запустим наши тесты, мы должны увидеть, что новое требование выполняется, и мы не сломали случайно другую функциональность.

Важно, чтобы ваши тесты _были чёткими спецификациями_ того, что должен делать код. Но есть повторяющийся код, когда мы проверяем, соответствует ли сообщение нашим ожиданиям.

Рефакторинг предназначен не _только_ для production-кода!

Теперь, когда тесты проходят, мы можем и должны рефакторить наши тесты.

```go
func TestHello(t *testing.T) {
	t.Run("saying hello to people", func(t *testing.T) {
		got := Hello("Chris")
		want := "Hello, Chris"
		assertCorrectMessage(t, got, want)
	})

	t.Run("empty string defaults to 'world'", func(t *testing.T) {
		got := Hello("")
		want := "Hello, World"
		assertCorrectMessage(t, got, want)
	})

}

func assertCorrectMessage(t testing.TB, got, want string) {
	t.Helper()
	if got != want {
		t.Errorf("got %q want %q", got, want)
	}
}
```

Что мы здесь сделали?

Мы рефакторили наше утверждение в новую функцию. Это уменьшает дублирование и улучшает читабельность наших тестов. Нам нужно передать `t *testing.T`, чтобы мы могли указать тестовому коду, когда нужно провалиться.

Для вспомогательных функций хорошо принимать `testing.TB`, который является интерфейсом, удовлетворяемым как `*testing.T`, так и `*testing.B`, так что вы можете вызывать вспомогательные функции из теста или бенчмарка (не беспокойтесь, если слова вроде "интерфейс" пока ничего для вас не значат, это будет рассмотрено позже).

`t.Helper()` необходим, чтобы сообщить тестовому набору, что этот метод является вспомогательным. Делая это, при сбое номер строки, указанный в отчёте, будет находиться в нашем _вызове функции_, а не внутри нашего вспомогательного метода. Это поможет другим разработчикам легче отслеживать проблемы. Если вы всё ещё не понимаете, закомментируйте его, сделайте так, чтобы тест провалился, и понаблюдайте за выводом теста. Комментарии в Go — отличный способ добавить дополнительную информацию в ваш код, или в данном случае, быстрый способ указать компилятору игнорировать строку. Вы можете закомментировать код `t.Helper()`, добавив два косых слэша `//` в начало строки. Вы должны увидеть, как эта строка станет серой или изменит цвет по сравнению с остальной частью вашего кода, указывая, что она теперь закомментирована.

Когда у вас есть более одного аргумента одного и того же типа (в нашем случае две строки), вместо `(got string, want string)` вы можете сократить это до `(got, want string)`.

### Возвращаемся к системам контроля версий

Теперь, когда мы довольны кодом, я бы дополнил предыдущий коммит, чтобы мы зафиксировали только прекрасную версию нашего кода с его тестом.

### Дисциплина

Давайте ещё раз пройдёмся по циклу:

*   Напишите тест
*   Добейтесь прохождения компилятора
*   Запустите тест, убедитесь, что он проваливается, и проверьте, что сообщение об ошибке осмысленно
*   Напишите достаточно кода, чтобы тест прошёл
*   Выполните рефакторинг

На первый взгляд это может показаться утомительным, но придерживаться цикла обратной связи важно.

Это не только гарантирует, что у вас есть _релевантные тесты_, но и помогает _проектировать хорошее программное обеспечение_ благодаря рефакторингу, обеспеченному безопасностью тестов.

Просмотр того, как тест падает, является важной проверкой, потому что он также позволяет вам увидеть, как выглядит сообщение об ошибке. Как разработчику, может быть очень трудно работать с кодовой базой, когда неработающие тесты не дают чёткого представления о том, в чем проблема.

Обеспечивая _быстроту_ ваших тестов и настраивая инструменты так, чтобы запуск тестов был простым, вы можете войти в состояние потока при написании кода.

Не написав тесты, вы обязуетесь вручную проверять свой код, запуская программное обеспечение, что нарушает ваше состояние потока. Вы не сэкономите себе время, особенно в долгосрочной перспективе.

## Продолжаем! Больше требований

Боже мой, у нас ещё больше требований. Теперь нам нужно поддерживать второй параметр, указывающий язык приветствия. Если передаётся язык, который мы не распознаём, просто по умолчанию используйте английский.

Мы должны быть уверены, что можем легко использовать TDD для реализации этой функциональности!

Напишите тест для пользователя, передающего испанский язык. Добавьте его в существующий набор тестов.

```go
	t.Run("in Spanish", func(t *testing.T) {
		got := Hello("Elodie", "Spanish")
		want := "Hola, Elodie"
		assertCorrectMessage(t, got, want)
	})
```

Помните, не обманывайте! _Сначала тест_. Когда вы попытаетесь запустить тест, компилятор _должен_ пожаловаться, потому что вы вызываете `Hello` с двумя аргументами, а не с одним.

```text
./hello_test.go:27:19: too many arguments in call to Hello
    have (string, string)
    want (string)
```

Исправьте проблемы компиляции, добавив ещё один строковый аргумент в `Hello`:

```go
func Hello(name string, language string) string {
	if name == "" {
		name = "World"
	}
	return englishHelloPrefix + name
}
```

Когда вы снова попытаетесь запустить тест, он будет жаловаться на то, что в ваших других тестах и в `hello.go` недостаточно аргументов, передаваемых в `Hello`:

```text
./hello.go:15:19: not enough arguments in call to Hello
    have (string)
    want (string, string)
```

Исправьте их, передав пустые строки. Теперь все ваши тесты должны компилироваться _и_ проходить, кроме нашего нового сценария:

```text
hello_test.go:29: got 'Hello, Elodie' want 'Hola, Elodie'
```

Мы можем использовать `if` здесь, чтобы проверить, равен ли язык "Spanish", и если да, изменить сообщение:

```go
func Hello(name string, language string) string {
	if name == "" {
		name = "World"
	}

	if language == "Spanish" {
		return "Hola, " + name
	}
	return englishHelloPrefix + name
}
```

Тесты теперь должны проходить.

Пришло время для _рефакторинга_. Вы должны увидеть некоторые проблемы в коде: "магические" строки, некоторые из которых повторяются. Попробуйте отрефакторить код самостоятельно, и при каждом изменении убедитесь, что вы снова запускаете тесты, чтобы гарантировать, что ваш рефакторинг ничего не ломает.

```go
	const spanish = "Spanish"
	const englishHelloPrefix = "Hello, "
	const spanishHelloPrefix = "Hola, "

	func Hello(name string, language string) string {
		if name == "" {
			name = "World"
		}

		if language == spanish {
			return spanishHelloPrefix + name
		}
		return englishHelloPrefix + name
	}
```

### Французский

*   Напишите тест, утверждающий, что если вы передаёте `"French"`, вы получаете `"Bonjour, "`
*   Убедитесь, что он падает, проверьте, что сообщение об ошибке легко читаемо
*   Внесите минимальные разумные изменения в код

Вы могли написать что-то, что выглядит примерно так:

```go
func Hello(name string, language string) string {
	if name == "" {
		name = "World"
	}

	if language == spanish {
		return spanishHelloPrefix + name
	}
	if language == french {
		return frenchHelloPrefix + name
	}
	return englishHelloPrefix + name
}
```

## `switch`

Когда у вас много операторов `if`, проверяющих конкретное значение, вместо них часто используется оператор `switch`. Мы можем использовать `switch` для рефакторинга кода, чтобы сделать его более читабельным и расширяемым, если мы захотим добавить поддержку большего количества языков позже:

```go
func Hello(name string, language string) string {
	if name == "" {
		name = "World"
	}

	prefix := englishHelloPrefix

	switch language {
	case spanish:
		prefix = spanishHelloPrefix
	case french:
		prefix = frenchHelloPrefix
	}

	return prefix + name
}
```

Обратите внимание, что мы используем `:=` один раз для `prefix` (объявляя новую переменную и присваивая ей начальное значение), но просто `=` везде, где она изменяется, как для `name` выше, так и для `prefix` внутри `switch`. `:=` — это [короткое объявление переменной](https://go.dev/ref/spec#Short_variable_declarations) в Go — оно создаёт новую переменную. `=` — это [обычное присваивание](https://go.dev/ref/spec#Assignment_statements) — оно изменяет значение уже существующей переменной (`name` уже существует как параметр, а `prefix` уже был объявлен парой строк выше с помощью `:=`). Использование `:=` для переменной, которая уже существует в том же скоупе, или `=` для той, которая ещё не существует, является ошибкой компиляции.

Напишите тест, чтобы теперь включить приветствие на выбранном вами языке, и вы увидите, как просто расширить нашу _удивительную_ функцию.

### Еще... один... рефакторинг?

Можно утверждать, что наша функция становится немного большой. Самый простой рефакторинг для этого — выделить часть функциональности в другую функцию.

```go

const (
	spanish = "Spanish"
	french  = "French"

	englishHelloPrefix = "Hello, "
	spanishHelloPrefix = "Hola, "
	frenchHelloPrefix  = "Bonjour, "
)

func Hello(name string, language string) string {
	if name == "" {
		name = "World"
	}

	return greetingPrefix(language) + name
}

func greetingPrefix(language string) (prefix string) {
	switch language {
	case french:
		prefix = frenchHelloPrefix
	case spanish:
		prefix = spanishHelloPrefix
	default:
		prefix = englishHelloPrefix
	}
	return
}
```

Несколько новых концепций:

*   В сигнатуре нашей функции мы сделали _именованное возвращаемое значение_ `(prefix string)`.
*   Это создаст переменную `prefix` в вашей функции.
    *   Ей будет присвоено "нулевое" значение. Это зависит от типа; например, для `int` это 0, а для `string` это `""`.
    *   Вы можете вернуть то, чему оно равно, просто вызвав `return`, а не `return prefix`.
    *   Это будет отображаться в Go Doc для вашей функции, что может сделать намерение вашего кода более ясным.
*   `default` в операторе `switch` будет выполнен, если ни один из других операторов `case` не совпадёт.
*   Имя функции начинается со строчной буквы. В Go публичные функции начинаются с заглавной буквы, а приватные — со строчной. Мы не хотим, чтобы внутренние детали нашего алгоритма были доступны миру, поэтому мы сделали эту функцию приватной.
*   Кроме того, мы можем группировать константы в блок вместо объявления их на отдельной строке. Для читабельности хорошей идеей является использование пустой строки между связанными наборами констант.

Кто бы мог подумать, что можно получить так много от `Hello, world`?

К этому моменту вы должны иметь некоторое представление о:

### Некоторых синтаксических особенностях Go, касающихся

*   Написания тестов
*   Объявления функций, с аргументами и типами возвращаемых значений
*   `if`, `const` и `switch`
*   Объявления переменных и констант

### Процессе TDD и _почему_ шаги важны

*   _Написание неработающего теста и наблюдение за его сбоем_, чтобы мы знали, что написали _релевантный_ тест для наших требований, и увидели, что он выдает _легко понятное описание ошибки_.
*   Написание минимального количества кода, чтобы тест прошел, чтобы мы знали, что у нас есть работающее программное обеспечение.
*   _Затем_ рефакторинг, поддерживаемый безопасностью наших тестов, для обеспечения хорошо написанного кода, с которым легко работать.

В нашем случае мы перешли от `Hello()` к `Hello("name")`, а затем к `Hello("name", "French")` небольшими, легко понятными шагами.

Конечно, это тривиально по сравнению с программным обеспечением "реального мира", но принципы остаются в силе. TDD — это навык, требующий практики для развития, но разбивая проблемы на более мелкие компоненты, которые вы можете протестировать, вы значительно упростите себе написание программного обеспечения.
