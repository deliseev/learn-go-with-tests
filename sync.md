# Синхронизация

**[Весь код для этой главы вы можете найти здесь](https://github.com/quii/learn-go-with-tests/tree/main/sync)**

Мы хотим создать счетчик, который безопасно использовать в параллельной среде.

Мы начнем с небезопасного счетчика и проверим, как он работает в однопоточной среде.

Затем мы проверим его небезопасность, используя несколько горутин, пытающихся использовать счетчик через тест, и исправим ее.

## Сначала напишите тест

Мы хотим, чтобы наш API предоставлял нам метод для увеличения счетчика, а затем получения его значения.

```go
func TestCounter(t *testing.T) {
	t.Run("incrementing the counter 3 times leaves it at 3", func(t *testing.T) {
		counter := Counter{}
		counter.Inc()
		counter.Inc()
		counter.Inc()

		if counter.Value() != 3 {
			t.Errorf("got %d, want %d", counter.Value(), 3)
		}
	})
}
```

## Попробуйте запустить тест

```

```

Давайте определим `Counter`.

```go
type Counter struct {
}
```

Попробуйте еще раз, и он завершится с ошибкой:


Итак, чтобы наконец запустить тест, мы можем определить эти методы:

```go
func (c *Counter) Inc() {

	return 0
```

Теперь он должен запуститься и завершиться с ошибкой:

## Напишите достаточно кода, чтобы тест прошел

Это должно быть тривиально для таких Go-экспертов, как мы. Нам нужно хранить некоторое состояние для счетчика в нашем типе данных, а затем увеличивать его при каждом вызове `Inc`.

```go
type Counter struct {
	value int
}

func (c *Counter) Inc() {
	c.value++
}

func (c *Counter) Value() int {
	return c.value
}
```

## Рефакторинг

Рефакторить особо нечего, но, учитывая, что мы собираемся написать больше тестов для `Counter`, мы напишем небольшую функцию утверждения `assertCounter`, чтобы тест читался немного понятнее.

```go
t.Run("incrementing the counter 3 times leaves it at 3", func(t *testing.T) {
	counter := Counter{}
	counter.Inc()
	counter.Inc()
	counter.Inc()

	assertCounter(t, counter, 3)
})
```
```go
func assertCounter(t testing.TB, got Counter, want int) {
	t.Helper()
	if got.Value() != want {
		t.Errorf("got %d, want %d", got.Value(), want)
	}
}
```

## Следующие шаги

Это было достаточно просто, но теперь у нас есть требование, что он должен быть безопасным для использования в параллельной среде. Нам нужно будет написать неудачный тест, чтобы проверить это.

## Сначала напишите тест

```go
t.Run("it runs safely concurrently", func(t *testing.T) {
	wantedCount := 1000
	counter := Counter{}

	var wg sync.WaitGroup
	wg.Add(wantedCount)

	for i := 0; i < wantedCount; i++ {
		go func() {
			counter.Inc()
			wg.Done()
		}()
	}
	wg.Wait()

	assertCounter(t, counter, wantedCount)
})
```

Это пройдет по нашему `wantedCount` и запустит горутину для вызова `counter.Inc()`.

Мы используем [`sync.WaitGroup`](https://golang.org/pkg/sync/#WaitGroup), что является удобным способом синхронизации параллельных процессов.

> WaitGroup ожидает завершения набора горутин. Основная горутина вызывает Add, чтобы установить количество горутин для ожидания. Затем каждая из горутин выполняется и вызывает Done по завершении. В то же время Wait может быть использован для блокировки до тех пор, пока все горутины не завершат работу.

Ожидая завершения `wg.Wait()` перед выполнением наших утверждений, мы можем быть уверены, что все наши горутины попытались увеличить (`Inc`) `Counter`.

## Попробуйте запустить тест

```
=== RUN   TestCounter/it_runs_safely_in_a_concurrent_envionment
--- FAIL: TestCounter (0.00s)
    --- FAIL: TestCounter/it_runs_safely_in_a_concurrent_envionment (0.00s)
    	sync_test.go:26: got 939, want 1000
FAIL
```

Тест _вероятно_ завершится с ошибкой с другим числом, но, тем не менее, он демонстрирует, что счетчик не работает, когда несколько горутин пытаются одновременно изменить его значение.

### Почему это происходит?

`c.value++` выглядит как единая, неделимая операция, но это не так. Это сокращение для чего-то более похожего на:

```go
tmp := c.value // 1. read
tmp = tmp + 1  // 2. increment
c.value = tmp  // 3. write
```

Каждый из этих трех шагов является отдельной операцией, и среда выполнения Go может свободно переключаться между горутинами в любой момент между ними. Если две горутины вызывают `Inc` примерно в одно и то же время, их шаги могут переплетаться, например:

```
goroutine A: reads c.value (0)
goroutine B: reads c.value (0)
goroutine A: increments its copy to 1
goroutine B: increments its copy to 1
goroutine A: writes c.value = 1
goroutine B: writes c.value = 1
```

Обе горутины вызвали `Inc` по одному разу, поэтому мы бы хотели, чтобы `c.value` стало `2`, но оно становится `1`. Одно из увеличений было незаметно потеряно, потому что обе горутины прочитали одно и то же начальное значение, прежде чем какая-либо из них записала свой результат обратно. Это называется _состояние гонки_ (race condition), и с тысячью горутин, одновременно соревнующихся за чтение, увеличение и запись, неудивительно, что некоторые из этих увеличений теряются.

## Напишите достаточно кода, чтобы тест прошел

Простое решение — добавить блокировку к нашему `Counter`, гарантируя, что только одна горутина может увеличивать счетчик за раз. [`Mutex`](https://golang.org/pkg/sync/#Mutex) из Go предоставляет такую блокировку:

> Mutex — это блокировка взаимного исключения. Нулевое значение для Mutex — это разблокированный мьютекс.

```go
type Counter struct {
	mu    sync.Mutex
	value int
}

func (c *Counter) Inc() {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.value++
}
```

Это означает, что любая горутина, вызывающая `Inc`, получит блокировку на `Counter`, если она будет первой. Всем остальным горутинам придется ждать, пока блокировка будет снята (`Unlock`ed), прежде чем получить доступ.

Если вы теперь запустите тест снова, он теперь должен пройти, поскольку каждая горутина должна ждать своей очереди, прежде чем вносить изменения.

## Я видел другие примеры, где `sync.Mutex` встраивается в структуру.

Вы можете увидеть такие примеры:

```go
type Counter struct {
	sync.Mutex
	value int
}
```

Можно утверждать, что это может сделать код немного элегантнее.

```go
func (c *Counter) Inc() {
	c.Lock()
	defer c.Unlock()
	c.value++
}
```

Это _выглядит_ красиво, но, хотя программирование — это чрезвычайно субъективная дисциплина, это **плохо и неправильно**.

Иногда люди забывают, что встраивание типов означает, что методы этого типа становятся _частью публичного интерфейса_; и вы часто этого не захотите. Помните, что мы должны быть очень осторожны с нашими публичными API: момент, когда мы делаем что-то публичным, — это момент, когда другой код может связаться с этим. Мы всегда хотим избежать ненужной связанности.

Предоставление `Lock` и `Unlock` в лучшем случае сбивает с толку, но в худшем случае потенциально очень вредно для вашего программного обеспечения, если пользователи вашего типа начнут вызывать эти методы.

![Показывает, как пользователь этого API может ошибочно изменить состояние блокировки](https://i.imgur.com/SWYNpwm.png)

_Это кажется очень плохой идеей_

## Копирование мьютексов

Наш тест проходит, но наш код все еще немного опасен.

Если вы запустите `go vet` на своем коде, вы должны получить ошибку, подобную следующей:

```
sync/v2/sync_test.go:16: call of assertCounter copies lock value: v1.Counter contains sync.Mutex
sync/v2/sync_test.go:39: assertCounter passes lock by value: v1.Counter contains sync.Mutex
```

Взглянув на документацию [`sync.Mutex`](https://golang.org/pkg/sync/#Mutex), мы узнаем, почему:

> Mutex не должен быть скопирован после первого использования.

Когда мы передаем наш `Counter` (по значению) в `assertCounter`, он попытается создать копию мьютекса.

Чтобы решить эту проблему, мы должны передать **указатель** на наш `Counter` вместо этого, поэтому измените сигнатуру `assertCounter`:

```go
func assertCounter(t testing.TB, got *Counter, want int)
```

Наши тесты больше не будут компилироваться, потому что мы пытаемся передать `Counter`, а не `*Counter`. Чтобы решить эту проблему, я предпочитаю создать конструктор, который покажет читателям вашего API, что лучше не инициализировать тип самостоятельно.

```go
func NewCounter() *Counter {
	return &Counter{}
}
```

Используйте эту функцию в своих тестах при инициализации `Counter`.

## Альтернатива: sync/atomic

`Mutex` — это универсальный инструмент: он может защищать любое количество полей и любые инварианты между ними, если вы помните о `Lock`/`Unlock` при каждом доступе. Но наш `Counter` настолько прост, насколько это возможно для общего состояния: одно целое число, увеличиваемое из нескольких горутин. Именно для таких случаев пакет [`sync/atomic`](https://pkg.go.dev/sync/atomic) предоставляет типы, такие как [`atomic.Int64`](https://pkg.go.dev/sync/atomic#Int64), которые обеспечивают безопасный параллельный доступ к одному значению без отдельной блокировки:

```go
type Counter struct {
	value atomic.Int64
}

func NewCounter() *Counter {
	return &Counter{}
}

func (c *Counter) Inc() {
	c.value.Add(1)
}

func (c *Counter) Value() int64 {
	return c.value.Load()
}
```

Никаких `Mutex`, никаких `Lock`/`Unlock`, и по-прежнему безопасно вызывать `Inc` из любого количества горутин одновременно — тот же тест, который мы написали ранее, проходит без изменений. Под капотом это использует низкоуровневые инструкции ЦПУ, чтобы сделать само увеличение атомарным, что обычно быстрее, чем `Mutex` для таких простых случаев. `atomic.Int64` (и его аналоги, такие как `atomic.Int32` и `atomic.Bool`) также не могут быть использованы неправильно, как это было возможно с вызовами функций в стиле `atomic.AddInt64(&x, 1)` в старых версиях Go — вы не можете забыть передать указатель, и вы не можете случайно прочитать поле, не пройдя через `Load`.

Обращайтесь к типам `sync/atomic`, когда вы защищаете одно значение; обращайтесь к `Mutex`, когда вам нужно поддерживать согласованность нескольких полей или какого-либо инварианта между ними.

## Подведение итогов

Мы рассмотрели несколько вещей из [пакета sync](https://golang.org/pkg/sync/):

-   `Mutex` позволяет нам добавлять блокировки к нашим данным.
-   `WaitGroup` — это средство ожидания завершения горутинами задач.
-   `sync/atomic` предлагает безопасный, безблокировочный доступ к отдельным значениям, и его стоит использовать, когда полноценный `Mutex` был бы избыточен.

### Когда использовать блокировки вместо каналов и горутин?

[Ранее мы рассматривали горутины в первой главе о параллелизме](concurrency.md), которые позволяют нам писать безопасный параллельный код, так почему же вы будете использовать блокировки?
[В вики Go есть страница, посвященная этой теме; Mutex или Канал](https://go.dev/wiki/MutexOrChannel).

> Распространенная ошибка новичков в Go — чрезмерное использование каналов и горутин только потому, что это возможно и/или потому, что это весело. Не бойтесь использовать `sync.Mutex`, если он лучше всего подходит для вашей задачи. Go прагматичен, позволяя вам использовать инструменты, которые лучше всего решают вашу проблему, и не принуждая вас к одному стилю кода.

Перефразируя:

-   **Используйте каналы при передаче владения данными**
-   **Используйте мьютексы для управления состоянием**

### go vet

Не забудьте использовать `go vet` в своих скриптах сборки, поскольку он может предупредить вас о некоторых тонких ошибках в вашем коде, прежде чем они дойдут до ваших несчастных пользователей.

### Не используйте встраивание только потому, что это удобно

-   Подумайте о том, как встраивание влияет на ваш публичный API.
-   Действительно ли вы _хотите_ раскрывать эти методы и позволять людям связывать с ними свой код?
-   Что касается мьютексов, это может быть потенциально катастрофическим очень непредсказуемым и странным образом. Представьте себе какой-либо вредоносный код, разблокирующий мьютекс, когда он не должен этого делать; это вызовет очень странные ошибки, которые будет трудно отследить.
